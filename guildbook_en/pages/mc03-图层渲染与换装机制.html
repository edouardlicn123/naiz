Layer Rendering and Costume-Change Mechanics

Created: 2026-06-27
Last updated: 2026-09-11

This page explains the Naiz engine's layer-rendering architecture from a creator's point of view — how sprites, the dialogue box, and the background stack on top of each other, and the rendering strategy for expression and costume changes.

1. The layer stack (bottom to top)

The PC-98 PEGC provides 2 graphics planes (Graphic Plane A + B) combined into a single-layer 8-bit 256-color VRAM (640×400), plus a separate hardware text plane (Text Plane). The engine uses only the graphics VRAM (the drawing target can switch between VRAM and the RAM composite buffer: render_set_target / text_set_target); the text plane is unusable — it is invisible under DOS/4GW protected mode, see fd01 §1.4. The engine achieves a multi-layer stack on the single-layer VRAM through ordered multi-pass rendering:

Layer 0: background (bg MAG)
Layer 1: dialogue-box background-region restore
Layer 2: sprites (character sprites, up to 16)
Layer 3: dialogue box (transparent/semi-transparent/solid base color)
Layer 4: text (dialogue lines, drawn over the dialogue box)
Layer 5: menu overlay (menu_layer, RAM composite buffer → fullscreen blit)

Each pass writes only the region belonging to its layer and never overwrites what is already drawn beneath. Menus (main menu/load/settings/gallery) are "transient overlays": when activated, the content is first drawn into a dedicated RAM composite buffer, then published to VRAM fullscreen by menu_layer_blit; on exit the underlying picture is restored. See §6 The menu layer.

2. Sprite (character sprite) mechanics

The engine controls sprites via the char command. See mc02 Sprites and Characters for details.

2.1 Showing and positioning

char charlie l            # show charlie on the left (default body; the left position mirrors horizontally)
char charlie r expr_happy # show charlie on the right, expression happy (face)
char charlie c body       # show charlie in the center (body, full figure)

2.2 Expression change / costume change

char charlie l expr_angry # refreshes only the face region (face mode, dialogue box not redrawn)
char charlie c body       # switches the body; not limited by clip_h

face constraint: an expression change (face) draws only in the upper-body region y < 280 and never touches the dialogue-box area.

Full-height drawing (since R20): sprites (body / full figure) are drawn at full height, no longer clipped because of the dialogue box — the dialogue box is composited on top of them (higher in z-order), and the PAT75 pseudo-transparency holes let the sprite's legs show through; calc_sprite_clip_h() now serves only the upper-body clipping of face expressions.

3. Dialogue box rendering

For the dialogue box's visual styles, see cf03 Dialogue Box Style Scheme. This section covers how the dialogue box appears, updates, and is cleaned up within the render pipeline.

3.1 When it appears

The dialogue box is triggered by text commands: when the scenario's first line of dialogue (host{...}, dialogue commands, etc.) appears, the engine pops up the dialogue box automatically. The flow:

  1. The text command calls dialog_show() (nb_dialog.c)
  2. If the dialogue box is not yet shown → layer_dialog_show(): build the composite buffer and publish "the frame + the current page of text" to VRAM
  3. If the dialogue box is already shown (page turn / subsequent lines) → redraw the frame page within the composite buffer and update the text

In other words: within one scene the dialogue box pops up only once; subsequent lines reuse the same frame and only replace the text content.

3.2 First popup (layer_dialog_show)

On first appearance it is built in this order:

  1. Allocate the composite buffer dialog_layer (480×115: frame + current page of text) and the active base dialog_occluder (plain background for the dialogue-box region + any sprite pixels already inside the frame)
  2. Draw the dialogue box's base color (semi-transparent pattern or solid fill, per the style setting) plus the 2px white border into the composite buffer
  3. Mark "dialogue box shown"

On every subsequent text refresh, only the frame page is redrawn within the composite buffer (clearing the previous page's text) plus the new text written, and the whole frame is published to VRAM — nothing outside the base color and border needs redrawing.

3.3 Composite buffer vs. active base

The dialogue-box region is carried by two independent RAM allocations with opposite purposes:

MemoryContentsPurpose
dialog_layerComposite buffer (frame + current page of text)After compositing, the whole frame is blitted to VRAM; after a background change the base is rebuilt against the new underlying picture, and the frame + current page of text are regenerated via "render projection"
dialog_occluderActive base (plain background for the dialogue-box region + sprite pixels inside the frame)Serves as the composite buffer's base (the PAT75 pseudo-transparency holes show the background/sprites through); when the dialogue box is hidden, it is used to restore that region to plain background

Key point: the plain base behind the dialogue box comes from the background layer (under_dialog). The active base must be rebuilt after every background change and every character added or removed; otherwise the pseudo-transparency and the hide-restore would use the wrong picture.

3.4 Dialogue box disappearance / cleanup

Three cases by trigger, with different degrees of cleanup:

ScenarioTriggerWhat happens
Normal hidebg(hidedialog) or char(hideall)The dialogue-box region is restored to plain background → the box disappears; the composite buffer and active base are kept, so it can pop up again quickly
Background changebg(...){key}The frame + current page of text survive across images (rebuilt against the new underlying picture and republished); cg(){key} instead retracts the dialogue box automatically and clears the dialogue
Scene switchscene(...)All state is cleared and the buffer memory freed; the next scene's first dialogue line pops the box up again

3.5 Character-coupled cleanup

When a character's body overlaps the dialogue-box region, cleanup must happen in order:

  • Hiding one character: if that character's body overlaps the dialogue box → after hiding, rebuild the active base and republish the composite buffer (the pseudo-transparency holes show the new picture)
  • The last character disappearing: first restore the background in the character region (above the dialogue box), then rebuild the active base (the picture above the dialogue box has changed)
  • char(hideall) (hide all characters) — the full chain:
    1. Hide every character one by one (rebuilding the active base each time)
    2. Hide the dialogue box: restore the plain background to the dialogue-box region
    3. Clear the dialogue state (character name and dialogue buffer reset to zero)

4. Background / CG and scene switching

  • bg(){key}: loads the new background MAG and captures the picture underneath; the dialogue box survives across images — the active base is automatically rebuilt against the new underlying picture, the "frame + current page of text" are regenerated via "render projection" and published (the background key goes in the curly-brace payload)
  • cg(){key}: shows the CG fullscreen and automatically retracts the dialogue box, clearing the current line (a fullscreen event; the next dialogue line reopens the box)
  • bg(hidedialog) / cg(hidedialog): only retracts the dialogue box and restores the dialogue-box region's background; no new image is loaded
  • Every scene(...) switch: the screen is automatically cleared to black, then the new scene's bg(...) command runs

6. The menu layer (menu_layer)

Four menus — the main menu (mainmenu()), load/save (save/load), settings (settingmenu()), and the CG gallery (cgvmenu()) — share one reusable wrapper, menu_layer: when a menu activates, its content is first drawn into a dedicated RAM composite buffer, and finally published to VRAM fullscreen. This and the dialogue box's composite buffer (§3.3) are two independent mechanisms — the dialogue box persists throughout the presentation, while menus are transient overlays.

Menus come in two modes:

ModeApproachCurrently used by
opaque (full opaque mask)On open, the underlying VRAM picture is snapshotted as the base (menu_layer_open); content is drawn into the composite buffer and published fullscreen by menu_layer_blit or locally by blit_rect; on close the base is restored in one block (menu_layer_close(1)) and the underlying picture comes back intactAll four menus
transparent (see-through cutout)The composite buffer is filled with the transparent index and the blit skips transparent pixels one by one (does not obscure the layer below, needs no base memory); on close, no restoreReserved (for future menu reuse)

Local changes such as focus movement go through an incremental session: menu_layer_begin_draw() (reattach the buffer target) → redraw only the changed text/indicators → menu_layer_commit() → menu_layer_blit_rect() (publish only the changed rectangles). The settings menu additionally uses menu_layer_erase_to_base() to erase the old language name/cursor region back to the underlying picture before drawing the new one, replacing the old VRAM snapshot array. For the API contract and integration examples, see the header comment in menu_layer.h.
