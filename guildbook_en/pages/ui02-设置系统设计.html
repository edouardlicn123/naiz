Settings System Design

Created: 2026-06-27
Last updated: 2026-07-01

This page covers the configuration side of the game settings system, including the two separately owned configuration files (config.toml and USER.CFG) and the settingmenu command.

1. Split Configuration Files

Key concept: configuration is split into a "project" copy and a "player" copy, with opposite ownership.An earlier settings.txt mixed the two together and is now abolished — the engine no longer parses any project configuration file at runtime.
CarrierOwnerWhat it holdsHow it reaches the engine
config.toml Project Dialogue box style, button colors, blackletter toggle, default language, version number, title, transitions Compiled into the engine at build time: export_config.py generates the NAIZ_* macros in nb_config.h → zero parsing at runtime
USER.CFG Player lang text_speed bgm snd vc bgm_vol pcm_vol Read at runtime by prefs_load() and written back by prefs_save(), the only runtime write point in the whole system

USER.CFG is plain-text key/value pairs, one key=value per line:

lang=chi
text_speed=2
bgm=1
bgm_vol=8

Why they must be separate: the lang key exists only in USER.CFG across the whole system. It used to exist in both files, and the function that read it and the function that wrote it were each bound to a different copy — the player picked Traditional Chinese in the boot menu, yet the game still started in English. Same key name, opposite ownership, is exactly the breeding ground for that mismatch, so project-side keys are always named differently (default_lang rather than lang).

Two ways to change configuration: change project configuration → edit config.toml and rebuild (the macros are compile-time); reset player settings → delete USER.CFG.

Why is config.toml not read at runtime?Because project configuration is fixed long before the player gets the game, so there is no reason for it to change at runtime. Compiling it into the engine removes the parsing code and also makes "wrong configuration" show up at build time, instead of the player entering the game and seeing a garbled screen.

2. Dialogue Box Style (config.toml's [dialog] style)

[dialog]
style = 5

Sets the dialogue box background style. style is an integer from 0–9, corresponding to 10 presets. Each preset defines the background color, border color, and how translucency is handled.

See cf03 — dialogue box style presets for the full presets.

3. Button Colors (config.toml's [button] style)

[button]
style = 2

Sets the menu button colors. style is an integer from 0–4:

ValueColors
0Black
1Blue
2Dark red
3Green
4Purple

See cf04 — button style presets for the full color and visual specifications.

4. lang — Multilingual Switching (USER.CFG's lang)

lang=chi

lang sets the game's display language and is written in USER.CFG. It is the player's own choice and does not belong to project configuration — which is why it is not in config.toml. All 9 languages are supported:

ValueLanguage
engEnglish
chiSimplified Chinese
chtTraditional Chinese
jpnJapanese
korKorean
freFrançais
gerDeutsch
itaItaliano
spaEspañol
porPortuguês

A missing USER.CFG is a normal first-run state; the engine then falls back to default_lang from config.toml.

Language must be chosen in the boot menu; it cannot be changed inside the game.The boot menu runs before the translation tables are loaded and can only draw pure ASCII; and since the language must be chosen before the translation tables exist, it can no longer be changed once you are in the game. That is why the Language line stays in the boot menu permanently.

When displaying command text, the engine uses tr() to look up the translation file for the corresponding language, i18n/*_<lang>.txt.

5. The settingmenu Command

settingmenu()

The settings menu command; currently a reserved stub with no effect yet. In the future it will provide a runtime settings screen, letting players change player-level preferences such as language and volume (USER.CFG) during the game — project-level styles (config.toml) are not in scope — and other options.
