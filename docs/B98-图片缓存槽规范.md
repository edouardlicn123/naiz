# B98 — 图片缓存槽规范

**代码**：`core/engine/image_cache.c`
**声明**：`core/engine/image_internal.h`
**相关**：`image.c`（IMAGE.DAT TOC 与解码入口）、`mag.h`（引用计数）

## 一、槽结构

```c
#define IMAGE_CACHE_SLOTS      32    /* 一次场景预取可装下全部 bg/char/cg */
#define IMAGE_CACHE_PREFETCH_HITS 4  /* 预取图的命中地板，防止刚预取就被淘汰 */

typedef struct {
    int       id;    /* asset_id，-1 表示空槽 */
    MagImage *img;   /* 解码结果，槽持有一份引用 */
    int       hits;  /* LRU 访问计数 */
    int       ready; /* 槽内是完整图像 */
} ImageCacheSlot;
```

## 二、所有权模型（引用计数，禁止深拷贝）

| 操作 | 语义 |
|---|---|
| `image_cache_lookup(id)` | 命中则 `mag_retain()` 后返回共享指针，**调用方必须 `mag_release()`** |
| `image_cache_insert(id, img)` | 缓存**接管** `img` 所有权，调用方不得再 release |
| 淘汰 / `image_cache_clear()` | 槽位 `mag_release()` 掉落缓存自身引用 |

借用指针不会悬空：只要槽位未淘汰，它始终持有活引用；淘汰只丢弃自己那一份。

## 三、策略

- **淘汰**：选 `hits` 最小的非空槽；同分按槽序（先到先淘汰）。
- **预取地板**：`image_prefetch()` 插入时把 `hits` 抬到 `IMAGE_CACHE_PREFETCH_HITS`，避免「刚预取、还没用就被新图挤掉」（devdoc 133 方案 D）。
- **ready**：`insert` 只接收完整解码结果，因此插入即置位；不存在「半个槽」状态。
- **容量**：32 槽只占指针级内存，真正的堆开销在 `MagImage` 本身；预取只保留脚本实际引用的资产。

## 四、与其它缓存的分工

| 缓存 | 内容 | 位置 |
|---|---|---|
| image cache | 解码后的 MAG 图像（按 `asset_id`） | 本模块 |
| snapshot cache | 图层快照（对话盒背景恢复等） | `image.c` 的快照区，见 B16 |
| VRAM bank | 前台/后台页 | `hal_pc98.c` |

三者互不替代：image cache 命中减少解码，snapshot cache 减少重绘，VRAM bank 负责翻页。

## 五、禁止事项

1. `lookup()` 返回的指针**不得**释放两次，也不得传给 `insert()`（会破坏引用计数）。
2. 不要在 `insert()` 之后继续使用传入的 `img` 指针——所有权已转移。
3. 不要在渲染循环里调用 `image_cache_clear()`；它只用于场景重载 / 退出。
4. 新增缓存入口不得绕过 `hits` 更新，否则 LRU 退化。

## 六、验收

- `image_cache_lookup()` 与 `mag_release()` 成对出现（审计 `tools/diag/symbol_audit.py` 可查调用面）。
- 连续切换 10 个场景后，槽位数稳定在 32，无增长、无泄漏。
