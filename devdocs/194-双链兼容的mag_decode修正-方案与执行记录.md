## 一、结论摘要（S2 定位后更新）

S2 阶段拿到了比 192 更硬的证据：**根因不是位流、不是 ISR，而是 action 表里被写入了一个
"含 0 nibble" 的字节**。三个独立的观测一起闭合了这个缺口：

1. **标准路径**（Python 等价实现，`/tmp` 探针，同一 `IMAGE.DAT` 第 13 项
   `yellow_grid`、11017B）：`iters=64000 out_pos=256000 fb=2120 col=80`，
   `n==0` 共 40 次，**全部发生在 out_pos ≤ 624（前 157 次迭代内）**——即 80 字节
   颜色流在图像前 0.25% 就被用完。
2. 因此 `out_pos > 626` 之后出现任何 `n==0` 都是**不可能**的；而 C 侧失败点恒在
   `255994 / 255998`。这两处的 `col=80 fb=2120 fapos=8000` 与标准路径完全一致，
   说明位流、flag B、颜色流都被恰好用完，**解码路径本身没有分歧**。
3. `n` 只来自 `action[act_idx % action_size]`。标准路径的 action 表内容为
   `41 11 11 11` 周期重复（160 项），**没有任何一项为 0**，两个 nibble 都非零。
   所以 C 侧那次 `n==0` 只能是 action 字节被外力改成了 `0x10` / `0x00` 一类值。

链式后果（这就是 192 一直看到的 `code=11` 假象）：

```
n==0 且 col 已耗尽 → error=12, break 内层
   ↓ 外层 while 没有检查 decode_ok，继续跑
后续每次迭代都读 1 bit、内层全部因同样原因 break（out_pos 不再前进）
   ↓ flag A 8000 字节耗尽
a = br_read() == -1 → 覆盖成 error=11，progress 记在同一个 out_pos
```

于是所有失败都被报成 `code=11`，且 `iters` 比标准路径多 1（第 64001 次读到位流末尾的
`-1`）。样本 A（`at=36044`）同理：那是 action/reader 更早被改写后的另一种表现。

**推论**：P1（Timer-B ISR 反射）被 S4 反证——gate 关掉 ISR 后失败依旧，只是失败点
从 `255998` 变成 `255994`。ISR 可以损伤栈帧，但解释不了"heap 里 action 表的某一个字节
恰好变成 0x10"。真正的破坏面是**解码器的工作区（堆块）被同进程的其他代码写穿**。

本轮的修正策略因此调整为**两层**：

1. **让失败可知、可归因**（已落地）：主循环遇错立即退出（不再让 `code=12` 被 `code=11`
   掩盖），并记录 `err12` 现场；action 表加影子副本，每 1KB 输出比对一次，
   把"哪个字节、被改成什么、发生在哪段输出"钉死。
2. **让破坏无害**（待落地）：影子校验命中时用影子值恢复，解码继续并按标准路径走完；
   两条链都受益，与是谁写穿无关。

顺序：先 1（纯观测，可回归），再 2；每一步都必须在两条链上各跑对照。

## 二、现象与已排除项（引自 192，不重复展开）

| 事实 | 含义 |
|---|---|
| 失败族恒为 `code=11`，失败后引擎继续正常运行 | 不是崩溃、不是 OOM |
| `image 13` 位流 64000 bit 零余量，Python 等价实现恰好用完 | 多要 1 bit 必失败 |
| 样本 A：`at=36044`，只消耗约 1127 字节（可用 8000） | 位流未到边界却报越界 → `fa` 字段被改 |
| 样本 B：`at=255998`，最后一个块少 2 字节 | 迭代数/`out_pos` 被扰动 |
| DOS4GW 变体同代码同数据未复现；开源链约 1/4 | 强烈指向 extender 差异 |
| 失败日志前一行固定是 `BGM IRQ ... co-operative pump stays active` | 失败窗口内 ISR 在活动 |

已排除：MAG 数据损坏、算法错误、TOC/注入、4bpp/裁剪路径、malloc 失败、extender 绑定。

## 四、修正设计

### F1（必做，双链通用）解码状态迁出栈

把 `mag_decode()` 的 `BitReader fa` 以及主循环的几个标量放进一个**独立的解码上下文**
（堆块或文件级静态结构，带 canary），所有读写经由该结构。解码算法与输出逐字节不变。

- 验收：`yellow_grid` 本地 harness 仍 `rc=0`；两条链 20 连跑无 `code=11`。
- 副作用：`mag_decode` 的栈占用变小（对 P5 也有效）；不可重入（引擎本来就是单线程解码，
  `mag_decode_into` 是第二份实现，需独立处理）。
- 观测：canary 命中时在日志里输出被改的字段序号。

### F5（新增，双链通用）action 表的影子与自愈

`MagBrGuard` 增加 `uint8_t act[MAG_ACT_SHADOW_MAX]`（512B，堆块内，不新增静态对象）；
每次 XOR 写 action 时同步影子，每 `MAG_ACT_CHECK_STRIDE`（1KB 输出）比对一次。

- **观测模式（当前）**：命中只记录 `act_bad/val/exp/out/it`，不恢复，让失败照常复现，
  以便定位写入者。日志形如 `act ok=1 bad=.. val=10 exp=11 at=...`。
- **修复模式（下一步）**：命中即 `action[k] = shadow[k]` 恢复，解码继续走标准路径。
  action 表是 160 字节的纯查表状态，恢复是精确的，不会引入近似值。
- 代价：每 1KB 输出 160 次字节比较（约 0.4% 的解码时间），两条链一致。
- 验收：日志出现 `act bad=n` 但 `image_load(13)` 成功、画面正常；20 连跑 0 失败。

### F6（新增，可选）失败重试

`image_load()` / `image_prefetch()` 在 `mag_decode` 失败时重试一次。数据是只读的、
解码是纯函数，重试只会拿到同样的结果——**除非**破坏是瞬时的。因此 F6 只作为
F5 之后的兜底，不作为主修法（避免"靠重试蒙过去"）。

### F2/F3（降级，暂不执行）

S4 反证后，ISR 不再是主因；`EXTENDER=dos32a` 目前保留 `hal_bgm_irq_init()` 早退的
gate（`NAIZ_DOS32A`），等 F5 落地、双链 20 连跑稳定后再评估是否恢复 Timer-B ISR。

- **F2a**：改用 DPMI `INT 31h AX=0303h` 安装 PM 中断处理程序，并提供专用中断栈、
  锁定代码与数据（`0306h`）；商业链保留现有 `_dos_setvect`。
- **F2b**（保守）：`EXTENDER=dos32a` 默认 `NAIZ_BGM_IRQ=0`，只跑协作泵；
  商业链保持 ISR。代价是长解码期间 BGM 略滞后，`frame_decode_pump` 已有缓解。
- 选择标准：F2a 通过 20 连跑且 BGM 不退化则优先；否则退 F2b。

### F3（开源链）ISR 最小化

handler 只做：读状态端口判断归属 → 计数器 +1 → 清 Timer-B → EOI。
时钟推进改为"主线程读计数器"，handler 不再调用任何 C 函数，也不使用栈局部。
这样即使进入上下文仍有偏差，被写的也只有全局计数器。

### F4（可选，调试期保留）canary 常驻

`MAG_DECODE_GUARD` 编译开关（默认在 `NAIZ_DEBUG>=2` 打开），失败时打印 canary 位图；
发布版关闭，避免额外日志。

### S1 F1 + canary

第一版的 F1 把 canary 结构做成**文件级静态对象**（`static MagBrGuard g_br_guard`）。
结果：开源链的 `engine32a.exe` **启动即崩**，屏幕显示：

```
DOS/32A fatal (4005): unrecognized fixup data in application exec "A:\ENGINE.EXE"
```

对照实验（同一 `demo-a2`、同一 10MB 基座）：

| 变体 | EXE 大小 | 结果 |
|---|---|---|
| HEAD（无 F1） | 219,888 | 正常进入 Naiz Settings |
| F1 静态对象 | 220,704 | **fatal 4005** |
| F1 局部对象（临时对照） | — | 正常进入菜单 |
| F1 堆对象（当前方案） | 220,704 | 正常进入菜单 |

结论：**DOS/32A 不能接受这次新增的文件级静态数据对象**（同一份代码、同一编译参数，
仅把对象从静态改成堆分配即恢复）。这是打包链本身的约束，必须写进实现：
守卫上下文一律用 `malloc`（静态只保留一个零初始化的指针，不产生新的 fixup）。

> 这个发现同时解释了为什么"商业链没事"：DOS4GW 的加载器接受这种 fixup 表，
> DOS/32A 的子集解析器不接受。凡是新增静态数据对象的改动，都要在两条链上各启动一次。

## 七、风险与回滚

| 风险 | 缓解 |
|---|---|
| F1 改变对象生命周期，导致 `mag_decode` 不可重入 | 引擎单线程解码；文件级静态上下文加注释与断言；`mag_decode_into` 单独评估 |
| F2a 的 PM 安装方式在 DOS/4GW 下反而变差 | 按 extender 分派，商业链不动 |
| 关闭 ISR 导致 BGM 在长解码时滞后 | 仅在 32A 且 F2a 失败时启用；`frame_decode_pump` 继续泵 |
| 观测代码进入发布版 | `MAG_DECODE_GUARD` 默认随 `NAIZ_DEBUG` 关闭 |
| 误把 P6（编译器 UB）当成 extender 问题 | S1 后若 canary 全 0 且仍失败，转 P6 单独排查 |

回滚：F1/F3 都是小范围改动（`core/lib/mag.c`、`core/plat/hal_irq.c`），
保留 `NAIZ_BGM_IRQ` 运行时开关即可退回协作泵，不需要回退二进制。
