## 一、问题与一句话结论

**用户问**：参考项目（PMD / ADV98 / 98fmplayer）能让 PC-98 的 BGM「不颤」，为什么 naiz 不直接采用它们那套机制？

**答案**：必须把「**机制**」与「**现成实现**」分开——这是两件事。

- **机制层（时序模型：YM2608 Timer-B 硬件溢出 → IRQ → 推进一拍，与主循环解耦）**：**该用，而且早在计划里**——`devdoc 134` 方案 C 就是复刻它。
- **实现层（`PMD86.COM` 这类挂在 INT 60h 的**实模式 TSR**）**：**搬不进来**，有四道硬墙（§三）。

参考项目能「直接用」这套机制，是因为它们**本来就跑在实模式 DOS、并且愿意把整块 OPNA 交给常驻驱动**；naiz 这两条前提都不成立，所以只能在**自研 FM 后端 + 32-bit 保护模式**里**重实现**这层机制，而不是「导入」。

> 一句话：**不是绕过机制，是不能导入实现。**

## 二、「参考的机制」是两层（机制 vs 实现）

| 层 | 内容 | naiz 的态度 | 出处 |
|---|---|---|---|
| **机制**（时序模型） | YM2608 **Timer-B 溢出 → PC-98 IRQ3 → ISR 推进音符一拍**；游戏主循环只「播/停/查」，与节拍解耦 | ✅ **该用** = 方案 C（`134`） | `F05 §2`、`144 §3`、`145 §3.1` |
| **实现**（常驻驱动） | `PMD.COM`/`PMD86.COM` 挂 **INT 60h** 的**实模式 TSR**；游戏把曲子读进其缓冲、发 `AH=xx` 命令 | ❌ **不能导入**（§三） | `F05 §1`、`145 §3.1` |

`145 §3.1` 实证：PMD 是「挂在 INT 60h 的常驻 TSR，签名位于入口偏移 +2」；`F05 §2` 给出时序模型 `主循环（任意阻塞都不影响） / YM2608 Timer-B 溢出 → IRQ3 → PMD ISR → 序列前进一拍`。**naiz 恰恰相反**（`146 §三`）：自研 `fmopn` 直写、无外部常驻、无中断 ⇒ 节拍由**主循环协作轮询**决定（`core/engine/audio.c` `audio_tick()` 由 `core/engine/frame.c` `engine_frame_pump()` 逐帧调用）。

**关键分辨**：「参考的机制」= 上表的**第一行**（可复刻）；人们说「直接用 PMD」通常指**第二行**（不可导入）。本文件回答的是为什么第二行不行、第一行为什么也只能**自建**。

## 三、四道硬墙：为什么不能直接搬 PMD

### 3.1 保护模式 ↔ 实模式边界（致命）

naiz 引擎运行在 **32-bit 保护模式**（DOS/4GW 首选，`AGENTS §四`）。PMD 是**实模式 TSR**。从保护模式调 INT 60h 需要走 DPMI 的**模拟实模式中断**（`INT 31h AX=0301h` + 实模式寄存器结构），这正撞在 `docs/B91 §3` 的「32-bit 保护模式禁止表」上（`F03 §1.2` 理由 2）。**这一条单独就否决了「直接把 PMD 挂上去」**。

### 3.2 OPNA 独占冲突

PMD **自行重置 OPNA 寄存器、跑它自己的中断驱动播放循环**（`F03 §1.2` 理由 2）。而 naiz 已在直接写 OPNA：`core/plat/hal_audio.c:144` 的 `outb(PCM_ID_PORT, 0x01)`（A460 bit0 选 OPNA / bit1=0 不静音）、`core/lib/fmopn.c` 直接写 `0x188/0x18A`、`core/lib/fmseq.c:188-191` 组装 `$B4`。两套都想拥有同一块芯片 ⇒ 冲突。

### 3.3 内容格式对不上

- PMD 吃 **MML / `.M` 编译谱**；naiz 的输入已定为 **MIDI**（`F03 §1.2` 选型表，`devdoc 123`）。
- 转换路径不可依赖：`ConvFMML` 已停止维护、且只转序列（`c52`）；`libopenpmd` 自述 **WIP、只做文件解析、完全不管芯片输出**（`F03 §1.3`）。
- 音色也随之变成 PMD 自己那套，与本仓 `assets/<项目>/fm/*.fmp` 的 32 字节自研格式脱钩。

### 3.4 许可 + 单一入口

- PMD 是 KAJA 的**免费二进制**，源码/再分发许可不明（`ReC98` 靠反编译理解它）；`F03 §5` 另确认「无 CC0 的 OPN 音色库、工具许可 ≠ 数据许可」。`AGENTS §十` 要求不复制不明许可代码。
- `AGENTS §十`「**所有项目统一入口为 `engine.exe`**」；往 HDI 里塞一个魔法二进制 TSR（并由 `AUTOEXEC.BAT` 预加载）违背这条，也把一个「外部常驻组件」变成运行期硬依赖。

### 3.5 附：为什么连 `98fmplayer`（BSD-2）也不直接用

`98fmplayer` 的 `libopna` 虽是 BSD-2，但它是**完整的播放/合成模型 + 自己的输出计时循环**，复用等于**替换现有 `fmseq` 架构**（而非「补一节中断」）；它解决的是「怎么解析/怎么渲染」，不解决「怎么在保护模式里拿到稳定节拍」。收益不成比例。

> `F03 §1.3` 的结论同样成立：PMD 值得借鉴的**只有 MML 这套记谱法**（纯文本、diffable），**不是它的代码**。

## 四、那为什么「机制」现在还没用上？

因为**机制的那道实现难题恰好在保护模式侧**，且本环境无法验证：

- 需要从零建：OPNA Timer-B 编程（`$24–$27` 写入 / `$29` 使能 IRQ）、**DOS/4GW DPMI 中断挂钩**（`_go32_dpmi_set_protected_mode_interrupt_vector` + CWSDPR0 + `_go32_dpmi_lock_code/data` 锁定内存）、**双 8259 级联 EOI**、链到原 ISR，ISR 内推进 `fmseq`（`134 §3`、`146 §五 P1`）。
- 现状：`core/plat/` **无任何 DPMI ISR / `cli`/`sti`/EOI 基础设施**——`core/plat/pc98.h:191-207` 只**定义了** `PIC_EOI` / `IRQ_*` 常量，**零使用**。
- 风险：本环境（NP2kai）**无法验证中断投递与级联 ACK**，写错 = **静默死机**（`AGENTS §八`）。故 `134` 把它**单独立项**，先做 **步骤 1 = 只读「中断投递探针」**（默认关、只计数 + 清标志 + 级联 EOI + 串口打印），**探针通过才值得做步骤 2（音泵接管）**。
- `134 §2` 三个**动手前硬阻塞的未确认项**：NP2kai 是否/以何频率投递 OPNA Timer IRQ（`F04:141`）、DOS/4GW 下 IRQ 向量映射（`G08:80`）、`$29` 默认位行为（`F04:173`）。

**结论**：机制该用；用它的那截电路（DPMI ISR + PIC + 锁内存）必须在保护模式里**自己焊**，不能从实模式 TSR 里「拔出来插上」。

## 五、收敛：BGM「颤 / 电流声」是三条独立的轴

把 `141`/`142`/`143`/`145`/`146` 的结论收敛到一张表。**务必分开**，因为它们互相独立、修法不同：

| 轴 | 症状 | 范围 | 性质 | 状态 | 出处 |
|---|---|---|---|---|---|
| **A｜时基** | 节拍抖动 / 音符起音不匀 / 快速句「塌成簇」 | **四曲皆有**（系统性） | **时域**伪影；软时钟 × 帧泵的**结构性天花板** | 根因机制已定性（本文件 §二/§四）；**判别待运行期取证** | `146 §三`、`134`、`145` |
| **B｜`bell.fmp` voicing** | 「电流声」（高音段） | **仅 003/004**（`icy_garden`） | **频谱**伪影；载波 `op2 mul=8` 过亮 | **根因已确认**，待 voicing 轮修 | `141 §二/§三`、`142 §三`、`143 §四` |
| **C｜LFO** | 轻颤音（可能加重 A 的听感） | 各带 `pms>0` 的音色 | 音色设计取舍 | 参数已知；默认差异见下 | `135`、`F05 §1` |

### 5.1 轴 A（时基）= 用户当前症状的最可信候选

- **机制**：`audio_tick()`（`core/engine/audio.c:534`）每次以 `cur = hal_wallclock_smooth_ms() - wall0`（`:558`）取播放位置，再让 `fmseq_pump()`（`:561`）发 `tick_ms <= cur` 的事件；而 `audio_tick` 由 `engine_frame_pump()`（`core/engine/frame.c:12`）**逐帧**驱动，`engine_frame_pump` 首行是**阻塞**的 `vblank_wait()`（`frame.c:14`）。
- **后果**：音符起音被**量化到一帧**；同一帧内到期的多个事件**同帧齐发**（`fmseq_pump` 的 `while (… tick_ms <= now_ms)`，`fmseq.c:508`；`fmseq.c:497` 的 `FMSEQ_PUMP_MAX_PER_CALL=32` 只封上界，正常密度远低于此）⇒ 快速句「塌成簇」。真机 ~60Hz → ~16.7ms 量化；**NP2kai pass 率约 20.5Hz**（`devdoc 131:122`、`G09:29`，`hal_pc98.c:154` 注释亦记）→ **~48.8ms 量化**。
- **`vclock` 只是补偿**：`core/lib/vclock.{c,h}` 用 1s 窗测速 + `target` 以 IIR 跟 + `step` 以 slew 追 + 窗闭合后 ±25% 钳制（`vclock.h:76/84/115-116`）；`139` 又加尖峰钳制。它们让**速率**更稳，但**无法把 tick 分辨率变得比一帧更细**——这是结构性的（`146 §三.1/§三.2`）。

> ⚠ **与 `142`/`143` 的关系（本文的重心调整）**：`142 §四`/`143 §五` 面对「001/002 录音谱干净，却称四曲都响」的矛盾，把系统性成分**首列**为「宿主 / NP2kai 输出层」。本文指出一条**被它列为低优先**的候选——`139` 节拍——**实为更可信**：因为轴 A 是**时域**伪影，**频谱 oracle（>5kHz 占比 / 质心）看不见它**，「录音干净」与「耳朵听到抖」**不矛盾**。**这是对 `142`/`143` 候选排序的重心调整，不是推翻**——`142`/`143` 均未证明宿主层成因，本文亦未证明时基成因（见 §六 判别法）。宿主层候选仍有效，只是应与时基**并列取证**而非默认领先。

### 5.2 轴 B（bell voicing）= 已确认、可快修的独立缺陷

`bell.fmp` 的 `alg=4` A 对为 `op1(mul=2,tl=14) → op2(mul=8,tl=14)`（`op2` 是**载波**）：载波倍频 **8×**，再由极响的调制器展成 `4f,6f,8f,…` 密频簇 ⇒ 频谱重心远高于 `targets.toml [bell] centroid_hz=[1500,5000]`（`143 §六` 已订正 `142` 误引的 `[900,3500]`，后者实为 `[piano]`）。实机录音 003/004 的 `>5kHz` 占比 **44.4% / 46.5%**，而 001/002 仅 **0.11%**（`142 §六` 实测）。**修法**（留待 voicing 轮）：`op2 mul 8→1`、把「8」移到调制器 `op1`（`143 §四.3`）。

### 5.3 轴 C（LFO）= 默认值差异，次要但值得记录

- **参考**：`98fmplayer` 的 `pmd_reset_opna` 复位时写 **`$22 = 0x00`（关 LFO）**，按曲再开启（`145 §3`）。
- **naiz**：`hal_fm_init()` 全局写 **`$22 = 0x08 | FM_LFO_RATE(=2)`**（`core/plat/hal_audio.c:244`，`FM_LFO_RATE` 定义于 `:228`），即 LFO **常开**、约 6.6Hz；仅对 `$B4` 的 `AMS/PMS>0` 通道生效（`fmseq.c:188-191`）。`strings pms=3`、`reeds/ethnic/synfx pms=3` 等会持续颤音（`142 §四` 候选 2）。
- **判定**：`flute pms=1` 只产生轻颤音，**理论上不足以称「电流声」**；但若用户所指「颤音」偏向 VCO 式音高颤动，则轴 C 会与轴 A 叠加。**是否算错误取决于目标音色方向，需用户拍板**。

## 六、判别法（运行期取证，供后续执行）

在动 `134`（轴 A）之前，先用两法把「颤」钉到轴上：

1. **`[VC]` trace 直读**（最低成本）：`VCLOCK_TRACE_ENABLED` 默认开的 `[VC] v= step= tgt= cal=` 行（`core/plat/hal_pc98.c` 的 `hal_wallclock_smooth_advance()`）——`step/16` 即 ms/pass；若稳态 `tgt` **平滑漂移**（而非尖峰），配合 §5.1 的帧量化即坐实轴 A。
2. **录 001（纯 flute）量 IOI 抖动**：001 已在两套 oracle 与实机录音中**频谱干净**（`142 §六`）；若其**音符起始间隔（IOI）**抖动 ≈ 帧周期且成簇 ⇒ **时域**坐实、轴 A 成立、轴 B 不适用于 001。录音链路（SDL3 `disk` 驱动 + RMS preflight）见 `142 §六.1`。

**若二者均指向时基** ⇒ 轴 A 为「四曲都颤」的主因，唯 `134`（P1）根治；**若仅 003/004 显著** ⇒ 轴 B 优先（voicing 轮快修）。**在执行前应请用户明确：实测平台（NP2kai / 真机）与主要症状曲目。**

## 七、结论与遗留

**结论**：

1. **「参考的机制」应分两层**：时序模型（Timer-B IRQ 定节拍）**该用**；PMD 常驻驱动**不能导入**（四道硬墙，§三）。
2. **「不直接用」不等于「绕过机制」**：naiz 的等价位是 `134` 方案 C（保护模式自建 DPMI ISR），单独立项 + 只读探针先行。
3. **BGM 残余问题收敛为三轴**（§五）：A 时基（系统性、时域）/ B `bell.fmp` voicing（仅 003/004、频谱）/ C LFO（默认值差异）。
4. **对 `142`/`143` 的重心调整**：其「宿主层优先」的排序应改为与「时基」**并列取证**——因时域伪影对频谱 oracle 不可见（§5.1 注）。

**遗留**：

- **轴 A 判别未执行**（§六 两法，需用户实机）。
- **`134` 未启动**（步骤 1 探针待用户拍板）。
- **轴 B 未修**（voicing 轮：`bell.fmp op2 mul 8→1`）。
- **轴 C 待用户定音色方向**（是否照 PMD 默认关 LFO、或降低 PMS 深度）。
- **`142`/`143` 是否走 §十四正式 ERRATA 订正**（把「宿主层优先」改成「时基/宿主并列」）——待用户决定；本文暂以 §5.1 注承载重心调整，未改动 `142`/`143` 正文。
- `targets.toml` 全 15 族仍 `calibrated=false`（`143 §六`），轴 B 修好后应逐族置 `true`。
