# 116 — 输入边界收口与阻塞语义陷阱修正

> **状态**：完结（**根因判定已被 `0.3.009` 推翻，见下方 errata**）
> **日期**：2026-09-29
> **起因**：`projects/demo-a2/scene/nbook004.nb` 中 `cg(){cg01}` 之后的第一句对白「一闪而过」
> **关联版本**：`0.3.008`（前序 `0.3.007` 为 CG 画廊 chrome 槽修复）

> ## ⚠ ERRATA（`0.3.009` 追加，正文以下部分按存档规则原样保留）
>
> **本文档「症状与证据」节所记的根因判定是错误的**，请勿据其排查同类问题。
>
> - **被推翻的结论**：点击 FIFO 在 `cmd_cg` 整屏 blit 期间堆积，故无输入自动翻页。实为 `mouse_update()` 纯轮询、无 IRQ，一次完整的「按下+释放」若整体落在两次轮询之间就采不到，**点击根本无从堆积**。原始证据 `logs/serial_demo-a2_trace.log` 在 CG 之后先有 **37 次 `b=0` 轮询**，随后才是两次真实点击的 `b=1`。
> - **真实根因**：`core/engine/nb_dialog.c` `dialog_show()` 对「能装进一页的整句」在完整绘制之后**重复 arm 打字机**，`dialog_render_reveal()` 用空前缀覆盖整页再重打；首击是否被吞取决于点击是否落在打字机进行中，故症状随点击时机而变。
> - **本文档的变更仍然有效**，但应重新理解为**重构与预防性加固**，而非该症状的修复：① `input_boundary.{h,c}` 收口；② 10 处入口统一（菜单类补 flush 属卫生性加固）；③ `anim_stop_internal()` 幽灵唤醒门控（**独立缺陷**，其自身的「无输入自行前进」机制成立）；④ 阻塞元数据死标志标注；⑤ 文档补充。
> - **正确记录见**：`devdocs/117-单页对白重复arm打字机根修与输入边界收口订正.md`、`CHANGELOG.md` 的 `c40`。

## 一、症状与证据

`nbook004.nb:9-10`：

```
cg(){cg01}
neon(){Hey,you really have a great figure.}
```

现象：CG 出现后的首句对白**无任何用户输入**却自动翻页（用户自述「就打字显示，然后自动跳到下一句」）。

串口追踪 `logs/serial_demo-a2_trace.log`（`NAIZ_DEBUG=ON` 为 `core/Makefile:21` 默认）给出决定性证据：

```
356264: [MAIN] Entering input waiting        <- CG 后首句开页
356265: [INPUT] Mouse clicked                <- (1) reveal-jump
356266: [MAIN] Entering input waiting
356267: [INPUT] Mouse clicked                <- (2) 翻页
356268: nb_process: line[10]: fei(){Sorry?}
```

用户只点过一次（推进上一行），第二次点击是 CG 那约 1 秒里进队列的。

## 二、根因

### 2.1 主因（已确诊）：鼠标点击跨脚本边界泄漏

`cmd_cg` 是剧本中途唯一**长耗时非阻塞**显示操作：`display_apply_cg()`
（`core/engine/scene_display.c:35`）依次执行 `image_load`（解 639×400 MAG）、
`layer_dialog_hide()`、`nb_dialog_reset()`、`palette_reset_reserved()`、
`layer_bg_change()`（整屏 blit + 2 次图层快照 + 立绘重绘）。

该过程**不调 `hal_mouse_update()`**，期间产生的点击事件全部堆积在
`mouse_click_fifo`（`core/plat/mouse.c:37`，16 深，满则丢弃 —— 溢出有正确保护）。

而 page-yield 边界的输入等待入口（`core/engine/main.c:147-150`）**只做了键盘 drain**：

| 设备 | 边界清理 API | 是否清累积事件 |
|---|---|---|
| 键盘 | `hal_kbd_drain_advance()` → `kbd_wait_release()` 内含 `kbd_bios_reset()` | **是**（擦 BIOS 环）→ 键盘不复现 |
| 鼠标 | `hal_mouse_drain()` 只清 dx/dy 累加器，**不清 FIFO** | **否** |
| 鼠标 | `hal_mouse_flush()` 清 FIFO，但 `main.c:207` 在**消费之后**才调用 | **否**（救不了已存在的条目） |

结果：积压点击被当作新页输入 —— 第 1 次走 `nb_dialog_reveal_finish()`（`main.c:164`，
整句一次画完，**不翻页**），第 2 次走 `vm_request_process()`（`main.c:166`，翻页）。
整句仅存活一帧 = 一闪而过。

### 2.2 同型站点（审计发现，4 处 + 场景重置）

全部 6 个「输入循环入口」的 drain 覆盖：

| 入口站点 | 键盘 drain | `hal_mouse_flush` | 读鼠标点击 |
|---|---|---|---|
| `core/engine/main.c:150` | 是 | **否**（仅 `:207` 消费后） | 是 `:161` |
| `core/engine/nb_save_dialog.c:123` | 是 | **否（零次调用）** | 是 `:175` |
| `core/engine/nb_saveload.c:260` | 是 | **否（零次调用）** | 是 `:364` |
| `core/engine/nb_setting.c:252` | 是 | **否（零次调用）** | 是 `:297` |
| `core/engine/nb_special.c:129` | 是 | **否（零次调用）** | 是 `:183` |
| `core/engine/layer.c:44-45` | 是 + ignore_frames | **否** | — |

后 4 个文件 `hal_mouse_flush` 出现次数均为 **0**，却都读 `hal_mouse_was_clicked()`。
症状形态：菜单刚打开即被陈旧点击命中，选中错项或菜单秒关。

### 2.3 键盘侧次级路径

`kbd_wait_release()`（`core/plat/keyboard.c`）实际语义是「擦 BIOS 环 + 约 50ms 延时后
即返回」，**不真正等待物理释放**（reset→delay→reset→检查时环必为空，条件恒真）。
故**按住**推进键时，擦除后自动重复的 make 码会被下一次 `hal_kbd_update()` 收走 →
同类泄漏。`hal_kbd_set_ignore_frames(2)` 全仓库仅 `layer.c:45` 用过，page-yield 边界缺失。
概率低于鼠标（追踪中仅出现点击），但同族，故一并纳入收口。

## 三、已排除的假设（避免走弯路）

| 机制 | 排除依据 |
|---|---|
| 打字机时钟跨 CG 累积 | `nb_dialog_reset()`（`nb_dialog.c:281-294`）清 `reveal_armed`；`nb_dialog_reveal_tick()` 首 tick 仅重置基线（`:235-240`） |
| 键盘输入泄漏 | `kbd_bios_reset()` 擦 BIOS 环（`kbd_drain_advance` 路径内） |
| `vm_delay` 门控主循环 | **误判已撤回**：`cmd_delay` 调 `vm_set_delay()`（`nb_commands.c:358`），`delay(1.5)` 在 `logo.nb`/`op.nb` 在用；`vm_delay_active()` 门控输入等待正是 delay 语义（延迟期间不接受翻页、到点自动继续），**行为正确** |
| `anim_stop` 残留唤醒 | 见 T3：`nb_anim.c:113` 无条件 `vm_request_process()`，今日被 `nb.c:463` 掩盖，**属真实隐患** |
| 分页游标残留 | `nb_dialog_reset()` 完整清零 `page_start`/`page_end`/`reveal_end` |
| 同一 pass 二次派发 | `nb.c:463` 的 `nb_dialog_pending()` 已正确暂停 |
| 鼠标 FIFO 溢出 | `mouse.c:369` 满则丢弃，边界有正确保护 |

## 四、相邻陷阱（诊断结论与处置）

### 4.1 B 项 —— `CMD_BLOCKING` / `CMD_NEEDS_INPUT` 是死标志

`nb_commands.c:372-373` 定义、约 20 个表项标注，但**全仓库无读取方**：
`nb_commands_dispatch()`（`nb_commands.c:416-428`）只调 handler，元数据整体被忽略。
唯一被强制的是 `CMD_TOUCHES_DISPLAY`（且仅由 `tools/tests/test_cmd_meta.py` 兜底）。
实际暂停**唯一**依赖 `nb.c:463` 的 `nb_dialog_pending()`。

危险点：`test_cmd_meta.py:42` 把这两个标志列入「合法标志集」，使命令表**看起来被测试
覆盖**，实际语义零强制。新增阻塞命令若漏写自暂停，脚本会在单个 pass 内跑完剩余全部行
（对白场景 = 一次性渲染完直接跳到场景末尾）。

**处置（T2）**：仅在 `nb_commands.c:372` 加注释声明「仅作文档用，引擎不读，阻塞由
handler 自行实现」。删除标志需动约 20 行表项 + 改测试标志集，性价比不划算，不做。

### 4.2 D 项 —— `anim_stop_internal()` 幽灵唤醒（真实隐患，本轮修复）

`core/engine/nb_anim.c:113` 尾部**无条件** `vm_request_process()`（`a->wait` 早在
`:89` 就被清零，请求不受 wait 约束），由 `display_apply_bg`/`display_apply_cg` 的
`anim_stop()` 触发。

咬人条件（**只需改 .nb 剧本，不需动 C**）：前面有 `anim`/`waitanima` 留下活动动画，
且 `cg`/`bg` 之后紧跟的不是对白行（如 `char(...)`、`delay{...}`、`scene(...)`）——
此时无人清除该唤醒，脚本在无输入下多跑一步。

**症状与 2.1 高度相似（对白自己跳）但根因不同**，若不修，未来复发极易误判为「A 类没修干净」。

**处置（T3）**：按 `nb.c:367` 注释的原设计意图（「anim 结束时重新请求处理」），
把尾部请求改为**仅在停止前处于 waitanima 持有态时**发出；普通 `anim` 停止不再留幽灵唤醒。

## 六、风险与边界

- **行为变更面**：入口 flush 只会吃掉「翻完页那一瞬间」本就该归上一页的输入，与既有键盘
  drain 语义一致；人不可能在一帧内点两次，故不会吃掉真实翻页。
- **不改 `vm_delay`**：经核实行为正确，误判已撤回（见 §三）。
- **不改 `CMD_BLOCKING` 语义**：仅加注释，避免触碰命令表与测试标志集。
- **鼠标点击读取站点全覆盖**：`tools/tests/` 对 drain/flush **零覆盖**，本轮不新增测试
  （无法单测硬件缓冲），依靠串口追踪验收。

## 八、一处误判纠正（留痕）

排查 §2.3 键盘侧时，曾 grep 符号 `vm_delay_set` 未命中，据此判定「delay 路径是死代码、`vm_delay_active()` 门控输入等待是潜伏陷阱」。**该结论错误**：真实符号是 **`vm_set_delay()`**（`vm.c:72`，由 `cmd_delay` 于 `nb_commands.c:358` 调用），且 `delay(1.5)` 在 `projects/demo-a2/scene/logo.nb:3,5` 与 `op.nb:3` 正在使用。`vm_delay_active()` 门控输入等待**正是 delay 的既定语义**（延迟期间不接受翻页输入、到点自动继续），行为正确，**本轮未作任何改动**。

教训：判定「零调用点」前必须确认符号名本身存在（`grep` 无命中既可能是无调用，也可能是拼错），此点已同步至本轮排除结论（§三）与 CHANGELOG `c39`。
