## 一、症状

用户实机复报：FM BGM 播放**全程**有「类似喇叭振动的电流声（buzz）」，并称**四个场景都有**。原始报告（0.3.035，早于 `138`）**同时**提到「音调似乎偏低」；其中**「偏低」已随 `138` 的低八度根因修复由用户实机确认解决**（用户澄清：此前已修复、仅未回传/未记录，见 §八），故本轮**仅剩 buzz 一项未收敛**。这与 `137`/`137b` 的原始报告同源，`137b` 的「提高 flute 调制器 `tl`」最小改动对 buzz **未能消除**。

本轮任务：判定 buzz 是否为 **FM 仿真不当** 所致，并给出可操作的诊断。

## 二、判定过程：先把「不是 FM 仿真」的结论钉死

buzz 的候选根因里，「仿真把寄存器语义解错了」是最需要优先排除的（错了则一切音色/音高分析作废）。三方交叉核对：

### 2.1 算子↔寄存器槽映射：引擎 = ymfm = fmgen

- 引擎侧：`core/lib/fmopn.c:12-14`

  ```c
  /* Register slot for each algorithm operator index (op1->0x30, op2->0x38,
   * op3->0x34, op4->0x3C). */
  const uint8_t fmopn_op_slot[FMOPN_OPS_PER_VOICE] = { 0, 2, 1, 3 };
  ```

- fmgen 侧：`/home/edo/NP2kai/sound/fmgen/fmgen_opna.cpp:53` 的 `slottable[4] = {0,2,1,3}`。
- ymfm 侧：`operator_map` / `operator_offset` 同序（见 `136` §十三）。

⇒ 三方的「算法算子序号 → 硬件寄存器槽」是**同一张表**。`137` 已指出这是 c66 修复后的正确状态，**不得回退 `OP_FILE=[0,1,2,3]`**。

### 2.2 各算法的载波集：直接读 fmgen 的合成 switch

`/home/edo/NP2kai/sound/fmgen/fmgen_fmgen.cpp:925-980` 的 `Channel4::Calc()` 逐算法给出调制连线，据此得到「引擎 `op=N` 标签」下的载波集（`op1..op4`）：

| alg | fmgen `Calc()` 连线（内部槽） | 引擎标签下的载波 |
|---|---|---|
| 0 | `op0→op1→op2→op3` | op4 |
| 1 | `(op0+op1)→op2→op3` | op4 |
| 2 | `op1→op2`；`(op0+op2)→op3` | op4, op1 |
| 3 | `op0→op1`；`(op1+op2)→op3` | op4 |
| **4** | `op0→op1`；`op2→op3`（`fmgen_fmgen.cpp:954-958`） | **op2, op4** |
| 5 | `(op0)→op1,op2,op3` | op2, op3, op4 |
| 6 | `op0→op1`；op2,op3 独立 | op2, op3, op4 |
| 7 | 四个并行相加 | op1, op2, op3, op4 |

（内部槽 `op[0..3]` 经 `slottable` 对应 0x30/0x38/0x34/0x3C，再由 `fmopn_op_slot` 折回引擎 `op1..op4`。）

### 2.3 `$B4`（pan/AMS/PMS）与 `$22`（LFO 使能）组装正确

- `core/lib/fmseq.c:186-195`：逐音写 `$B0`=`fb_alg`、`$B4`=`pan|ams<<4|pms`、`$A4`/`$A0`=`block/fnum`。
- `core/lib/fmopn.c:193-205`：`pan`=bits7-6、`ams`=bits5-4、`pms`=bits2-0，与 OPNA 手册一致。
- `core/plat/hal_audio.c:252-255`：`hal_fm_init()` 写 `$22 = 0x08 | FM_LFO_RATE(=2)`，即 bit3 使能 + LFRQ=2。

⇒ 寄存器语义层**无错**。

### 2.4 排除：SSG / 无人机音

- **SSG 仅用于打击乐**：`core/lib/fmseq.c:26-28,282+`，`percussion_class()` 只把 GM 鼓键分到 SSG0/1/2。两首 BGM（001/002 与 003/004）**都无鼓**，故 SSG 不发声（`ssg_write_mixer()` 把 mixer 置 `0x3F` 全关）。
- **不是未关的持续音**：`fmseq_stop()`（`fmseq.c:516-535`）对每个 active FM 声道写 `$28` keyoff（keymask=0）并静音 SSG；`hal_fm_shutdown()`（`hal_audio.c:268+`）再对全部 6 个 FM 声道 `$28` keyoff。场景切换经 `audio_stop_all()`（`audio.c:574+`）调用二者。

⇒ 「有持续电流声」不是「音符没被关掉」造成的。

**本节的结论：buzz 不是 FM 仿真的寄存器语义错误。**

## 三、已确认的客观异常：`bell.fmp` 载波倍频过亮

尽管「不是仿真错误」，音色数据本身可以**客观过亮**。逐一列出 15 族的载波 `mul`（脚本从 `.fmp` 文本解析）：

| 族 | alg | 载波（`op:mul,tl`） | 备注 |
|---|---|---|---|
| **bell** | 4 | **op2: mul=8, tl=14**；op4: mul=1, tl=22 | **op2 mul=8 = 音高 ×8（三倍频程上方），且 tl=14 极响** |
| flute | 4 | op2: mul=1, tl=2；op4 静音(tl=127) | 正常 |
| strings | 7 | op1:1 / op2:2 / op3:1 / op4:3 | 加法「拉杆」 |
| organ | 7 | op1:1 / op2:2 / op3:1 / op4:4 | 加法「拉杆」 |
| brass | 7 | op1:1 / op2:5 / op3:3 / op4:1（tl≥36） | tl 弱 |
| sfx | 7 | mul 2/9/5/1 | 刻意怪异 |
| synfx | 7 | mul 1/5/7/1 | 刻意怪异 |
| piano | 6 | op2:4 / op3:1 / op4:2 | 中等 |
| perc | 6 | op2:3 / op3:1 / op4:2 | 中等 |
| synlead | 7 | mul 1/4/2/1 | 中等 |
| 其余 | — | 载波 mul ∈ {1,2} | 正常 |

`bell` 是**唯一的极端离群值**：其 `alg4` 的 A 对为

```
op1(dt=0 mul=2  tl=14)  ->  op2(dt=0 mul=8  tl=14)   [载波]
op3(dt=1 mul=5  tl=16)  ->  op4(dt=0 mul=1  tl=22)   [载波]
```

载波 op2 的 `mul=8` 使这一对输出中心落在 **8×音高**，再由极响的 `mul=2` 调制器（`tl=14` ≈ −10.5 dB，调制指数很高）展成 `8f±2nf = 4f,6f,8f,10f,12f…` 的密频簇；而低基频（1f）只由 B 对（op4，`tl=22`）提供。结果：**频谱重心远高于设计值**。

**量化佐证**（`/tmp/opencode/fm/` 既有产物）：

- `assets/demo-a2/fm/targets.toml` 的 `[bell] centroid_hz = [900, 3500]`（P1b 设计带）。
- fmgen 单音渲染 `bell_lfo.wav`：谱峰集中在 880/1320/2200/2640 Hz（即 f=220 时的 4f/6f/10f/12f），质心 1982 Hz —— **且这还是「低一个八度」的渲染**（见 §五），真实八度下约 ×2。
- ymfm 歌曲渲染 `icygarden_nolfo_trim.wav`（003/004，bell×2+strings）：整体质心 **6304 Hz**，`>5kHz` 能量占比在**高音段**可达 **33–52%**（远超 bell 设计带上限 3500）。

⇒ `bell.fmp` 的 `op2 mul=8` 载波是 **003/004 高音段可闻「电流声」的可信根因**，属 **voicing 缺陷**（把高倍频放在了「载波」而非「调制器」上），**不是仿真 bug**。

> 注：该渲染的开头高音段贡献了大部分 `>5kHz` 占比，中低音段回落到 <0.2%；故更准确的表述是「**bell 在高音区过亮**」，而非「全程恒定噪声」。

## 四、未收敛的系统性部分：为何「四个场景都有」

若 buzz 独属 bell（003/004），则 001/002（`melody_town`，**纯 flute 独奏**）不应 buzz。但**两套互相独立的 oracle 都渲染 flute 干净**：

| 素材 | oracle | 质心 | `>5kHz` | 判定 |
|---|---|---|---|---|
| `melodytown`（flute，001/002） | ymfm（`song_render2.py`→`fm_render`→fmbench） | 1051 Hz | 0.10% | 干净 |
| flute 单音（fmgen） | fmgen（`fmgen_render`） | 131–221 Hz | 0.00% | 干净 |
| `icygarden`（bell，003/004） | ymfm | 6304 Hz | 高音段 33–52% | 过亮 |
| bell 单音（fmgen） | fmgen | 1982 Hz（低八度） | 0.31% | 过亮 |

**关键矛盾**：flute 在**两套独立仿真**里都用引擎自身的音色数据渲染，均干净 ⇒ **001/002 的 buzz 不在音色数据里**。既然「四场景都有」，则系统性成分必然在音色数据**之外**。

据此列出剩余候选（按可能性排序）：

1. **宿主 / NP2kai 输出层**：bell 在真实八度下高音段有 8–15 kHz 的强分量，44.1 kHz 输出 + 声卡重采样可能把其折返为可闻噪声；NP2kai 配置 `SNDboard=4`、`DAVOLUME=128`、`USEFMGEN=true` 也可能影响听感（需实机 A/B）。
2. **LFO 的实际听感**：引擎全局使能 `$22`（LFRQ=2≈6.6 Hz），仅对 `AMS/PMS>0` 的通道生效。flute `pms=1`、`ams=0` 只产生轻颤音，理论上不足以称「电流声」；但离线 oracle 对 `$B4`/`$22` 的复现程度需进一步确认。
3. **`139`（节拍尖峰）的实机状态未知**（**低优先**）：「偏低」已随 `138` 实机确认解决（§八），**低八度不再是候选**；`139` 尚无实机复核，但节拍与 buzz **不同轴**，最多是叠加干扰，优先级最低。

**本节的结论**：无法用离线素材把「四场景皆响」归到一个音色/寄存器缺陷上；它最可能来自**运行期/宿主层**（`138` 已排除，`139` 与 buzz 不同轴），需按 §六 在运行期取证。

## 五、工具缺陷：`fmgen_render` 的刻度是旧的 `18432`

`/tmp/opencode/fm/fmgen_render.cpp:33` 的 `note_ratio()`：

```cpp
double full = freq * 18432.0 / 975.0;   /* 旧刻度 */
```

而引擎（`core/lib/fmopn.c:25-26`）与 `fmbench.cpp` 已在 `138` 改为 `FMOPN_FNUM_SCALE_N = 36864`。故：

- **fmgen 单音渲染低一个八度**：实测 `n69.wav`（A4）→ **219.8 Hz**；`c15974400.wav`（时钟翻倍）→ 440.59 Hz。
- 歌曲渲染走 ymfm（`36864`，刻度正确），故 §三/§四的歌曲结论有效；但**任何基于 `fmgen_render` 单音的音高/频谱对比都必须先修刻度**，否则整体错一个八度。

这是纯工具侧的缺陷，**不影响引擎**，但会误导后续 fmgen 侧的诊断。

## 六、下一步判别法（供后续讨论，不在本轮执行）

要把「系统性 buzz」钉死，需在**运行期**取证，二选一：

1. **录 NP2kai 的真实输出**：对同一场景分别录 WAV，与 `melodytown_nolfo_trim.wav`（ymfm oracle）做同口径频谱对比。若实机 WAV 干净 ⇒ 症状来自 oracle 侧；若实机 buzz 而 oracle 干净 ⇒ 宿主/模拟器差异。
2. **dump 引擎的 FM 寄存器流再回放**：`core/plat/hal_audio.c` 已内建逐写 trace（`FM_TRACE_ENABLED`，`hal_audio.c:232`，编译期开关，判据见 `123` §1.5）。翻转后采集一次实际 `(port,addr,val)` 序列，喂给 fmgen/ymfm 回放——**回放干净 ⇒ 问题在宿主；回放 buzz ⇒ 问题在引擎的寄存器流**。这能把「引擎 vs 宿主」一刀切开。

### 6.1 「录音是静音」的历史与可靠抓取

此前多次「录 NP2kai 却得到**静音**（接近全零）文件」，是阻塞上述判别的直接障碍，必须先把抓取链做对。已查明：

- **历史方法**（devdocs 125–129）：`parec` 抓 PulseAudio **sink 的 `.monitor`** source，**预启动**后台进程，检测到串口 `BGM start` 后录 5s。已知坑：初版抓的是 `default` source（**当时为麦克风而非 `.monitor` ⇒ 全零**）；`parec` 启动时延 30–80 ms 使首音丢失；若窗口落在无 BGM 时段同样得到静音。
- **本机环境实测（2026-10-16）**：`wxnp21kai` 用 **SDL3**（`libSDL3.so.0`，请求格式 `S16 / 2ch / 44100`，`sdl/soundmng.c:1006`）；`SDL_AUDIODRIVER=pulse` **能正常初始化**（ctypes 实测 `init_ok=True driver=pulseaudio`）⇒ **驱动名不是根因**；本机只有一个 sink，其 `.monitor` 即默认 source；**抓取时若同一 sink 上还有其它 PA 客户端（如音乐播放器），会一并录进去**（内容被污染，但不会是静音）。
- **0.3.026 期的「静音」另有隐情**：devdoc `126`/`128` 证实当时**引擎侧本就近乎静音**（`fmseq_finished` 判定过早 → 首音后全体 keyoff），故部分「静音录音」是**源真的静音**、而非抓取缺陷——该项已随后续修复解决。

**推荐抓取法（二选一，均须带 preflight）**：

- **首选 —— SDL3 `disk` 驱动**（已实测可用）：以 `SDL_AUDIODRIVER=disk` + `SDL_AUDIO_DISK_OUTPUT_FILE=<path>` 启动 wxnp21kai，直得 `S16 / 2ch / 44100` 裸流。**不经 PulseAudio、不受其它客户端污染、不依赖 `.monitor`**。代价：抓取期间扬声器**无声**。
- **备选 —— null-sink 监听**：新建 `module-null-sink`，令模拟器输出到它，`parec` 其 `.monitor`（与实际输出解耦、便于实时监听）。
- **preflight（强制，§九.6 消灭静默失败）**：录制后立即算 RMS，**静音即非零退出**，绝不产出「假通过」文件；并断言抓到的确是目标源。另先跑一次「播已知音调 → 抓取 → 断言非静音」的 smoke test，自证链路可用后再录 NP2kai。

配套：`tools/naiz_audio/` 的 `targets.toml` 目前 **全 15 族 `calibrated=false`**，故 bell 的过亮**不被任何测试拦截**；若后续进入 voicing 轮，应逐族量测后置 `true`。

## 七、本轮结论与遗留

**结论**：

1. **不是 FM 仿真 bug**（引擎/fmgen/ymfm 三方算子映射、算法载波集、`$B4`/`$22` 组装均一致且正确）。
2. **已确认**：`bell.fmp` 的 `op2(mul=8, tl=14)` 载波使其频谱重心远超设计带（`targets.toml [bell] centroid [900,3500]`，实测高音段质心 6304 Hz），是 **003/004 高音段 buzz** 的可信根因（voicing 缺陷，留待后续 voicing 轮修复）。
3. **未收敛**：001/002（flute）在两套独立 oracle 中均渲染干净 ⇒ 「四场景皆响」的系统性成分不在音色数据内，最可能是**宿主/模拟器输出层**（或 `139` 节拍，低优先），需按 §六 取证。
4. **工具缺陷**：`/tmp/opencode/fm/fmgen_render.cpp:33` 用旧刻度 `18432`（低一个八度），后续 fmgen 侧诊断须先修。
5. **状态澄清**：原始报告的**「音调偏低」已随 `138` 实机确认解决**（§八），不在本轮遗留。

**遗留（待讨论）**：

- **可靠录音通路**（§六.1）：先建带 preflight 的抓取（首选 SDL3 `disk` 驱动），否则 §六 的鉴别无法执行。
- `139`（节拍尖峰）的**实机复核**（低优先；`138` 已实机确认修复，移出遗留）。
- bell voicing 重做（`op2 mul 8→1`，把「8」移到调制器 `op1`；或提高调制器 `tl` 以收紧边带），目标把质心拉回 `[900,3500]`。
- `fmgen_render` 刻度 `18432→36864`。
- 若 §六 取证实为宿主/模拟器，再单独立项。
- `targets.toml` 逐族 `calibrated=true`（使设计带成为可执行的回归）。
