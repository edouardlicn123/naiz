## 一、音频通路现状（三后端，先分清再谈问题）

引擎启动时**自动检测**后端（`core/engine/audio.c`）：有 MPU-401 → MIDI；无则 → FM（OPNA）；两者都无 → `fail-loud`。

| 用途 | 芯片/通路 | 引擎代码 | 串口成功标记 | 现状 |
|---|---|---|---|---|
| BGM（首选） | MIDI over MPU-401 | `core/lib/midi.c` + `hal_midi_out()` | `AUD MPU OK` | 宿主/NP2kai 无 MPU 时**设计内静音降级**，非 bug |
| BGM（降级） | FM over 86 板 OPNA | `core/lib/fmopn.c` + `core/lib/fmseq.c` + `hal_fm_*()`（`hal_audio.c`，`outb()` 唯一出处） | FM 就绪 + patch 装载行 | **已实现**（S0–S7） |
| SE / 语音 | 86 板 YM3433B PCM | `pcm_play()` + FIFO 泵 | — | 可闻 |

**定性第一步**：BGM 无声先看串口——见 `AUD WARN: no MPU-401` 即已定性（降级到 FM 分支）；见 `AUD` 的 FM 装载告警才需查音色数据。**不要先怀疑脚本/key 登记/AUDIO.DAT**。

## 四、线 2–4：通了之后的三个「绝对音质」问题

### 线 2 — 全音符低一个八度（devdoc 138，0.3.036）

- **根因**：`core/lib/fmopn.c` 的 `FMOPN_FNUM_SCALE_N = 18432` 隐含 `2^block`，**漏了 `2^(block-1)` 折半** ⇒ 引擎把每个 MIDI 音符编低一个 block，芯片只给半频 = 实听「音调偏低」。
- **三证据链交叉确证（非推断）**：YM2608 官方手册公式 `f = (fnum << (block-1)) × 7987200/(144×2^20)`；NP2kai fmgen（= 用户实听通路）逐行核算 + 宿主渲染实测（block4/520→220Hz、block5/520→440Hz）；ymfm `compute_phase_step` 净值恰 `2^(block-1)`。
- **修法**：`18432→36864`（A4 改发 block5/fnum520、C4→block4/fnum618）；新增 `fmopn_ratio_freq(block,fnum)` 作编码逆，bend（`fmopn.c:93`）与 SSG 打击恢复（`fmseq.c:298,394`）改用它，**常量单一事实源**；SSG 音高不变（编解码同步改）。
- **连带订正**：devdoc 136 §十五 曾把该 0.5 判为「ymfm 低八度」并给 oracle 打 `FNUM ×2`，**恰好掩盖引擎 bug**；138 已把 oracle 的 ×2 撤销。教训：**oracle 的职责是忠实再现给定寄存器的输出，不是输出目标音高。**
- **防复发**：`test_fmopn`/`test_fm_seq`/`test_fm_timbre` 锚点更新；`test_devdoc_refs::test_devdoc_136_keeps_its_errata_block`（136 必须留 ERRATA 指 138）。
- **状态**：`实现完成待实机验证`。

### 线 3 — 演奏时快时慢 / 颤动（devdoc 130 → 133 → 139）

这是**三层叠加**的节拍问题，逐层收敛：

1. **130**：虚拟时钟由「平滑」改「变步进」——`step` 每次最多动 `VCLOCK_SLEW_UNITS`，相邻 advance 有界。
2. **133**：治**稳态残留颤**（±5% 整数量化锯齿）→ `VCLOCK_MEAS_SMOOTH=4` IIR；治**起播先快** → **首窗直采**（`calibrated`，不再从 `VCLOCK_INIT_STEP_UNITS=640` 缓升）。
3. **139**：治**残留尖峰**——一个窗若先经历几次 `delta=0` 短停顿、再吃到 `+1000..+6000ms` 成簇大跳，`passes ≥ VCLOCK_MIN_WINDOW_PASSES=2` 仍被采纳，`want` 飙到 `VCLOCK_RATE_MAX_MS`(≈2.5×)，数秒才回落。修法（`core/lib/vclock.c:118-137`）：窗口闭合、IIR 更新**前**把 `want` 钳到 `[target*4/5, target*5/4]`（**±25% 带**，`VCLOCK_MAX_WINDOW_RATIO_NUM/DEN=5/4`）；**首窗（采纳窗）免钳**（整机真实速率本 ≠ 初值 640 时仍一次校准到位）；`RATE_MIN/MAX`(1/100ms) 绝对钳制保留为外层界。

- **兼容性核对**：`test_first_window_is_adopted_not_ramped`、`test_rate_change_converges_without_lurch`、`test_tempo_at_various_pass_rates`、`test_quantised_jitter_is_smoothed`、`test_sustained_rate_change_still_converges` 全过。
- **状态**：`实现完成待实机验证`。**代价**：真实 2.5× 持续变率需 ~15 窗才完全跟随（pass 率实际稳定，可接受）。
- **兜底路线**：若实机 `[VC]` 行（`hal_pc98.c`，每 64 pass）显示 `tgt=` 是**平滑漂移**而非一次性尖峰，则说明偏快另有机制，唯**方案 C（devdoc 134：OPNA Timer / GDC vsync 中断驱动时基）**可根治。134 目前 `计划中`，是**独立线**，与本三线的实机结论绑定。

### 线 4 — buzz（电流声）+ 感知音高偏低（devdoc 135 / 136 / 137 / 137b，未收敛）

- **背景**：`op=` 标签语义修复（CHANGELOG c66，恒等映射 `OP_FILE=[0,1,2,3]`）后，flute 从「静音」恢复，但暴露出「整段播放期间的电流声（buzz）+ 感知音高偏低」。
- **137**：初判为 LFO 深度相关 → 方案 1：`flute.fmp` `pms 2→1`。
- **137b**：**方案 1 无效**（buzz 是整段连续、非颤动问题）→ 定性为**正确 op 映射下稳态 FM 调制指数偏高**；方案 2a：`op1 tl 52→54`（提高调制器衰减、降低调制指数）。
- **绝不回退**：`tools/naiz_audio/fm_patch.py::OP_FILE` 保持 `[0,1,2,3]`；`core/lib/fmopn.c::fmopn_op_slot` 保持 `{0,2,1,3}`（语义 = 算法算子→寄存器槽的硬件事实，引擎零行为改动）。
- **当前 `assets/demo-a2/fm/flute.fmp` 实况**：`pms=1`（方案 1）、`op1 tl=54`（方案 2a）、`op2` 载波软起音 `ar=16 tl=2`、组 B 静音（`op3/op4 tl=127`）。
- **状态**：**未收敛**。方案 2b（`tl 54→56`）、`tl=60`、或微调 `op2 tl` 为后备；这是**欠定的逆问题**，只能靠离线 oracle 逐族调（136 的 P1c），不是一次改对的事。
