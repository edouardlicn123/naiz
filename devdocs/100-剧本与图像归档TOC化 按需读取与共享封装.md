# 100-剧本与图像归档TOC化 按需读取与共享封装

> 版本：0.2.110 之后（bump 至 0.2.111）
> 状态：设计定稿，待实施（Phase 1–5）
> 关联：devdocs/96（对话框图层化）、devdocs/89/90/92/93/94（CG 画廊）、R25（8.3 短名）

## 1. 背景与动机

完整商业级 PC-98 VN（100+ 背景、40+ 立绘、全 CJK 字库）的内存与磁盘部署
存在四类瓶颈，全部由"IMAGE.DAT 整档常驻 + 场景散文件部署"的现状造成：

1. **内存（最大瓶颈）**：`image.c:59` `file_read_all()` 把整张 IMAGE.DAT
   一次性 `malloc+fread` 常驻。8–15 MB 的归档 + CJK 字库 ≤1.25 MB + 解码
   LRU ≤2 MB + 层缓冲 ~1 MB，在 DOS/4GW 约 13–14 MB 平坦堆上**逼近甚至
   超限**。实测峰值可到 15–20 MB。
2. **FAT 根目录条目上限**：场景目前在 HDI 里是逐个 FAT 根目录文件
   （`inject_common.py:155-185` 逐文件注入）。FAT12 根目录约 224 项，
   千级场景直接撞墙。
3. **簇尾碎片**：上千个小 `.nb`（61–824 B）每文件浪费大半个簇，磁盘
   白耗 MB 级。
4. **构建残留**：`deploy_runtime`（build_game.py:279-284）只拷不清理，
   demo 部署树已残留 0 字节 `nbook005-020.nb`/`nopbook.nb`，每次经
   build/make 还会被注入 HDI（现已确认残留注入）。

剧本侧"内存"其实早已按需（`nb_load` 每次只把当前场景读进固定 32 KB
`nb.buf`），因此**剧本归档化不改内存模型，只改字节来源**；IMAGE.DAT 才
需要真正从"整档常驻"改为"TOC 常驻 + 按需读 entry"。

## 2. 现状分析（关键事实）

### 2.1 IMAGE.DAT 归档格式（pack_images.py:304-317 写出）
```
uint32 count  （读端 clamp 8192，image.c:75-79）
count × { char name[12]; uint32 offset; uint32 size }   20 B/项，绝对偏移
顺序拼接的图像数据（无归档层压缩；MAKI02 内部压缩）
```
- 空洞合法：ASSETS.DB id 非连续时空项 size=0。
- `mag_decode`/`mag_read_palette`/`mag_decode_into` **只吃单 entry 连续
  内存**，随机访问整个 blob，无法 fd 直流；但**只需 entry 自身字节**。

### 2.2 引擎读取现状
- `image_init`：整档入内存 + 全档调色板一致性校验（warn-only，image.c:88-136）。
- `image_load`（image.c:145-186）：cache 命中优先；miss → TOC 定位 →
  `mag_decode(g_image_data+off)` → 入 8-slot LRU（LFU）。
- `image_raw_blob`（image.c:193-215）：返回 `g_image_data+off`，借用期
  "直到下次 init/close"；**唯一调用方 `nb_anim.c:333`**（ANI 播放持 `a->blob`
  整个播放期），且总是先 `anim_stop_internal()`（nb_anim.c:319）再取下一个。
- `nb_load`（nb.c:153-199）：`fopen(filename,"r")` → `fgets` 逐行灌入
  `nb.buf[32768]`，超限截断告警 + 清行数；结束后 scene_end/dialog_reset/
  title/type 清空 + `vm_request_scene_change()`。
- 场景名全部由字符串解析（save.c:39、nb_scene.c:50 的 `sscanf("nbook%u.nb")`
  只碰字符串不碰文件），调用方覆盖 logo/op/mainmenu/loadscen/cgview/
  startset/nbook{id}。

### 2.3 部署现状
- build_game.py:279-284 将 `scene/*.nb` 逐个拷到 `games/<game>/` 根目录；
- inject 再把整个部署树逐文件写进 HDI；`IMAGE.DAT` 是唯一归档。

## 3. 目标

1. IMAGE.DAT 从"整档常驻"改为"TOC 常驻 + 按需读 entry"，全规模项目
   峰值内存 ~5 MB，**不受归档体积影响**。
2. 场景脚本打包进 **SCENE.DAT**（同一 TOC 布局），解决 FAT 根目录上限、
   簇尾碎片、构建残留；内存不变（仍是 1×32 KB）。
3. 抽取**跨模块共享封装**，一次落地两处受益：
   - C：`core/lib/farchive.{c,h}`（TOC 读取总管）
   - Python：`tools/naiz_lib/toc_archive.py::make_toc_archive()`（TOC 写包）
4. 公共 API 零变动（`image_load/image_raw_blob/nb_load` 签名不变），
   向后兼容（归档缺失自动回退散文件）。

## 4. 总体设计

### 4.1 统一归档格式（IMAGE.DAT / SCENE.DAT 共用）
```
uint32 count
count × { char name[12]; uint32 offset; uint32 size }
顺序拼接数据
```
- IMAGE.DAT：name 为调试用 8.3 短名（运行期按 id 寻址，image.c:7-9 现状）。
- SCENE.DAT：name 为源名的 8.3 大写规范短名（base8.NB，如 NBOOK001.NB，
  先截断再判互异，见 §7.1），运行期按名寻址（大小写不敏感）。

### 4.2 C 共享库 farchive（新 core/lib/farchive.{c,h}）
```c
typedef struct {
    FILE    *fp;          /* 打开句柄，全程保持 */
    uint8_t *toc;         /* 4 + count*20 常驻 */
    long     file_size;
    int      count;
} FArchive;

int   farchive_open(FArchive *a, const char *path, int max_entries);
void  farchive_close(FArchive *a);
int   farchive_lookup_id(FArchive *a, int id, long *off, long *sz);        /* 0/-1 */
int   farchive_lookup_name(FArchive *a, const char *name,
                           long *off, long *sz, int *out_id);             /* 0/-1，8.3 大小写不敏感 */
uint8_t *farchive_read_alloc(FArchive *a, long off, long size, long *out_len);
long  farchive_read_buf(FArchive *a, long off, long size, void *dst, long dst_cap);
```
- open：fopen rb → 读 count（LE32，`read32_le` 复用 endian.h，clamp
  max_entries + 警告）→ malloc TOC → fseek END 取文件大小；失败路径
  `hal_log` 记录（C14）。
- read_alloc：`off+size <= file_size` 边界校验 → malloc → fseek+fread 单 entry；
  短读即失败返回 NULL。调用方负责 free（瞬时缓冲）。

## 5. image.c 重构（TOC 常驻 + 按需读）

状态替换：
```
g_image_data/g_image_size/g_image_count/g_image_toc_off
    →  static FArchive g_arc;
       static uint8_t *g_blob_buf; static long g_blob_len; static int g_blob_id;
```

1. **image_init**：`farchive_open(path, 8192)`；失败 → hal_log + -1。调色板
   校验循环（原 :88-136）改为逐 entry `farchive_read_alloc` 全量读 →
   `mag_read_palette(buf, size, …)` → `free(buf)`。I/O 总量与现状一致，
   内存瞬时（单 entry ≤ 单片尺寸）。日志文案不变。
2. **image_load** miss：`farchive_lookup_id` → `read_alloc` → `mag_decode`
   → **free raw** → `image_cache_insert`（解码结果仍进 8-slot LRU）。
3. **image_raw_blob**：单槽复用：
   ```c
   if (g_blob_id != id) { buf = read_alloc(...); free(g_blob_buf); 存新; }
   ```
   借用语义收紧为"有效至下一次 image_raw_blob / image_close"。已论证安全
   （唯一借用方 nb_anim 的先停后取次序）。
4. **image_close**：`farchive_close` + free blob 槽 + `image_cache_clear`。
5. 抽内部 helper `img_read_entry(id, &off, &sz)` 消除 image_load 与校验
   循环两处重复的"lookup→read→free"。

## 6. nb.c 接 SCENE.DAT

- `static FArchive g_scene_arc; static int g_scene_arc_open;`
- 新 helper `nb_scene_archive_read(const char *name, char *buf, int cap, int *truncated)`：
  `farchive_lookup_name`（8.3 大小写不敏感）→ `read_buf` 有界拷贝；
  size>cap 置 truncated；返回拷贝长度，未命中返回 -1。
- **nb_init**（nb.c:138 `nb_load("logo.nb")` 之前）：
  `farchive_open("SCENE.DAT",8192)` 成功置标志，失败 `hal_log` 警告继续。
- **nb_load 重构**（单一尾段，不复制业务）：
  ```
  归档命中：拷贝进 nb.buf（NUL 收尾）→ 若 truncated 打 WARN（对齐现状）
            → num_lines = '\n' 计数 + (前缀非空且末字节≠'\n' 时 +1)
              精确等价现行 fgets 路径（nb_parser.c:97 nb_get_line 按 '\n'
              分段执行，末行无换行也计 1 行；否则 nb.c:283 pc≥num_lines
              提前 halt 漏执行末行）
  归档未命中：现行 fopen+fgets 路径原样保留
  共尾：scene_end / nb_dialog_reset / 清 title/type / [LOAD] 日志 / vm_request_scene_change
  ```
- `nb.filename` 仍存原始名（入参原样），`sscanf("nbook%u.nb")`
  字符串解析逻辑零改动。

## 7. 打包侧

### 7.1 build_game.py 新增 pack_scenes(game_dir, proj_dir)
1. 遍历 `scene/*.nb` 排序（对齐现 glob 次序）；
2. TOC name = 源名的 **8.3 规范短名**：base 截 8 字符大写 + `.NB`
   （复用 `to_dos_name` 的 base8/扩展约定，naiz_lib __init__.py:83，
   返回填充字节需再拼成 `BASE.EXT` 字符串）；**先截断再校验短名互异**
   （防基名>8 截断同名，如 `nbook001.nb` 与 `nbook0012.nb` 均截为
   `NBOOK001.NB`——R25 同类防呆）；
3. 校验：count ≤ 8192、单脚本 < NB_BUF_SIZE(32768)、非空；
4. `make_toc_archive` 写 `games/<game>/SCENE.DAT`（增量：内容哈希未变跳过）；
5. **清理 games/ 根目录遗留 `.nb`**（含历史空文件），部署树不再散放场景文件。

### 7.2 deploy_runtime 改动
`:279-284` 的场景逐文件拷贝块 → 改调 `pack_scenes`。其余部署不动
（SCENE.DAT 与 IMAGE.DAT 一样经 inject 进 HDI 根目录）。

## 8. 内存账与性能账

| 项目 | 改前（完整游戏） | 改后 |
|---|---|---|
| IMAGE.DAT 常驻 | 8–15 MB | TOC ≤164 KB（8192 上限） |
| 解码 LRU | ≤2 MB | ≤2 MB（不变） |
| SCENE.DAT | 散文件 0 驻留 | TOC ≤164 KB |
| nb.buf | 1×32 KB | 1×32 KB（不变） |
| ANI raw 单槽 | 指向整档 | ≤ 单个 ANI blob |
| **峰值** | **~15–20 MB** | **~5 MB** |

- 每次 `image_load` miss：一次 `fseek+fread`（60–170 KB）+ 解码；LRU 兜底，
  复访不重读。NP2kai 下无感，实机 SCSI 也为几十 ms 级。
- `nb_load`：归档命中一次有界 `fread`（≤32 KB），零额外分配。

## 9. 兼容性与风险

1. **SCENE.DAT 缺失/损坏** → 引擎回退散文件，向后兼容（旧 HDI 照跑）。
2. **`image_raw_blob` 生命周期收紧**：已确认全库唯一借用方 nb_anim.c:333
   且先停后取；doc 注释同步更新。
3. **文件句柄**：IMAGE.DAT/SCENE.DAT 各保持 1 个 FILE*，DOS 限制内。
4. **`"r"`→`"rb"` 文本语义**：现行 `nb_load` 用文本模式；已实测 demo-a2 全部
   场景源纯 LF（0 CRLF），DOS 文本模式对孤立 LF 不做转换，故归档 `rb`
   原样拷贝与 fgets 文本结果逐字节一致。**若未来源文件引入 CRLF**，
   必须在打包端（TOC 写入前）或读取端归一化 LF——实施时在 pack_scenes
   加 CRLF 检测告警。存档文件名仍是字符串，互不影响。
5. **IMAGE.DAT 格式不变**：`tools.naiz_lib.image_dat.verify_shared_palette_file`
   / makegame、HDI、既有测试不受影响（writer 仅重构、字节一致，pytest 守护）。
6. **C14 日志**：farchive 所有失败路径 `hal_log` 记录。

## 12. 结论

TOC 化把完整游戏的运行时峰值从 ~15–20 MB 压到 ~5 MB，并把上千场景文件
收敛为一条 SCENE.DAT；共享封装（farchive / make_toc_archive）一次落地
两处归档，符合"先借后造、小而专"原则。公共 API 零改动 + 回退路径保证
兼容，任何一步回卷都不伤现状。
