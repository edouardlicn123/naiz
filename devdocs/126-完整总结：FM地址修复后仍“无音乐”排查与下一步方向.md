> 版本：`0.3.026`

## 1. 问题回顾

用户反馈：修复 `fm_op_addr`（`base+4*r`）并做 FMP 微调后，**主观上仍然“没有音乐”的声音**。

实测数据：
- `BGM start 'melody_town' (310 events) (FM)` 正常触发（串口日志）
- 波形抓取成功（提前后台启动 parec + monitor 源）：`precise*.raw`
- 首音瞬态：从 pre-fix ~ -54 dBFS 提升至 ~ -24 dBFS（峰值 2048）——**地址修复已生效（寄存器写到正确算子）**
- 持续段：双声道有能量（R 声道更明显），活动段落 rms ~ 600–1100（约 -29 dBFS），整体 RMS 仍偏低
- FMP SL 分布 2–9（并非此前推断的 14），flute 族小幅 TL 微调（-6）改善声道平衡但主观改善有限，已恢复原值

## 2. 已做的事（总结）

1. **根因 1 修复（代码）**：`core/lib/fmseq.c::fm_op_addr` 由 `3*(r&1)+8*(r>>1)` 改为 `base + 4*r`（符合 OPN/OPNA 布局 `{0,4,8,12}`）。
2. **测试同步**：`tools/tests/test_fm_seq.py` 断言更新，`test_fm_seq.py + test_fmopn.py` **26 passed**。
3. **重编译+HDI**：`make -C core` 干净 → `build demo-a2 && make demo-a2` 更新 `disks/demo-a2.hdi`。
4. **抓取时机解决**：“parec 提前后台启动（monitor 源）+ 标记后立即录制 5s”稳定产出波形，消除“检测后再启动导致首音丢失/空文件”。
5. **波形量化**：瞬态大幅提升（-54→-24 dBFS），证实地址修复生效。信号确实存在。
6. **FMP 分析与微调**：识别 melody_town 用 GM 73→flute（索引8），尝试 TL -6/-10 并复测，-10 过衰减，-6 平衡改善有限，恢复原值。补充 devdoc 125–125d。

## 3. 核心矛盾

**波形上有信号，但主观上“没有音乐”。** 可能的原因：

- **声道/输出路径**：分析显示信号主要在 R 声道。若主机音频平衡偏左、扬声器单侧、或 PulseAudio sink 输出配置导致感知不均，可能听不到清晰旋律。
- **FM 输出增益**：hal_audio.c 目前处于诊断态（曾有 FM_TRACE_ENABLED、0x0F/0x2F 写入、set_volume 固定写入等临时改动）。若临时改动被部分保留（或 A466 音量路径处理）导致 FM 整体衰减，波形 rms 仍偏低。
- **FM 序列时序/loop 行为**：`audio_tick()` 用平滑时钟驱动 `fmseq_pump`，并在 `fmseq_finished()` 时 `fmseq_stop()+rewind`（loop 处理）。若 MIDI 前几小节触发了“finished”判定过早（或时钟平滑导致事件延迟），可能只剩极短脉冲后静音，导致主观上感觉“没放出来”。
- **算法/patch 平衡**：melody_town 的主旋律族（flute）在当前默认 TL 下，载波衰减较大，导致持续段 rms 偏低（-29 dBFS 左右）。虽然 TL -6 改善有限，但可能需要更系统地调节（选取所有真正用到的族，而不是只调 flute）。
- **MIDI 通道/音色选择**：只检查到 program 73？需确认 melody_town 是否有其他 program change（鼓组除外）或是否走 GM 默认导致族错配。
- **模拟器音量设置**：wxNP21kai 的 SNDboard/DAVOLUME、主机 parec monitor 源与实际扬声器音量。波形存在但实际播放时被衰减。
- **hal_fm_detect/hal_fm_init 路径**：诊断期间可能改动了 hal_audio.c（如 A460 bit 设置），需确认 FM 实际开始发声的寄存器序列是否完整。

## 4. 下一步排查方向（规划）

优先级从“最容易验证主观感受”到“最可能改动代码”排序。

### A. 主观直试听（最高优先，零改动）
- 在 wxNP21kai 里直接运行 `disks/demo-a2.hdi`，全程开大音量，左右声道平衡居中。目视/倾听是否能听见旋律。
- 尝试用其他输出设备（耳机）或直接在宿主用 `aplay` 播放刚才的 `precise5.raw`（stereo s16le 44100）确认录音本身是否能听出旋律。
- 若 `aplay` 能隐约听见但模拟器里几乎听不见，重点看模拟器音量/声卡设置（DAVOLUME、混音）。

### B. 还原 hal_audio.c 临时诊断态（极关键）
`core/plat/hal_audio.c` 先前标注“临时诊断态”（FM_TRACE_ENABLED=1、写 0x0F/0x2F、set_volume 固定 0x0F）。这些改动很可能：
- 强制写了测试值导致 FM 音量衰减
- 开启 trace 可能改变某些时序（不太可能）但更可能影响寄存器写入顺序/值

**行动**：对照最近 git 历史（或 devdoc 125 前后的状态），把 hal_audio.c 恢复到“非诊断”正常状态：
- FM_TRACE_ENABLED 设为 0（或按原始值）
- A466 写入恢复为 `(uint8_t)atten`（而不是固定 0x0F/0x2F）
- 移除/还原任何仅用于“SL14.EXE/FMBLAST”测试的临时写入

恢复后重新 `make -C core && build+make demo-a2`，用相同抓取流程对比波形 rms（尤其是持续段）。

### C. 检查 FM 初始配置（A460/A466）
devdoc 123 §8.1 强调：“Init must raise A460 bit0 first or the extended window 0x18C/0x18E never routes (F03 §3.8 fact 1)”。hal_fm_init 是否严格按这个顺序？
另外 A466 是各通路音量（VOL1/VOL2/VOL6 独立）。若诊断时误写成全通路相同固定值，可能导致主音量偏低。

需核对 `core/plat/hal_audio.c::hal_fm_init()`、`hal_fm_set_volume()` 当前实现，与“非诊断”版本是否一致。

### D. 深入分析 MIDI 事件时序（loop/finished 判定）
`audio.c` 在 FM 模式下：
```c
fmseq_pump(g_fm_seq, &g_fm_sink, cur);
if (fmseq_finished(g_fm_seq)) {
  ...
  g_bgm.wall0 = now;
  fmseq_stop(g_fm_seq, &g_fm_sink);  // keyoff all + silence SSG
  // （注意：并未重新调用 fmseq_events 重装载事件）
}
```

这意味着一旦 `fmseq_finished()` 返回真，**事件队列会被清空（stop）但不会重播**。如果平滑时钟（`hal_wallclock_smooth_ms`）在某些帧算出 `cur` 突然超出事件总时长，或者 MIDI 事件表的 tick 计算导致“finished”过早，就会在极短时间后进入“finished”分支并 stop。

但串口日志显示 `BGM start ... (310 events)`，且抓到的波形有一小段能量（证明刚开始时确实泵过事件）。关键是：在进入场景后的前几秒内是否很快触发 finished？

**验证方式**：临时加日志（或复用现有 FM trace 思路）——在 `audio_tick()` 的 `fmseq_finished()` 分支打印 `ring`、`idx`、`count`、`cur` 值，跑一遍串口抓日志，观察 finished 是否在 1–2 秒内被触发多次。

但要避免大幅改动。可先用串口 trace 思路：确认 `hal_audio.c` 现有 trace（若还开着）是否能暴露这点，或者临时加 `hal_logf("FM finished ring=%d idx=%ld/%ld cur=%lu\r\n", ...)`。

### E. 全量跑 pytest 确认无回归（安全网）
虽非直接解“没听到音乐”，但地址修复影响 fmseq 路径，确认现有 FM 相关测试仍全绿：
```bash
tools/env_setup/venv/bin/python -m pytest tools/tests/test_fm_seq.py tools/tests/test_fmopn.py tools/tests/test_audio*.py -q
```

### F. 针对性调 FMP（备选）
若 A–D 都排除后仍偏静，可针对 melody_town 真正用到的族（目前只确认 flute）做更细致的载波 TL 微调（-2/-4 分步），并用同一抓取流程量化 rms 对比。但要避免“盲改所有族”。

## 5. 建议优先顺序

**推荐按 A → B → C → D → E → F 执行**

1. **A（主观直试听）**：最省时间，直接回答“到底听不见还是几乎听不见”。很多时候是主机音量/平衡导致。
2. **B（还原 hal_audio.c 临时诊断态）**：极有可能是这点导致“波形有但电平成倍衰减”。改动范围小但影响大。
3. **C（复核 hal_fm_init/A466）**：排除寄存器初始配置差异。
4. **D（finished 判定日志）**：若一开场就频繁 finished→stop，FM 就只播极短片段。
5. **E（pytest 回归）**：保底。

## 6. 写入 devdoc 的结论

本次修复证明：
- 地址公式错误是确凿的（root cause 1），修复后瞬态能量从 -54 dBFS 跃升至 -24 dBFS，寄存器写入已落到正确算子。
- 但“波形存在 ≠ 主观可听”。现有数据指向：**hal_audio.c 临时诊断态残留** 或 **FM 音量路径（A466）处理** 最有可能是导致持续电平偏低从而主观“没音乐”的主因。

下一步应先**还原 hal_audio.c 非诊断状态**，再做主观直试听+波形对比。只有在还原后仍偏静，才需要进一步细调 FMP 或排查 finished 判定。
