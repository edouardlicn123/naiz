## 四、周日 11-01：两条线并行

### 4.1 CWTEST 第四/五轮：把"环境能不能用"判死（190 / 191 / refdoc I03）

**190（第四轮）** 用版本基线对照把四种失败模式摆齐：

| 配置 | 结果 |
|---|---|
| 3.60 存根 | 三重故障 → 复位 |
| 3.52 存根（`cfg_min` / `cfg_dev`） | 实模式 `#UD`，且栈转储随内存配置变化（不是固定非法指令） |
| 3.52 + VCPI（HIMEMX+EMM386） | EMM386 报 `no suitable UMB`，随后挂死 |
| 官方绑定（官方 cwstub 47152B） | **静默退出**，应用一个字节都没写出 |

结论转向执行指令：**"先求可用环境，不追求把 CauseWay 做好"**。

**191（第五轮）** 是关键转折：

- 自写 `pmprobe.asm`（完全不依赖 CW）在 `cfg_min` 下串口打出 `R A B C 1 2 D` —— **PE + 4KB 分页 + 恒等映射 + 映射页读写全部可用**；
- 因此**环境不是瓶颈**；三种失败模式共同指向 **CW 的扩展内存获取与自身映像映射**（XMS 分配落在低址、`GetINT15Page` 返回 ≈682MB 远超实装 15MB、scratch 页与 CW 自身映像重叠）；
- 上游 CW 源码**没有 PC-98 分支**（全库 grep 无实义命中）。

**refdoc I03** 把这五轮的经验抽成方法论：模拟器能力边界、S0–S3 方针、"模拟器 ≠ 实机"。

### 4.3 新问题：DOS/32A 下 `mag_decode` 间歇失败（192）

开源镜像上启动菜单背景约 **1/4 启动**解不出来（`code=11` flag A 枯竭），DOS4GW 变体未观察到。
两个样本形态不同（早退 `at=36044` / 尾退 `at=255998`），且位流是**零余量**（恰好 64000 bit），
所以任何一次迭代偏离都会立刻放大成 `code=11`。样本 A 的"1127 字节就报越界"指向**栈上 `BitReader` 被外部改写**，首要嫌疑是 BGM IRQ 的 ISR 与解码并发。
**用户明确要求本轮不处理，只记录**——排查路线已写进 192 §七（V1–V6）。

## 八、本轮教训（可直接复用）

1. **链接器只会警告，不会失败**：wlink 找不到 `dos32a.exe` / `cwstub.exe` 都只发 W1093 并产出坏 EXE。必须在 Makefile 里 `$(error)` 前置拒绝。
2. **make 的"已是最新"不等于"已重链"**：改链接参数后要删产物再 make。
3. **观测工具先于被测对象**（185 的 93 个幻影 STALL；189 的调试宏没编进内核）。
4. **"计划文档里的结论"要被实测推翻**：178 的 CauseWay 主选 → 周日换成 DOS/32A。
5. **模拟器自动化的三条硬规则**：一条命令内完成启动→操作→截图；窗口用 `wmctrl` 找；点击不可靠就用键盘。
6. **零余量数据是天然的放大器**：`mag_decode` 的 64000 bit 恰好用尽，任何 1 bit 的扰动都会立刻报错——这对定位是好事，对"能跑就行"是坏事（192）。

## 九、11-01 深夜补记：任务 3–6 的落地与实测

### 9.1 naiz-openpack 独立化（任务 3）

新增 [`make_base_hdi.py`](../../naiz-openpack/make_base_hdi.py)（**整仓库自包含，仅用 Python 3 标准库**）：

- 以包内 250MB 模板为源，`mmap` 解析分区表 / VBR BPB / 双 FAT / 完整目录树；
- 按 `--size`（`250M` / `500MB` / `2G`，1024 进制）重算 CHS 几何（17 扇区/道 × 8 磁头，整柱面取整）；
- 簇大小自适应（4/8/16/32/64 扇区），并强制 `4085 ≤ 簇数 < 65525` 以免落进 FAT12/FAT32 解释区；
- 重建干净 FAT16 镜像：HDI 头补丁 → 原样复制 IPL/分区前保留区 → 补丁 VBR BPB（0x0B–0x1A、0x20）→ 双 FAT → 根目录 → 数据区按 DFS 连续分配；
- 回读产物逐文件比对 名字/属性/大小/SHA256。

实测：250M → 511,904 扇区 / 3,764 柱面 / 4,096B 簇 / 63,901 簇（用 1,247）；500M → 1,023,944 扇区 / 8,192B 簇 / 63,953 簇（用 690），均"文件树校验: 通过"。

**启动实证**：生成的 250MB 基座在 np21kai 上完整启动——`FreeDOS(98) kernel - GIT (build 2043 DBCS OEM:0xfd)`、`HimemX 3.34`、`FreeCom 0.85a_DBCS`，停于 `A:\>` 提示符，`size = 249 MB`。截图 `/home/edo/文档/Trae-CN/temp_20261031_01/base_boot_freedos98.png`。

**追加：10MB 小基座（体积下限与启动修复）**

250MB 基座对 GitHub/仓库分发仍偏大，因此把默认基座压到 10MB：

- 10M → 20,400 扇区 / 150 柱面 / 2,048B 簇 / 5,007 簇（用 2,368，剩 2,639 ≈ 5.4MB）；8M 因簇数 < 4085 会落进 FAT12 解释区，故 **10MB 是当前下限**；
- 改体积后一度只能看到 **`FreeDOS(98) Err!`**：反汇编 VBR（LBA 136）后发现它把模板布局常量**内嵌在 0x45–0x57**——FAT 起始 LBA=2、根目录 LBA=502、根目录 192 扇区、数据区 LBA=694。体积变化后这些常量没跟着改，VBR 仍按 LBA 502 读根目录 → 读错扇区 → 报错；
- 修复：重建时同步改写 `0x45 / 0x47 / 0x4B / 0x51` 常量（并加"模板值吻合"守卫，避免误改未知 VBR），同时按目标最后扇区重算分区表结束 CHS（此前 BIOS 显示体积仍读模板的 `249 MB`）；
- 另修正 BPB `total` 与几何：`0x13/0x20` 应写**分区内扇区数**（整盘扇区 − 136），`0x1C hidden` = 136；
- 结果：`make_base_hdi.py --size 10M --out tools_open/base_freedos98_scsi_10m_clean.hdi` 产出的镜像在 np21kai 上正常启动（见 `size = 9 MB`），并已用它完成一次注入实测（进入 `Naiz Settings` 菜单）。

### 9.5 引擎双打包方式兼容（任务 6）

- `core/Makefile`：`EXTENDER ?= dos4g`；`open` 目标产出 `engine32a.exe` / `engine_a32a.exe`，引擎源码零改动即可双链构建（DOS/32A 由 wlink 绑定进 EXE，DOS/4GW 走盘上 `DOS4GW.EXE`）；
- `build_game.py`：`pack_mode()` / `extender()` 统一解析；`check_pack_assets()` 缺资源即报错并指路 `start.sh openpack|commercial`；
- `deploy_engine()` 按链选产物；`engine_a32a.exe` 缺失时**删除残留 `engine_a.exe`**（否则会把另一条链的 AUTOEXIT 引擎注入盘中）；
- `deploy_runtime()` 只部署本链运行时并清理另一链残留（openpack 清 VEM486 系列/DOS4GW/QMOUSE，cmpack 清 HIMEMX/CTMOUSE）；

- 注入自适应沿用基座探测：有 `FDCONFIG.SYS` 用 FreeDOS 配置、有 `HIMEMX` 用 HIMEMX、QMOUSE 优先 CTMOUSE。
