## 一、症状与证据

实机（`demo-a2`，日文/英文 A/B 截图比对）发现：`nbook001.nb:29` 的整句对白在**全部 9 种语言下都显示英文原文**，译文不生效。该句并非个别，而是「长度超过某阈值」的句子会静默回退英文。

已固定的证据链：

1. **像素比对**：`/tmp/opencode/demo_jpn_017.png` vs `demo_eng_017.png`，对白带 y280–400 差异仅 4.67%（bbox≈62,310–408,400），姓名带 0.00% —— 说明译文确实参与了渲染，但该句未替换。
2. **文件长度审计**（`projects/demo-a2/i18n/`）：

   | 指标 | 最大值 | 出现处 |
   |---|---|---|
   | key 字节 | **223** | 全部 `game_*.txt`（同一键） |
   | value 字节 | **292** | `game_fre.txt` |
   | 整行字节 | **516** | `game_fre.txt` |

3. **对照常量**：`core/lib/tr.c:20` `TR_KEY_LEN 128`、`:21` `TR_VAL_LEN 256`、`:56` `char line[512]`。

即：key 223 ≥ 128 → 存储被截断到 127 → 运行时 `tr()` 用完整 223 B 查表 `strcmp` 失败 → 回落原文。**9 语全中**，因为 key 是英语源文本、长度与语言无关。

## 二、根因：一条由 7 道固定上限构成的链

「长句子失效」不是单点，而是**多道独立上限各自静默失败**：

| # | 上限 | 位置（0.3.017） | 超限行为 | 静默? |
|---|---|---|---|---|
| 1 | `NB_BUF_SIZE 32768` | `core/engine/nb_internal.h:18` | 整份脚本超限 → 干净停机 | 有 WARN |
| 2 | `NB_LINE_MAX 256` | `core/engine/nb_internal.h:16` | 单脚本行 ≥255 B **整行跳过** | 有 WARN |
| 3 | `char line[512]` | `core/lib/tr.c:56`（`fgets`） | 翻译文件整行被**拆行**，值尾部丢失 | **静默** |
| 4 | `TR_KEY_LEN 128` | `core/lib/tr.c:20`（clamp `:83-86`） | key 截断 → 查表失配 → 回落原文 | **静默** |
| 5 | `TR_VAL_LEN 256` | `core/lib/tr.c:21`（clamp `:89-92`） | value 截断 → 译文显示不全 | **静默** |
| 6 | `TR_MAX_ENTRIES 1024` | `core/lib/tr.c:18`（break `:79`） | 超出条目**丢弃** | **静默** |
| 7 | `dialog_text_buf[1024]` | `core/engine/nb_dialog.c:20` | 显示前截断 | 有 WARN（`:107-109`） |

另有显示端一致性副本 `dialog_render_text[1024]`（`core/engine/layer_dialog.c:56`），供换背景后 recompose 重绘；它虽不参与查找，但高于 1023 的页面文本会被截断，必须与 #7 同步。

**同类根因横向排查**（AGENTS §十七「Bug 排查原则」）：`layer_dialog.c:56`、`nb_dialog.c:20` 与 `tr.c` 三处的固定长度缓冲为同型；`nb_question.c` 的 `opt_labels[10][64]` 是另一条独立上限（问题选项标签，本设计**不纳入**，见 §十）。

## 三、容量模型：1 个对话框 = 3 行

按引擎现行规格推导，不靠估：

| 项 | 值 | 出处 |
|---|---|---|
| 框体 | X=80 Y=280 W=480 H=115 | `scene_layers.h:26-29` |
| 正文宽 | `LAYER_DIALOG_CONTENT_W` = 480−12−12 = **456 px** | `scene_layers.h:38` |
| 正文档 | `LAYER_DIALOG_CONTENT_Y` = 280+28 = **308** | `scene_layers.h:39` |
| 行高 | `TEXT_LINE_HEIGHT` = **20 px** | `render.h:27` |
| 每页 max_y | `CONTENT_Y + 60` = **368**（3 行 × 20） | `layer_dialog.c:331/343`；`docs/B02:892` |
| 停绘判据 | `if (y >= max_y) return;`（值 308→328→348，到 368 停） | `render_text.c:136` |
| 换行判据 | CJK `cx+16 > x+456`；ASCII `cx+8 > x+456` | `render_text.c:214/173` |

→ **1 行 = 28 CJK 字**（456÷16）或 57 ASCII（456÷8）；**1 个对话框 = 3 行 = 84 CJK 字**；角色名头部 `bold` 行不参与翻页。

**「5 个对话框」容量**：

| 口径 | 算式 | 字节 |
|---|---|---|
| 译值（CJK，3 B/字） | 5 × 3 × 28 × 3 | **1260 B** |
| 键（英文，1 B/字） | 5 × 3 × 57 | **855 B** |

## 四、设计：常量改动（方案 A）

目标：把上限抬到「5 个对话框」并有 **fail-loud** 保护，而不是再堆一道静默墙。

| 文件 | 现值（0.3.017） | 改为 | 依据 |
|---|---|---|---|
| `core/lib/tr.h` | 无 | 新增 `#define TR_KEY_LEN 1024`、`#define TR_VAL_LEN 1280`（**单一事实源**，供显示层共用） | 键 855 B→1024；值 1260 B→1280 |
| `core/lib/tr.c` | 本地 `TR_KEY_LEN 128`（`:20`）、`TR_VAL_LEN 256`（`:21`） | 删本地定义改用 `tr.h`；新增 `#define TR_LINE_MAX (TR_KEY_LEN + TR_VAL_LEN + 4)`（=2308）；`char line[512]`（`:56`）→ `char line[TR_LINE_MAX]` | 消 #3 拆行 |
| `core/engine/nb_internal.h` | `NB_LINE_MAX 256`（`:16`） | `1152` | ≥ key 1023 + `ira(){}` 包装 7 + 余量 |
| `core/engine/nb_dialog.c` | `dialog_text_buf[1024]`（`:20`） | `[TR_VAL_LEN]` | 显示层不再截断（`nb_dialog.c` 已 include `tr.h`） |
| `core/engine/layer_dialog.c` | `dialog_render_text[1024]`（`:56`） | `[TR_VAL_LEN]` | recompose 副本同步（需 include `tr.h`） |

- `TR_INIT_CAP 64`（`:19`）注释随之更新：初块 64 × 2304 B ≈ 144 KB。
- `TR_MAX_ENTRIES 1024`（`:18`）**不改**，但纳入守卫（§六）与运行期告警（§五）。
- 余量说明：值 1280 相对理论最坏 1260 仅 20 B（+NUL 后可用 1279）。**可选**给值留余量改 1536（≈6 框），代价是条目内存增至 2560 B。默认取 1280。

## 五、运行期「静默 → 响亮」

仅抬常量仍是「移到更远的墙」；必须让**下一次超限在运行期可见**：

1. `core/lib/tr.c` 新增 `static int tr_trunc_count;`，`tr_init()`（`:103`）开头与表释放一起置 0。
2. `load_file()` 在 4 个截断点自增计数：
   - key 命中 `TR_KEY_LEN`（clamp 前判定 `klen >= TR_KEY_LEN`）；
   - value 命中 `TR_VAL_LEN`（clamp 前判定 `vlen >= TR_VAL_LEN`）；
   - `fgets` 后**行未以 `\n` 结尾且非 EOF**（即 #3 拆行）；
   - `tr_count >= TR_MAX_ENTRIES` 提前 `break`（#6）。
3. `core/lib/tr.h` 导出 `int tr_get_truncations(void);`。
4. `core/engine/nb.c::nb_set_lang()`（`:329`）在 `:343` 回落分支合流之后加：

   ```c
   if (tr_get_truncations() > 0) {
       NB_DEBUG("WARN: %d translation entries truncated\r\n", tr_get_truncations());
       hal_log("WARN: translation truncated\r\n");
   }
   ```

   串口通道（`makegame.sh test <game> --serial`）是最可靠出口，WARN 必须走 `hal_log`。

## 六、守卫测试 `tools/tests/test_tr_capacity.py`（新增）

**为什么现有守卫漏了它**：`test_i18n_label_width.py` / `test_cjk_font.py` / `test_user_cfg_settings.py` 断言的是「内容对错 / 放得下宽度 / 键集齐全」，没有一个读 `tr.c` 的容量常量。容量与内容无因果关系，pytest 全绿**不构成**容量正确的证据（AGENTS §十）。

设计：从源码**正则读取**常量，对全部 `projects/*/i18n/*.txt` 与 `projects/*/scene/*.nb` 断言：

1. 每个 i18n 行：`len(key) < TR_KEY_LEN`、`len(val) < TR_VAL_LEN`、`len(line) < TR_LINE_MAX`；
2. 每个 `.nb` 行：`len(line) < NB_LINE_MAX`；
3. 每项目每语言条目数 `≤ TR_MAX_ENTRIES`；
4. 一致性：`NB_LINE_MAX ≥ TR_KEY_LEN + 8`；`dialog_text_buf` 与 `dialog_render_text` 维度 `≥ TR_VAL_LEN`。

**先红后绿自证**（必须留证）：先写测试并在**未改常量**时运行 → 必因 `game_chi.txt:15` key 223 ≥ 128 而失败（红，证明测试真能抓此 bug）→ 再改 §四/§五 → 转绿。

## 十、范围边界与风险

**不做**（本次设计外）：

- `opt_labels[10][64]`（`core/engine/nb_question.c`）问题选项标签上限——选项标签天然短，独立于对白文本；如后续要覆盖，另开一轮。
- `dialog_render_name[64]`（`layer_dialog.c:55`）角色名缓冲——角色名天然短。
- 改动显示管线几何（`scene_layers.h`）——AGENTS §十一 锁定，未经明确许可不得改；本设计**完全不碰**几何，只在既有几何上推导容量。

**风险与权衡**：

| 风险 | 量级 | 处置 |
|---|---|---|
| 内存 | `TrEntry` 384 B → 2304 B；demo-a2 85 条 → 容量 128 → ≈288 KB 堆；硬上限 1024 条 → ≈2.25 MB | 可接受；如紧张可降值至 1280/key 至 1024（已是最省） |
| 栈 | `NB_LINE_MAX 256→1152`：`nb_process` 局部 ≈2×1152 B、`cmd_sceneconf` title ≈1152 B | 增幅约 1.8 KB/帧；`core/Makefile` 无显式 stack 指令，实现后**必须实测**不溢出 |
| 余量偏紧 | 值 1280 对最坏 1260 仅 20 B | 可选值取 1536；或依赖 §五/§六 在下一轮超限时立即报错，而非静默 |
