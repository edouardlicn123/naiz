## 二、实测日志（核心证据）

`logs/serial_demo-a2.log`（2026-10-27 09:52，NP2kai `--start --auto`）节选：


**结论**：

1. **Timer-B 中断确实在工作** —— 第一条候选 INT 14h（IRQ12，slave 4）在**一帧内 tick 了 67 次**。理论期望 ≈62 Hz，67 在 NP2kai 帧时间抖动范围内。这完全证实 devdoc 174 §二的复核：「Timer-B 不可用」是过期结论。
2. **虚拟时钟推进正常** —— `v=4606` at ticks=208。208 tick × 258 units ÷ 16 = 3348 ms，加上 bootmenu 之前的累积 ≈4606 ms。墙钟 w=3000 ms 只是秒级量化的 DOS 时钟。时钟无问题。
3. **候选扫描机制本身是好的** —— 从编程 Timer-B（所有线仍屏蔽）→ 探测第一条 → tick 立即选举 → ISR 接管，零冗余、零误判。
4. **但用户实测「听不到声音」**（ISR 接管后）。这是本轮回归，也是必须回退的根因。

## 四、ISR 路径 FM 静音根因分析（当前待解）

回退只是暂时的。Timer-B IRQ 确认在 tick、虚拟时钟推进正常，说明问题不在 Timer-B 或 IRQ 或 ISR handler 的硬件 I/O —— 问题一定在**从帧路径换到 ISR 路径时漏了什么**。

`audio_tick()`（帧路径，devdoc 174 前一直在跑）做了**不止一件事**。对比：

```
audio_tick()                          audio_tick_isr(delta_units)  (ISR 路径)
──────────────────────────────────   ──────────────────────────────
[AP] 日志                             
audio_tick_isr(last_advance_units) ←→ audio_tick_isr(BGM_TIMER_B_UNITS) ← 参数不同！
g_bgm.rewound 日志 (fmseq_fm_voices)    fmseq_stop + bgm_rewind_phase + g_bgm.rewound 标志
bgm_irq_lock() + PCM buffer free        hal_pcm_advance_units
                                        fmseq_pump / MIDI 事件推进
                                        bgm_rewind_phase (if cur>=len_ms)
```

三个差异可能导致静音：

### 4.1 `hal_wallclock_last_advance_units()` vs `BGM_TIMER_B_UNITS`

帧路径把 `hal_wallclock_last_advance_units()` 的返回值传给 `audio_tick_isr()`；ISR 路径直接传 `BGM_TIMER_B_UNITS`（=258）。这两者**是否等价**？

- `BGM_TIMER_B_UNITS` 是编译期常量（Timer-B 理论步长，16.154 ms 对应 258 个 1/16 ms units）。
- `hal_wallclock_last_advance_units()` 是 vclock 校准后最近一次发出的 advance 大小 —— 在 NP2kai 的 20 Hz 帧节奏下，它**绝不是 258**，而是 `~1000 ms ÷ 20 Hz = ~50 ms = 800 units` 左右。

等等。这是**关键线索**。让我重读 `hal_wallclock_fixed_advance()` 和 `hal_wallclock_last_advance_units()`：

```c
// core/plat/hal_pc98.c
void hal_wallclock_fixed_advance(unsigned long delta_units)
{
    vclock_fixed_advance(delta_units);  // 直接写入，不走校准
}

unsigned long hal_wallclock_last_advance_units(void)
{
    return vclock_last_advance_units();  // 最近一次 smooth_advance 发出的单位数
}
```

`vclock_fixed_advance` 是 ISR 专用入口，**绕开校准**、直接按硬件时基推进；`vclock_last_advance_units()` 返回的是帧路径（`hal_wallclock_smooth_advance`）的最近一步 —— 校准后 ≈800 units / pass（NP2kai 20 Hz）。

### 4.2 两条路径的 PCM 泵大小

帧路径：`audio_tick_isr(hal_wallclock_last_advance_units())` ≈ 800 units。

ISR 路径：`audio_tick_isr(258)` —— 每次只推 258 units。

两者累计吞吐量理论上一致（258 × ~62 Hz = 16 ms/秒，800 × ~20 Hz = 40 ms/秒 —— **不对，帧路径是 ISR 路径的 2.5 倍**）。

**但这不可能导致静音**，只会导致 PCM 播放更慢。FM 的推进是基于 `hal_wallclock_smooth_ms()`（虚拟时钟当前值），与 delta_units 无关 —— 只要虚拟时钟在涨，FM 就应响。

### 4.3 `audio_tick()` 额外做了什么？

**fmseq_stop() 在帧路径 `audio_bgm_stop()` 中显式调用**，ISR 路径 `audio_tick_isr()` 里也有（当 `cur >= g_bgm.len_ms && fmseq_finished` 时）。

**PCM buffer free** 只在 `audio_tick()` 中，带 `bgm_irq_lock()`（即 `_disable()` 关中断）。ISR 路径**永远不 free** —— 但这只泄漏，不会静音。

**`bgm_irq_lock()` 在 ISR 内是否安全？** 它的开头是 `if (hal_bgm_irq_in_isr()) return;` —— ISR 里 `g_bgm_irq_in_isr_flag = 1`（handler 自身置位），所以 ISR 内 `bgm_irq_lock()` 直接 return，不会 `_disable()`。锁对 ISR 路径是安全空操作。

### 4.4 真正的嫌疑：`g_bgm.rewound` 在 ISR 路径的状态

ISR 里 `audio_tick_isr()` 到 `cur >= g_bgm.len_ms && fmseq_finished(g_fm_seq)` 时做：

```c
fmseq_stop(g_fm_seq, &g_fm_sink);
bgm_rewind_phase(now);
g_bgm.rewound = 1;
```

帧路径 `audio_bgm_start()` 和 `audio_bgm_stop()` 在接管/释放 FM 序列时是否用 `bgm_irq_lock()` 同步？让我看看 `audio_bgm_start` / `audio_bgm_stop`：

```c
// audio_bgm_start:
bgm_irq_lock();
fmseq_stop(g_fm_seq, &g_fm_sink);   // 先停旧序列
bgm_rewind_phase(now);
bgm_irq_unlock();

// audio_bgm_stop:
bgm_irq_lock();
fmseq_stop(g_fm_seq, &g_fm_sink);
g_bgm.active = 0;
bgm_irq_unlock();
```

关键问题：**bootmenu 里是否有 BGM？** 让我查一下。

实际上 bootmenu 默认配置下（`bgm = OFF`）**没有 BGM**。`AUD OPNA OK` 表示 OPNA 硬件在，但 `g_bgm.active` 会是 0 —— `audio_tick_isr` 直接 `return`。**所以 ISR 接管后，FM 根本没有被播放**。这就是为什么用户听不到声音！

等等，但那也意味着 ISR 接管时 BGM 本来就没启动 —— 用户听到的「声音恢复正常」到底是啥？让我再想想...

实际上 bootmenu 里应该没有 BGM，用户场景是**进场景后**的 BGM。但我们串口测试只跑了 bootmenu 就 AUTOEXIT 了，所以没等到 BGM 启动。**我没有在 BGM 启动后验证 ISR 路径是否真的会静音**。

**这个分析目前停在「bootmenu 没有 BGM → ISR 路径无音」** —— 这可能是个假阳性。真正的根因可能在别的地方。需要进 scene 后再测 ISR 路径。但用户已要求先回退并写 devdoc，本 devdoc 先停在这里，把「bootmenu 无 BGM 可能掩盖了真实 ISR 行为」作为下一个验证目标记录。

devdoc 174 §三说「候选扫描机制解决了挂错线的风险」—— 这一条不变，实测证实 67 tick / 帧的选举完全正确。

## 六、174 的代码结构保留理由

我没有删除 devdoc 174/174 实施的**任何一行代码**，只是把 `NAIZ_BGM_IRQ` 默认值改回 0。理由：

1. Timer-B IRQ **确实在 tick**（67 tick/帧实锤）—— 候选扫描设计正确，不应被废弃；
2. `audio_tick_isr()` 的 ISR-safe 核心（devdoc 165 §四）是独立价值 —— 即便它现在在 ISR 路径上静默，帧路径仍在调用它，且它是 `bgm_irq_lock()` 临界区的唯一写法；
3. 根因（见 §四）**集中在一处**：帧 vs ISR 路径的单位参数 + 额外清理差异；不是 Timer-B、不是 IRQ 线、不是候选扫描的设计；
4. 修完根因后，只需把 `NAIZ_BGM_IRQ` 默认改回 1 即可重启整个方案 —— 零代码改动，一次开关。

## 十一、附录：两条路径的代码对照（核心片段）

**ISR 路径**（`core/plat/hal_irq.c::bgm_irq_handler`）：

```c
hal_wallclock_fixed_advance(BGM_TIMER_B_UNITS);   // 固定 258 units / tick（16 ms）
audio_tick_isr(BGM_TIMER_B_UNITS);
```

**帧路径**（`core/engine/frame.c::engine_frame_pump` + `audio.c::audio_tick`）：

```c
hal_wallclock_smooth_advance();                    // 校准后 ≈ 800 units / pass（50 ms @ 20 Hz）
audio_tick();
  └── audio_tick_isr(hal_wallclock_last_advance_units());  // 传校准后最近一步
  └── g_bgm.rewound 日志                                   // ISR 不做
  └── bgm_irq_lock() + PCM buffer free                     // ISR 不做（ISR-safe 原则）
```

参数差（**258 vs 800 units**）是当前最显眼、最具体、最容易修的嫌疑点，但 **FM 事件推进是看虚拟时钟当前值（`hal_wallclock_smooth_ms() - g_bgm.wall0`），与 delta_units 无关** —— 所以这个差异应只影响 PCM 泵大小，不应影响 FM 是否发声。真正的静音根因仍在 §四 的「bootmenu 无 BGM 污染证据」之后才能判定。
