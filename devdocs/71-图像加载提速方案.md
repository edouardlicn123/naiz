# 71 — 图像加载提速方案（细化版）

> **状态**: P1/P2/P3 已实施（0.2.022）；P4 及撤回项待未来资产式样变更时再评估
> **日期**: 2026-08-13
> **范围**: IMAGE.DAT 加载链路（`core/engine/image.c` / `image_cache.c` / `core/lib/mag.c`）
> **方法**: 静态分析 + 运行期热路径推断 + 资产实测，结论核实到 `file:line`
> **结论（修正版）**: 当前全部资产为 **8bpp**（`mag.c:326-339` 的 4bpp 扩展路径从不执行），真实热点是「缓存命中必 `mag_copy` + 未命中插入再 `mag_copy`」的整幅深拷贝；建议优先做**缓存引用计数免拷贝**，其次去 padding 行化与 LRU 扩容
> **实施记录（0.2.022）**: P1 引用计数免拷贝落地（`MagImage.refcount` + `mag_retain`/`mag_release`，`image_cache` 直接持有不深拷贝，6 处 `image_load` 调用方 `mag_free`→`mag_release`，`mag_copy` 移除）；P2 LRU 4→8 槽；P3 去 padding 逐行 `memcpy`（8bpp/4bpp 统一）。host 单元验证全绿（引用计数平衡、借用不悬垂、8bpp/4bpp 像素等价），`make -C core` 0 error/warning，audit A/B 清空，pytest 62 passed。

## 1. 加载链路现状（基线，已核实）

### 1.1 调用时序

```
image_load(id)  [image.c:143]
  → image_cache_lookup(id)      [image_cache.c:49]
      → 命中: mag_copy(整幅)    [image_cache.c:58]   ← 热点① 每次调用深拷贝
  → mag_decode(raw, size, &img) [mag.c:88]            ← 仅未命中
  → image_set_palette(img)      [image.c:175-177]      ← 未命中时(非 sprite)
  → image_cache_insert(id, img) [image_cache.c:72]
      → mag_copy(img) 入槽      [image_cache.c:80/100] ← 热点② 又一次深拷贝
  → 命中路径同样调 image_set_palette(cached) [image.c:156-158]  ← 修正：命中也设调色板
```

### 1.2 资产实测（全部 8bpp）

| 资产 | 尺寸 | 像素字节 | 用途 |
|---|---|---|---|
| comlogo / mainmenu / powed / seasidebg / splbg / pink_grid / yellow_grid | 640×400 | 256,000 | 背景/整屏 |
| fei-*×5 / ira-*×2 / neon-normal | 200×400 | 80,000 | 立绘 sprite |
| loadtitle / savetitle | 155×40 / 166×40 | ~6,000 | 黑花标题 |

**推论**：`mag_decode` 内 4bpp→8bpp 扩展（mag.c:326-339）对当前资产**零执行**；去 padding（mag.c:350-363）对 8bpp 全幅对齐图也**跳过**（`pad_px_left=0` 且 `crop_width==pixel_width` 时不进入）。解码主循环本身是格式核心，不可跳过。

### 1.3 调用方契约（6 处，全为「加载→即用→立即释放」）

| 调用方 | 位置 | 使用模式 |
|---|---|---|
| `layer_sprite_show` | layer_sprite.c:107 | load → blit → `mag_free` |
| `layer_sprite_face` | layer_sprite.c:158 | load → blit → `mag_free`（y≥280 时提前 return 释放 :164） |
| `layer_sprite_replace` | layer_sprite.c:234 | load → blit → `mag_free` |
| `layer_redraw_sprites` | layer_sprite.c:326 | 循环内 load → blit → `mag_free`（:329/:334） |
| `cmd_bg` | nb_commands.c:159 | load → blit → redraw → `mag_free` |
| `save_load_draw` | nb_saveload.c:57 | load → blit_sprite → `mag_free` |

**共性**：全部读像素后立即释放，无任何写回、无跨帧持有。这是引用计数方案可行的前提。

## 2. 方案细化（按修正后优先级）

### 2.1 缓存引用计数免拷贝 — 高风险，收益最高（推荐 P1）

**问题**：每次 `image_load` 命中即 `mag_copy`（image_cache.c:58）整幅 256KB/80KB；未命中时插入又 `mag_copy` 一次（:80/:100）。sprite 热路径每帧对每个 active sprite 调用，每帧 N 次 malloc+memcpy+free。

**方案**：`MagImage` 增加引用计数，用 `mag_retain`/`mag_release` 取代深拷贝语义。

**数据结构**：
```c
/* mag.h */
typedef struct {
    ...
    int refcount;      /* 新增：引用计数，0 时释放 */
} MagImage;

/* mag.h 新增 API（替代 mag_free 调用点） */
MagImage *mag_retain(MagImage *img);   /* refcount++，返回 img */
void      mag_release(MagImage *img);  /* refcount--，归 0 时 free 像素+结构 */
```
`mag_copy` 保留（未命中解码产物入槽用），`mag_free` 改为 `mag_release` 内部实现或保留为强制释放。

**数据变更**：`MagImage` 增加 `refcount` 字段；`mag_copy` 移除（无调用方）；`mag_free` 改 `mag_release`。

**image_cache.c 语义变更**：
```c
/* lookup：命中返回槽内共享指针并 retain，不再深拷贝 */
MagImage *image_cache_lookup(int id) {
    ...
    if (slot.id == id) { slot.hits++; return mag_retain(slot.img); }
}
/* insert：解码产物直接入槽（refcount=1），不再 mag_copy */
/* evict：mag_release(slot.img)，仅减槽引用 */
```

**image.c 语义变更**：`image_load` 未命中路径 —— `mag_decode` 产物入槽持有 1 引用，返回给调用方前 `mag_retain`（refcount=2）；调用方 `mag_release` 后剩 1（槽持有）。

**调用方 6 处**：`mag_free(img)` → `mag_release(img)`，其余不变。

**正确性论证（引用计数消除悬垂）**：
- 借用期间 evict：槽 `mag_release` 仅 refcount--，因调用方仍持引用，内存存活，无悬垂
- 调用方释放：refcount 归 0 才真正释放
- 无需「借用区间不跨 insert」的脆弱约定——这是纯借用方案的缺陷（见 2.2）

**边界分支**（必须逐一处理）：
- layer_sprite_face y≥280 提前 return（layer_sprite.c:164）——该分支的 `mag_release` 不能漏
- layer_redraw_sprites 循环 continue 分支（:329）
- `image_set_palette` 只读像素，借用安全

**风险**：中高。
- 每处 `mag_retain` 必须配 `mag_release`，漏配 = 内存泄漏（可在 `image_cache_clear` 后断言 refcount 归零）
- `image_load` 返回 NULL 时调用方已有判空，无影响
- `mag_copy` 需初始化 refcount=1

**收益**：命中路径省 1 次 malloc+memcpy+free；未命中路径省插入的 1 次拷贝。每帧 N 个 sprite 省 N×(80KB 深拷贝)；背景整屏省 256KB。

### 2.2 纯借用指针（备选，不推荐）— 高风险

**方案**：命中直接返回槽内指针，调用方不释放；仅未命中返回解码产物（调用方释放）。

**缺陷**：调用方无法区分「借用 vs 自有」，且 `cmd_bg`（nb_commands.c:159-172）持借用指针期间调用 `layer_redraw_sprites()` → 内部再 `image_load` → 可能 evict 掉同一槽 → **悬垂**。必须依赖「借用区间不跨 `image_load` 调用」的脆弱约定，易回归。仅当不想改 `mag.h` 时备选。

### 2.3 去 padding 逐行 memcpy — 低风险，低-中收益（P3）

**问题**：去 padding（mag.c:350-363）是逐像素双重循环。对 8bpp 全幅对齐图（当前资产）不进入；但对**非对齐 8bpp 图**或 **4bpp 图**每解码执行 O(w×h) 逐像素拷贝。

**方案**：8bpp 时 `pad_px_left` 为整数像素，可直接逐行 `memcpy`：
```c
for (y = 0; y < crop_height; y++)
    memcpy(cropped + (size_t)y * crop_width,
           output + (size_t)y * pixel_width + pad_px_left, crop_width);
```
4bpp 时需先扩展再裁剪（见 2.4），该优化与其合并。

**风险**：低。**收益**：仅在存在 padding 时体现；当前 8bpp 对齐资产无收益，作为格式健壮性优化。

### 2.4 4bpp 扩展与去 padding 合并单趟 — 低风险，当前无资产受益（P4）

**问题**：4bpp 解码分两步——扩展（mag.c:326-339，O(n)）+ 裁剪（:350-363，O(n)），两次分配。

**方案**：解码输出直接扩展进最终缓冲（跳过 pad 区），一次分配一次遍历。

**注意**：当前所有资产为 8bpp，此路径**零执行**。仅当未来工具链产出 4bpp 资产或格式兼容需要时才有收益。**无需优先做**。

### 2.5 LRU 槽数 4 → 8 — 极低风险，低收益（P2）

**问题**：4 槽在场景（背景+立绘×表情）下频繁 evict，放大解码次数。实测立绘资产 5+3+1 个，背景 7 个。

**方案**：`IMAGE_CACHE_SLOTS`（image_cache.c:12）4 → 8。**保持编译期宏即可，不引入 config.toml 注入**（运行时配置收益/复杂度不成比例）。

**风险**：极低。**收益**：命中率提升，减少重复解码。内存代价：每槽一图（8×80KB~256KB 驻留，仅在用过的图像累积）。

### 2.6 调色板 — 修正事实，非热点

**修正**：`image_set_palette` 命中路径（image.c:156-158）**也会调用**，但仅限非 sprite 且仅在 `image_load` 时（scene 切换/背景加载）。sprite 立绘**不设调色板**（image.c:223 跳过 7/15 判定只在 sprite 时执行 `image_set_palette` 内部判断）。

**结论**：调色板非热路径，**不优化**。之前「每帧重设」的描述有误，撤回。

### 2.7 构建期预转 8bpp — 高风险，远期

**方案**：工具链 `pack_images` 预扩展为 8bpp。**现状资产已是 8bpp**，此方案收益归零，仅当未来引入 4bpp 资产时再评估。降级为「不推荐」。
