# 173 — 虚拟时钟停顿保护：窗口校准被 stall delta 污染导致「追赶式快速播放」

> **状态**：`已实施并实机验证`（`core/lib/vclock.c` stall protection 落地；用户实测「速度正常了」，残余「轻微拖延/过快」归因于 20Hz 帧粒度，见 devdoc 174）
> **创建于**：2026-10-27
> **承接**：`devdocs/171`（ISR 未触发与协作泵双失）、`devdocs/172`（引擎层修复验证）
> **后继**：`devdocs/174`（Timer-B 中断线候选扫描）

---

## 一、症状

用户实测：BGM 在某些操作（换立绘、文字刷新、过场）完成后**先快速播放追赶、再回到正常速度**；同时「每个音都拖得很长」。

两条症状互斥，说明是**时钟本身**在两个方向上振荡，而不是事件表或音源的问题。

## 二、根因

`hal_wallclock_smooth_advance()`（`core/plat/hal_pc98.c`）是虚拟时钟的唯一写者，它把每次调用之间的真实毫秒差 `delta` 喂给 `vclock_advance()`（`core/lib/vclock.c`），后者用**滑动窗口**（`VCLOCK_WINDOW_MS = 1000`、`VCLOCK_MIN_WINDOW_PASSES = 2`）测量「每 pass 平均消耗多少真实毫秒」，并以该速率前进虚拟时间。

主线程在长 VRAM blit、`playanima` 解码或过场扫描中会**停顿** 100–500 ms。恢复后的第一次调用拿到的 `delta` 是**整段停顿**，把它计入 `accum/passes` 会严重稀释每 pass 速率（例如 5 ms/pass 被算成 25 ms/pass），窗口随即按错误速率发布；随后数个帧虚拟时钟一次推进 25 ms，`audio_tick()` 每个 tick 派发 5 倍数量的事件 —— **这就是耳朵听到的「追赶」**。反之，校准长期偏低则表现为「拖」。

## 三、修复（方向 A，已落地）

在 `vclock_advance()` 中识别 stall 并**丢弃该 delta 的校准贡献**：

```c
if (vc->calibrated
    && delta > VCLOCK_MAX_ADVANCE_MS      /* 100 ms */
    && delta < 500UL) {
    vc->passes = 0;
    vc->accum = 0;
    return;                                /* 虚拟时钟暂停，保留已校准步长 */
}
```

检测带**双边有界**，理由必须写清（否则下一次「优化」会拆掉一边）：

- **下界 `VCLOCK_MAX_ADVANCE_MS`（100 ms）**：低于它的抖动本来就被窗口钳制吸收，不构成本质污染；把 50 ms 也判为 stall 会把正常的 20 Hz 帧节奏打成永久暂停。
- **上界 500 ms**：NP2kai 的 DOS 时钟（INT 21h AH=2Ch）是**秒级量化**的，第 20 次调用会给出 `delta = 1000 ms`。若把它当 stall 处理，虚拟时钟每过一秒就冻结 1 秒，比原问题更糟。真实 blit/解码在 NP2kai ~20 Hz 下被帧预算限制在 50–200 ms，不会接近 500 ms。

行为语义：**stall 期间虚拟时钟暂停，恢复后按停产前的步长继续**。这等于「音乐在卡顿时停一下再继续」，而不是「卡顿后狂赶」。

## 四、为什么没有第二条时间基线（方向 B 已撤销）

曾评估过让 FM 音序器脱离虚拟时钟、直接读墙钟（`fmseq` 内部维护 `wall_ms_cursor` + `fmseq_pump_elapsed()`）。**已全部删除并回退到 HEAD**，原因：

1. 两条时间基线会各自漂移，同一乐句的音符间距开始抖动；
2. 用户的核心约束是**流畅**而非「追上」——卡顿时保留音乐相位比强行对齐墙钟更接近原始硬件行为；
3. 墙钟路径与 ISR 的固定步长（`hal_wallclock_fixed_advance()`）语义冲突，双写者不可分离。

`core/lib/vclock.c:127-128` 保留一段说明：FM 管线**跟随同一个虚拟时钟**，因此 stall 暂停也会让 BGM 暂停；这是设计选择，不是缺陷。

## 五、验证与残余

- 用户实测：「速度正常了」→ 追赶爆发消失。
- **残余**：「还有轻微的拖延和过快」。这与 stall 无关——`audio_tick()` 只在帧泵调用点运行，NP2kai 下实际 pass 率约 20 Hz（50 ms 网格），音符起音被量化到最近的帧。±25 ms 的抖动正好是可闻的「轻微拖延/过快」。
- 该残余只能靠把音泵粒度从 50 ms 降到 Timer-B 的 ~16 ms 解决，即 devdoc 174 的候选线扫描。
