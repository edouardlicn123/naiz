一、重建与参考引擎分析

00 – 09

引擎重建纲领、图像/场景格式规范、参考引擎（love es××××）差异分析，以及显示路径的多轮探索（VRAM 直写 / GDC 端口 / GRCG / DPMI）。

00新引擎重建计划计划 · 多数阶段已实施

核心思路

  • 抛弃 gcc-ia16/DJGPP 双目标 + MHVN98 遗产，重建 Open Watcom → DOS/4GW → LE → VEM486 → NP2kai 完整链路，与参考游戏一致。
  • 放弃厚重 HAL 抽象与 EGC/GRCG 残留，改为无 HAL、直接 port I/O、32-bit flat 指针、纯软渲染、标准 C 文件 I/O 的单目标构建。
  • 启动从 CONFIG.SYS INSTALL= hack 改为 AUTOEXEC.BAT；内存管理用 VEM486（XMS/EMS/VCPI），SET DOS16M=1 启用 DOS/4GW PC-98 路径。
  • 工具链全部 Python；FAT16 文件系统即容器，无需 ARCHIVE 格式；分 Phase 0–4 实施。
最终落点：成为后续所有工作的总纲，直接催生 core/ 下 engine/plat/data 分层架构；键盘/VRAM 等阻塞点在后续文档继续推进。
现状关联：现引擎（core/ 目录、watcom 构建、render.h 软渲染管线）即本计划产物。
01MAKI / MAG 图像格式规范规范

核心思路

  • MAKI/MAG 为 Woody Rinn 两代 PC-98 图像格式；核心压缩 = 有序抖动像素规律 + flag 帧标记 + 行间 XOR 去重。
  • MAKI（MAKI01A/B）：MSB-first、640×400、4bpp；Phase 1 建 mask buffer、Phase 2 光栅填充、Phase 3 行间 XOR。
  • MAG（MAKI02）：LSB-first、变长头（签名/型号/用户名 + 固定 32 字节 + 调色板）、4/8bpp；主循环每 2 字节处理，相对回拷表 15 位置。
  • 调色板按型号代码复原（MSX 3 位、X68K 5 位、Mac 8 位等），MSX 需 YJK→RGB 转换。
最终落点：成为 mag.c 解码器与 png2mag/img2mag 编码器的实现依据。
现状关联：MAG 现为引擎主图像格式（IMAGE.DAT、mag.c、docs/B11）。
02场景字节码格式规范规范

核心思路

  • SCENE.DAT 格式：头 + 每场景 LZ4 独立压缩块（解压最大 4096 字节）。
  • VM 状态：Z/N 标志 + VMFLAG；统一 16 位地址空间五区（临时/全局/局部变量与标志）。
  • 执行模型：while(VMFLAG_PROCESS) 逐帧 dispatch，阻塞靠清标志，nowait(0x0F) 为异步前缀。
  • 指令集 0x00–0x3F 共 46 opcode；Naiz 扩展重定义 0x30–0x3F 并新增 0x40。
最终落点：成为 scene.c 场景 VM 与 scene_asm.py 汇编器依据（现 NB 解释器的前身）。
现状关联：现引擎已演进为 NB 剧本解释器，但标志/阻塞/nowait 核心模型思想延续。
03当前进度与等待反编译期间的行动指南调查记录

核心思路

  • 记录 2026-06-08 时点进度：工具链、串口、GDC 初始化、LZ4、场景 VM、文本、FONT、MAG 均已就绪或待确认。
  • 两套引擎格式对比（MHVN98 vs love es××××）：脚本 EQA、图像 ECG、容器 LOVE.EAR、文本格式高风险冲突，硬件层一致。
  • 划分「可安全继续」与「必须暂停等反编译」的工作清单。
最终落点：指导等待期工作分配；最终 Naiz 选择自研 NB 剧本 + MAG/256 色路线而非移植 EQA。
现状关联：历史背景。
04参考引擎分析与修正计划已实施

核心思路

  • 定位 VRAM 平面地址错误：参考引擎用 PC-9801 VM 4 平面紧密布局 0xA8000/0xA9000/0xAA000/0xAB000，当前引擎继承分散布局，疑为黑屏根因。
  • 已验证路径：GRCG + 绝对地址 0xA8000 是唯一有效显示路径；TMW 写 0x0000 黑屏、应写 0xFFFF。
  • 调色板端口 RGB 分别写 0xAA/0xAC/0xAE（原全写 0xAA，已改）；GDC 模式用极简序列；VSYNC 读 0xA0 bit0。
  • ECG 比 MAG 简单 10 倍，建议直接实现 ECG（后未采纳）。
最终落点：pc98.h 平面地址修正与 gdc.c 调色板三端口已落地。
现状关联：现引擎调色板端口与 VRAM 平面即按此修正；ECG 主张最终被否决，GRCG 被 PEGC bank 方案取代。
05方案 A 实施计划（DOS 文本层显示）计划

核心思路

  • 放弃 32-bit CPU VRAM 直写，统一用 printf（DOS 文本层）作为全部显示通道，短周期内让 VM/文本引擎可观测。
  • 无需 GDC 初始化、BIOS 模式切换、VRAM 访问。
最终落点：作为临时显示方案执行，后被 13 起 PEGC bank 切换的像素级渲染取代。
现状关联：「显示不可用先走 printf」的思路仍在早期调试中沿用。
06GDC 端口像素写入计划计划 · 未成为主线

核心思路

  • uPD7220 可通过 WDAT 命令直接写像素绕开 CPU 内存总线；设写光标 → WDAT(0x20) → 逐字节写 0xA0。
  • 实验分四步：基础像素 → 白方块 → 字形 → 文本框系统。
最终落点：WDAT 在 NP2kai 中 0x20 非标准命令，被 13 的 PEGC bank 方案取代。
现状关联：gdc_set_palette 端口序列仍沿用，WDAT 写入函数已删除。
07GRCG 重试计划计划 · 未成为最终方案

核心思路

  • 用参考引擎 vram.c 精确寄存器序列重建 GRCG 驱动，此前失败疑因模式寄存器/平面地址/CG-TMW 未对齐。
  • 按参考序列设 GDC 模式 → 调色板 → 直接 CPU 写 VRAM → 不工作再加 GRCG CG mode。
最终落点：09/10 揭示根因在 NP2kai 渲染管线而非 GRCG 本身；GRCG/EGC 代码已被引擎彻底移除。
现状关联：全部软渲染，显示走 PEGC packed-pixel。
08VEM486 Raw DPMI 启动迁移计划计划 · 备选运行时

核心思路

  • 放弃 DOS/4GW WATCOM stub，改用参考引擎 start16.asm 原始 DPMI 启动（INT 2Fh/1687h → INT 31h → C main）。
  • 与 DOS/4GW 路径共享全部 C 源码，仅入口不同；Makefile 双目标。
最终落点：VEM486 原生 DPMI 为备选运行时；实际主线仍走 DOS/4GW。
现状关联：DPMI INT 31h 映射在 09 被证实在 NP2kai 中不达显示；int386()（15）成为 BIOS 中断正确途径。
09VRAM 调查完整记录调查记录 · 12 小时

核心思路

  • CPU 直写/DPMI 映射/GRCG 触发均不达显示，唯一有效通道为 CRT BIOS；后确认 CPU 写入实际可达 GDC，只是 NP2kai 内存表 text-RAM 交错页造成条纹。
  • memfn0 表 32KB 粒度（34 条目），entry 20 映射 memtram 且内部静默丢弃 0xA5000–0xA7FFF。
  • 关键事实：0x6A 端口是触发 CRTC→MEMM_VRAM 更新的关键，参考引擎写 outp(0x6A,0x00)。
  • 四轮修复 + NAIZ_DEBUG 三层诊断框架（DRAW trace / VRAM BMP / PIXBUF raw）。
最终落点：NAIZ_DEBUG 诊断框架与 gdc.c 修复（移除文本层 STOP + outb(0x6A,0x00)）。
现状关联：现引擎显示管线已走 PEGC（13–15），不再依赖这些 NP2kai 补丁。

13256 色模式迁移方案已实施

核心思路

  • 从 16 色（GDC/EGC 4 平面）迁移到 256 色 PEGC packed-pixel（INT 18h AH=30h，640×400 line-double）。
  • 调色板端口不变，每通道 4-bit 右移改为 8-bit 直写；VRAM 访问改为 bank 切换（逻辑地址 Y*640+X，bank 寄存器 0xE0004）。
  • engine 改动：pc98.h PEGC 宏、video.c AH=30h、gdc.c 变空 init + 8-bit 调色板、render.c 完全重写、img2mag.py --256 标志。
最终落点：256 色 PEGC 显示管线全面落地；IMAGE.DAT 从 108KB 增至 252KB（约 2.3×）。
现状关联：现引擎显示管线的直接基础（docs/B02）。
14256 色模式迁移：阶段总结已实施 + 调查

核心思路

  • 引擎侧全部完成，但 NP2kai 显示不更新——VRAM BMP 恒为 RGB(0,0,26)。
  • 根因：NP2kai 256 色四个互锁缺陷——① AH=30h 未启用 bank 切换 ② 渲染函数漏查 gdc.analog&4 ③ 8bpp 需 GDCANALOG_256E ④ VGAWR8 设错 GDCSCRN 标志。
  • 选项：A 深修 NP2kai / B 回退 16 色 / C 16 色+dithering。
最终落点：缺陷 ①② 已修（bios18.c、pccore.c），诊断工具链（naiz_vram_*.bmp 等）建立。
现状关联：衔接 15 第二阶段；outb 0x6A 在 15 被证实无效，改为 int386()。
15256 色模式移植：第二阶段调查 + 修复

核心思路

  • 关键发现：outb(0x6A,...) 在 DOS/4GW 中无效（被 VEM486 DPMI host 吞掉），必须用 int386() DPMI 调用。
  • 阶段 1 根因修复：scrndraw.c:317 的 naiz_composite_planar() 在 256 色被错误调用，改为 (gdc.analog & 3)==0 才走 composite。
  • 阶段 2 瓶颈：pex_g 只渲染 24 像素，np2_vram 数据已到位、调色板链路正常，剩余疑点 SURFACE_WIDTH/grphvad/dirty。
最终落点：阶段 1 修复落地；阶段 2 的 pex_g 问题留待后续，诊断与修改清单完整交接。
现状关联：int386() 调用方式与 engine 侧 bank-switched 渲染路径成为现引擎标准。

17VRAM 批量写入优化方案已实施

核心思路

  • 消除每像素一次 bank_select，改为按 bank 边界切块写入，全屏 blit 从 256,000 次降到 ≤9 次。
  • vram_blit/fill_rect 用 while(addr<end) 切块算法；透明/不连续场景用 prev_bank 缓存去重。
  • 明确不做 EGC 加速、解码缓存、软件帧缓冲；函数签名全不变。
最终落点：当前 render.c 采用 win[addr & (VRAM_BANK_SZ-1)] 按 bank 切块写入。
现状关联：显示管线的性能基础。

19NP2kai 平台差异与调色板自检系统已实施

核心思路

  • 本机 NP2kai 为完整 PC-9821 VX 模拟（SUPPORT_PC9821/CRT31KHZ/PEGC），与其他简化版存在行为差异。

  • 自检 video_check_palette()：端口回读验证索引 1=Blue、7=White。
最终落点：video.c AH=30h→40h 顺序、image_set_palette 全量上传、pack_images 重映射预留索引。
现状关联：video_check_palette() 仍存在于 video.c:136，「Pal chk OK」串口自检沿用至今。
