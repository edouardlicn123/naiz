## 一、结论速览

1. **「完整开源（含源码）的 90 年代商业 PC-98 游戏」几乎不存在。** 商业作品（Falcom/elf/Will 等）全部闭源；可分析对象分**三类**：①反编译/作者存档的游戏本体、②音源驱动与播放器、③现代复刻引擎。
2. **对「游戏怎么做 BGM」信息密度最高的不是游戏本体，而是 ReC98（游戏侧集成实证）+ ADV98（现代工程最小样例）+ PMD 系驱动源码（节拍模型）。**
3. **原版主流做法再次确认**（与 `F05` §5 对照表一致）：**音序器常驻（PMD 类）+ YM2608 Timer-B 硬件中断（IRQ3）驱动节拍，游戏主循环只发「播/停/查」命令**——节拍与主循环解耦，这正是本仓方案 C（`devdocs/131`/`134`）的蓝本。
4. 许可差异大：**pmdmini 为 GPL-2（不得复制进本仓）**、ReC98 无开源许可且反编译对象为商业作品（只读研究）、PC98src/mucom88 为 CC BY-NC-SA 类（非商用+署名）、ADV98(MIT)/98fmplayer(BSD-2) 最干净。详见 §五。

### 三.1 ReC98：游戏侧如何集成声音子系统（最有价值的实证）

ReC98 的 README 与发布记录（【核实】）给出的 BGM 相关事实：

1. **音序器不是 ZUN 自己写的**：`ONGCHK.COM` 明文标注「part of the PMD sound driver by KAJA, and therefore doesn't need to be disassembled」——TH02–05 的 ZUN.COM 内含 PMD 组件，重建时保持其二进制原样。
2. **声音子系统是一等公民**：TH04/TH05 有**首启声音设置菜单**（BGM mode / S.E. mode 选择，rec98.nmlgc.net/blog/2023-11-30）；机型检测失败时给出 `Startup PMD ...` / `WARNING: Cannot detect PMD` 类提示（`F05` §1 转引其 2021-05-12 博客）。
3. **缓冲区按曲类分配**：TH02 的 `GAME.BAT` 给 PMD 分配 FM 曲 8KB / 音效 2KB / MMD 12KB，且**大小是驱动命令行可配的**——游戏侧曾因硬编码读入大小而溢出（ZUN bug，ReC98 记录，`F05` §1）。
4. **切曲先停再载**：TH02 Music Room 修复为「先停当前曲再加载新曲」，避免慢速存储加载期间 **PMD 或 MMD 播放垃圾数据**（releases 页）。
5. **机型分型**：CanBe 机型使用特殊 FM 芯片、无法自动探测、需要专用 PMD 驱动（releases 页）——原版生态对「探测 + 降级」的处理粒度。
6. API 形态（`F05` §1 转引）：`AH=09h` 查驱动类型（OPN/26K 兼容 vs OPNA/86 兼容）、`AH=22h` 查缓冲区实际大小——**游戏与驱动之间只有查询/控制命令，没有寄存器直写**。

**对本仓的意义**：这 6 条 = 「游戏侧集成 PMD 的正确姿势」检查单素材（停了再载 / 缓冲上限 / 机型探测 / 模式选择 / 失败降级），可对照审 naiz 的 `audio.c` 后端自动检测与 `audio_bgm_start` 流程。

### 三.2 ADV98（yarufu/pc98）：与 naiz 工程形态最近的对标

【核实】README 要点：

- **PMD BGM 支持**：PMD 常驻时 BGM 有效，**未常驻时游戏本体照常运行**（声音静默降级，不 fail-loud——与 naiz「无 MPU→FM→都无 fail-loud」的策略不同，属设计取舍差异）；
- 实机验证环境：PC-9821Ra43 + PC-9801-86 / PC-9821V13 + PC-9801-118（非 PnP），模拟器 T98-NEXT；必要内存约 300KB；
- 工具链 ia16-elf-gcc（16 位）+ Makefile，脚本型 ADV（背景/立绘/选项/存读档），`ADV98.EXE` + `script.txt` 部署形态；
- 依赖 KAJA 的 PMD 为外部常驻组件，**引擎本身不含音序器**——与 naiz「自研 `fmseq` 音序器内置」形成对照。

**可借鉴点**：①「驱动常驻与否」的降级语义；②实机验证清单写法（机型逐列）；③脚本层与音频层的接缝（BGM 键→曲文件）。

## 六、核心结论：原版 PC-98 游戏 BGM 的三条路线

| # | 路线 | 谁在用 | 节拍机制 | 本仓对应 |
|---|---|---|---|---|
| 1 | **常驻 PMD/FMP 驱动 + 中断 API** | 商业 ADV/STG 主流（PMD 生态） | YM2608 Timer-B → IRQ3 → 驱动 ISR 推进一步 | `F05` 全文；方案 C（`devdocs/131`/`134`）复刻此模型 |
| 2 | **游戏随附/内含音序器组件**（如 ZUN.COM 内含 ONGCHK 等 PMD 部件） | 东方 PC-98 系 | 仍是 PMD 系时基（组件本身按 Timer-B 走） | ReC98 实证（§三.1） |
| 3 | **MIDI over MPU-401** | 依赖扩展卡的后段作品/本仓首选 | MPU 侧时基 | `F03` §1.2 已决选型 |

**三条路线的共同点**：**节拍与游戏主循环解耦**。游戏侧的声音子系统只暴露「播放/停止/查询/模式选择」，从不在主循环里按墙钟写寄存器——这与 naiz 现状（`fmseq` 协作轮询 + vclock 帧泵，`F05` §5 表第三列）形成直接对照，也正是「原版不颤、我们颤」的架构级解释（`devdoc 143` 未收敛项之一）。

**ReC98 追加的集成级细节**：先停再载、缓冲区按曲类配额、机型探测与专用驱动、首启 BGM/SE 模式、探测失败提示——原版把声音当独立子系统做完整性处理，而非「写几个端口」。

## 七、与 naiz 的对照及行动含义

1. **方案 C 方向再确认**：`F05` §6 的四条行动含义（Timer-B 初始化 → 挂 handler → 解耦事件表 → `G08`/`G09` 风险清单）不受本调研动摇；ReC98/ADV98 提供的都是**旁证**——原版与现代复刻均走「驱动管节拍」。
2. **策略差异登记**：ADV98 的「无 PMD → BGM 静默降级但游戏照跑」 vs naiz「无 MPU 且无 FM → fail-loud」。两者各有理由（ADV98 兼容无音源机器；naiz 消灭静默失败，AGENTS §九.6），**不改，但应知悉这是有意分歧**。
3. **可落地素材（均为读物，非依赖）**：ReC98 集成检查单（§三.1 六条）→ 供审 `audio.c` 后端检测/`audio_bgm_start`；ADV98 → 降级语义与实机验证清单写法；98fmplayer `fmdriver/` → 格式与寄存器精度读物；pc98sndpmdtools OpenWatcom 示例 → 若未来引入外部素材管线的对接参照。
4. **零代码改动**：本轮不产生任何 `core/`/`tools/` 修改，不触发 `bump_version`（AGENTS §十六 仅对 `.c/.h/.py/.nb` 源文件）。

## 八、建议分析路径（按投入产出排序）

1. **`F05` + ReC98 博客（rec98.nmlgc.net/blog，2021-05-12 / 2023-11-30 两篇为入口）** → 拿到「游戏侧集成 PMD」的完整模型；仓内 `F05` 已消化大半，增量在集成细节。
2. **clone `yarufu/pc98`（MIT）** → 最小可运行样例：脚本 ADV 如何接 PMD、如何降级；与 `core/engine/audio.c` 对照阅读成本最低。
3. **clone `myon98/98fmplayer`（BSD-2）** → `fmdriver/`（PMD/FMP 格式解析）+ `libopna/`（寄存器层精度），配合仓内 `F03`/`F04` 寄存器表互证。
4. **（可选）clone `onitama/PC98src`** → grep 音源调用，确认 90 年代商业品质汇编里的发声路径（内容未核实，先开箱再定）。
5. **不推荐优先投入**：pmdmini/hoot（GPL 红线，读思路即可）；商业游戏反汇编（闭源 + 许可风险，ReC98 博客已消化的部分足够）。
