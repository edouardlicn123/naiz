> **结论一句话**：`hal_irq.c` 的 `BGM_TIMER_B_UNITS = 129` 把**手册口径的 1152 当成了 φM 的个数**，而真机 Timer-B 每步是 **2304 个主时钟**（NB=200、φM=7.9872 MHz ⇒ **16.154 ms**）⇒ 常量只有真值的一半，ISR 构建下虚拟时钟以真实时间 **49.8%** 的速率前进，BGM/动画/打字机全线半速、SE/voice 欠喂断续。**NP2kai 的 16.128 ms 是忠实建模（−0.16%）**，正确常量 = **258 units**，真机与模拟器通用，**无需分档**。

## ⚠ 结论订正（2026-10-24）

本文件 2026-10-22 初稿把「实测 16.19 ms vs 手册 8.06 ms」判成 **NP2kai 的 2× 错误**，并据此把修复方案定为「编译期分档：NP2kai 258 / 真机 129」。**方向相反**——错的是 129 这个常量，不是模拟器：

| 初稿断言 | 订正后 |
|---|---|
| 真机 `tB = 1152·(256−NB)/φM` ⇒ NB=200 为 8.064 ms | 手册的 1152 配的是 **φM/2** 时钟；等价写法 `2304·(256−NB)/φM` ⇒ 真机 **16.154 ms** |
| NP2kai 的 16.102 ms 是 2× bug | NP2kai 化简后恒为 `288×(256−NB) µs` = **16.128 ms**，与真机差 **−0.16%**（= 8.0000 vs 7.9872 MHz），**忠实** |
| 5 MHz 模式为 15.851 ms / 254 units | 代数化简后 **同样是 16.128 ms**；「周期随宿主不是常量」的前提不成立 |
| 修复 = 编译期分档（真机 129） | 修复 = **单一常量 258**；真机档 129 若真机生效会把同一个半速故障原样复现 |

**订正证据链**（完整推导与逐行对照见 **`docs/refdocs/F07_opn_timer_clock_reference.md`**）：① YM2612 手册（同源 OPN 核）写 `288×(256−NB) µs`，恰为 YM2608 手册的 2 倍，GenDev/SpritesMind 2008 定论为「定时器按 φM/2 计数」；② ymfm（`period × 24 × 6 = 2304`）、Nuked-OPN2（`subcnt==16` × 144 clk/样点）、BlastEm（`sub_timer_b += 0x10` 满 16 次 = 2304）、NP2kai（`288×(256−NB) µs`）**四份**独立实现一致给出 2304；③ PMD 的节拍常数 `10800000`（`F05` §2）只在 2304 口径下自洽，按 1152 反解会要求 φM ≈ 4 MHz；④ 86 板晶振经 MAME `pc9801_86.cpp:85` 取证为 7.9872 MHz；⑤ 本文件 §3.1 自己的实机数据（6795 tick / 110.000 s = 61.77 Hz）与 16.15 ms 模型吻合、与 8.06 ms 差一倍；⑥ **2026-10-25 补充外部取证**：MUCOM88 的 `t198`（直写 `$26`，PC-8801 的 OPNA 同为 7.9872 MHz）被社区实测为 ≈1/60 s/步 ⇒ 每步 ≈288µs（`F07` §4.4），TmEE 的实机读数也是 **~100 Hz 而非文档的 ~50 Hz**（`F07` §2.2）。

**保持不变**：§4.2（PCM 投料时间源取虚拟钟，独立根因）、§5.2、§5.3 的 `v/w` 判据、§六 方法纪律（「速率断言必须有独立对照量」正是本轮订正的方法论来源）。

## 一、症状

`NAIZ_BGM_IRQ=1` 构建在 NP2kai 上**不卡死、中断链完整**（`[ISR] ticks` 单调递增），但用户侧听感不对：音乐拖沓、发声断续，主观接近「顿挫」。同期协作式构建（默认）则表现为「立绘/场景切换时 BGM 停住」——那是 `devdocs/163` 的 M1 时间债，与本文是两件事。

## 二、判定过程

### 2.1 先推翻一个假阻塞

`devdocs/167` 初稿把「当前阻塞」写成「FM 后端 `malloc(fmseq_size())` 失败 ⇒ `g_fm_ok=0` ⇒ `hal_bgm_irq_init()` 被跳过 ⇒ ISR 未安装」。该结论有**两条独立反证**：

1. **日志时效性**：初稿引用的 `logs/serial_demo-a2_trace.log` mtime 为 **2026-09-29 11:51**，内容是 `AUD WARN: no MPU-401 (BGM disabled, PCM unchanged)`——早于 FM 后端存在的时期，全文件不含 `BGM IRQ` / `[ISR]` / `OPNA OK`。它证明不了 10 月构建的任何行为。
2. **逻辑互斥**：`hal_bgm_irq_init()` 只在 `g_fm_ok` 为真时被调用，而 `g_fm_ok = 0` 正是 FM 分配失败的直接后果 ⇒ 同一启动**不可能**同时打印 `BGM IRQ install failed` 与 `AUD WARN: no memory for FM backend`。

真实的 ISR 构建抓取是 `logs/serial_demo-a2.log`（2026-10-22 17:43），其内容为：`AUD OPNA OK` → `FM: 15 patch families ready` → `BGM IRQ: probing INT 14h (IRQ12 (slave))` → `0204 -> 800050:0080` → `_dos_setvect(INT 14h) handler=46a5fd` → `programming Timer-B` → `unmask IRQ12 (slave) (imr 51 -> 41)` → `Timer-B installed (NB=200, ~124Hz, IRQ12 (slave))`，随后 `[ISR] ticks` 204→6999 单调递增。**中断链完全打通，FM 分配成功**。（该行 `~124Hz` 是按错误常量 129 印出来的期望值，实测 61.77 Hz——见 §5.1，实施时一并改。）

### 2.2 真正的线索藏在 `w=` 里

`devdocs/167` §三.3 给 `[ISR]` 行加了 `w=`（真实墙钟），本意就是「对比 `v` 与 `w` 判断 ISR 是否跟上真实时间」——但没人做这个对比，反而用「141 tick × 8.064 ms = 1136 ms」与**假设周期**自比，得出「相位精确」。**速率断言不可自证**：用假设周期验证按假设周期推进的实现，必然「精确」。

把首末两点拿来做这次对比，结论立刻显形。

## 三、根因一：Timer-B 周期常量取成了真值的一半

### 3.1 实测

`logs/serial_demo-a2.log` 的 `[ISR]` 首末采样：

```
[ISR] ticks=204  v=1636  w=0
[ISR] ticks=6999 v=56421 w=110000
```

| 量 | 值 | 推导 |
|---|---|---|
| Δticks | 6795 | 6999 − 204 |
| Δv（虚拟钟） | 54785 ms | 56421 − 1636 |
| Δw（墙钟） | 110000 ms | 110000 − 0 |
| 虚拟步进 | **8.0625 ms/tick** | 54785 / 6795（= 129 units ÷ 16，与 `core/plat/hal_irq.c:66` 的常量一致） |
| 真实步进 | **16.188 ms/tick** | 110000 / 6795（= 61.77 Hz） |
| **虚拟钟速率** | **49.8%** | 54785 / 110000 |

**关键**：16.188 ms 不是「模拟器的 2× bug」，而是真机 Timer-B 的正常周期（§3.2）——真值 16.154 ms，实测偏大 0.21%，落在墙钟 1 秒粒度的误差界内。

### 3.2 机理（两侧源码）

**NP2kai**（`sound/opntimer.c:59-68`）：`l = 288 × (256 − NB)`，随后按 CPU 模式乘 `1248/625` 或 `1536/625`、再乘 `pccore.multiple`；事件以 CPU 时钟计，而 `pccore.realclock = pccore.baseclock × pccore.multiple`（`pccore.c:326-328`）⇒ `multiple` 约掉。两种 baseclock 的换算式化简后**都是 1e-6**：

| 宿主 | 周期公式（化简后） | NB=200 实际周期 | 折算 units（1/16 ms） |
|---|---|---|---|
| 真机 86 板 OPNA（φM=7.9872 MHz） | `tB = 2304×(256−NB)/φM`（`docs/refdocs/F07_opn_timer_clock_reference.md` §1–§3） | **16.154 ms** | **258.5** |
| NP2kai（8 MHz 模式，baseclock `1996800`） | `288×(256−NB) µs` | **16.128 ms** | **258.0** |
| NP2kai（5 MHz 模式，baseclock `2457600`） | `288×(256−NB) µs`（同一闭式） | **16.128 ms** | **258.0** |

⇒ **NP2kai 与真机相差 −0.16%**（恰好是标称 8.0000 MHz 与实测晶振 7.9872 MHz 之差）；周期在 NP2kai 上**是常量**，与 CPU 模式、倍频无关。`hal_irq.c` 的 129 与之差 **一倍**。

**手册为什么写 1152**：OPN 的定时器按 **φM/2** 计数——`1152 个 φM/2 时钟 ≡ 2304 个 φM 时钟`。手册公式本身自洽（NB=255 时确实「等于」它自己写的 144µs 分辨率），错的是把它读成「φM 的个数」。论证与四实现逐行对照见 `docs/refdocs/F07_opn_timer_clock_reference.md` §2–§3。

### 3.3 一致性校验

- 实测 16.188 ms vs NP2kai 模型 16.128 ms ⇒ 差 **+0.37%**；vs 真机模型 16.154 ms ⇒ 差 **+0.21%**。墙钟 `w` 只有 1 秒粒度（`w % 1000` 恒为 0），全窗口误差界约 ±0.9% ⇒ **三者相符**。
- 反向校验：若周期真是 8.06 ms，6795 tick 只需 54.8 s，而墙钟走了 110 s——**观测本身就把「8 ms」排除掉了一倍**（初稿把这个矛盾读成了模拟器故障）。

## 四、连带影响

### 4.1 半速清单（虚拟时钟是所有时基的公共上游）

**归因**：清单里所有「半速」都来自 §三 的**单一常量错误**（`BGM_TIMER_B_UNITS` 取半），不是模拟器缺陷，也不是各处独立 bug。常量改对后全部同时修复。

| 受影响项 | 位置 | 现象 |
|---|---|---|
| BGM 事件调度 | `core/engine/audio.c:87,385`（`g_bgm.wall0`）、`core/lib/fmseq.c` | 音乐**半速** |
| SE / voice 的 FIFO 投料 | `core/engine/audio.c:674-684` | 每 tick 喂 22050×8.0625/1000 ≈ **178** 字节，而 DAC 每 16.188 ms 需 ≈ **357** 字节 ⇒ 欠喂 ~50% ⇒ FIFO 欠载 ⇒ 断续 |
| 打字机揭示 | `core/engine/nb_dialog.c:258` | 半速 |
| 动画时基 | `core/engine/nb_anim.c:568` | 半速 |

（`chime`/`ding` 的采样率为 22.05 kHz（`assets/demo-a2/se/*.pcm` 头 `rate_code=2`），`hi` 为 11.025 kHz（`rate_code=4`）。）

### 4.2 根因二：PCM 泵的时间源取自虚拟时钟（`devdocs/167` 引入）

`hal_pcm_tick(uint32_t elapsed_ms)`（`core/plat/hal_audio.c:176`）的 `elapsed_ms` 由 `audio_tick_isr()` 用 `hal_wallclock_smooth_ms()` 算出（`core/engine/audio.c:674-684`）⇒ 取的是**虚拟时钟**而非真实时间。

- 协作式路径的虚拟钟是自测量时钟，速率被钳制在 `target×4/5 … target×5/4`（`core/lib/vclock.h:115-116`），实测 `logs/probe_run.out` 尾段 Δv/Δw ≈ 4646/5000 = 93%；
- ⇒ SE/voice 的播放速度与音高随虚拟钟漂移。此前实现是「一直推到 FIFO 满」⇒ 硬件速率精确。

这条**与 ISR 无关**，默认（协作）构建同样中招 ⇒ 属于本轮 `devdocs/167` 引入的回归。

## 五、已拍板的修复方案（本轮只订正文档，实施在下一轮）

### 5.1 Timer-B 周期常量：单一值 258 units

**决定**：常量取 **258 units（16.125 ms/tick）**，一个值覆盖真机与 NP2kai，**不做编译期分档**（初稿的「NP2kai 258 / 真机 129」方案作废，理由见文首「结论订正」）。

| 取值 | 每 tick | 对 NP2kai（16.128 ms） | 对真机（16.154 ms） |
|---|---|---|---|
| 129（现状） | 8.0625 ms | **−50.0%** | **−50.1%** |
| **258（采用）** | 16.1250 ms | −0.02% | **−0.18%** |
| 259 | 16.1875 ms | +0.37% | +0.21% |

- 258 对两个宿主的偏差都在 0.2% 以内（约 3 音分，听不出）；259 反而更差。「取更接近真机的 258.46」需要小数累加器，收益不抵复杂度（BGM 是 tick 调度、误差只影响速度不累积漂移）。
- 注释必须写清三件事：**每步 2304 主时钟**、86 板 φM=**7.9872 MHz**（`docs/refdocs/F07_opn_timer_clock_reference.md` §1/§3）、以及「手册的 1152 是 φM/2 口径」——否则下一个读者会再次按手册算出 129。
- **不选运行时自校准的理由不变**：`hal_wallclock_ms()` 在 NP2kai 上只有 **1 秒粒度**（`w % 1000` 恒为 0），用它标定 tick 周期需要数十秒窗口才能把误差压到 1% 级；而两个宿主的真值只差 0.16%，一个常量即可。运行时自校准保留为备选（§七）。
- 同时要改的两处展示：`hal_irq.c` 的启动日志 `~124Hz`（8.06 ms 的倒数）应为 **~61.9Hz**；`devdocs/165` 的 ERRATA 已指向本文件，无需再改。

### 5.2 PCM 投料与虚拟时钟解耦

- **协作路径**：`elapsed_ms` 改取**真实墙钟** `hal_wallclock_ms()` 的差值 ⇒ SE/voice 速率回到硬件精确；
- **ISR 路径**：`elapsed_ms` 取**硬件 tick 步长**（= §5.1 选定常量换算的毫秒数）⇒ ISR 内不碰 DOS（保持 165 的 B1 约束），且周期改对后即等于真实时间；
- 接口形态：`audio_tick_isr()` 显式接收投料时长（而非自己读时钟），两条路径各自提供 ⇒ 时基来源在调用点即一目了然。

### 5.3 验证判据

1. **速率**：`[ISR]` 行的 `v/w` 应落在 **1.0 ±2%**（现状 49.8%）；按 §3.1 的数据换算，修正常量后预期 `Δv ≈ 6795×258/16 ≈ 109,569 ms` 对 `Δw = 110,000 ms` ⇒ **99.6%**；
2. **单位自洽**：虚拟步进 = **258 ÷ 16 = 16.125 ms/tick**（真机 16.154 / NP2kai 16.128 都在 −0.2% 内）；
3. **听感**：BGM 恢复正常速率；SE/voice 不再断续、速度与协作构建一致；
4. **构建纪律**：`export EXTRA_DEFS=-DNAIZ_BGM_IRQ=1` 必须贯穿 `makegame.sh build` + `make` **全管线**（`build` 会重跑 `compile_engine()`），结束后用 `strings` 确认部署树与 `core/engine.exe` 一致且不含 ISR 符号（c79/c81 教训；`tools/tests/test_engine_deploy_consistency.py` 已守机制）。

## 六、防复发

- **守卫点（下一轮实施时落地）**：把「`hal_irq.c` 的周期常量 == 258」与「该常量在源码注释里带 2304 clk / 7.9872 MHz 的宿主推导」做成 pytest 断言，防止常量被改回手册口径（129）或与注释脱钩；并把 165 的 ERRATA 块、167 的「§五 已重写且不含过期日志」做成守卫，防止订正被静默删除。
- **文档纪律**：`devdocs/167` 的 §五/§六 已按实机日志重写，**不得**再引用 `logs/serial_demo-a2_trace.log`（2026-09-29）作为任何 10 月构建的证据。
- **方法纪律**：任何「速率/时序正确」的断言必须有一个**独立于被测实现**的对照量（本例即 `w=`）；用被测实现的假设值自比不构成验证。**本轮订正就是这条规则的反面教材**：初稿用「141 tick × 8.064 ms ≈ 1136 ms」自证「相位精确」，而 8.064 ms 本身就是错的假设——两个错误互相抵消，误差显示为 0。

## 七、遗留与备选

1. **真机周期无示波器实测**：真机值 16.154 ms 由「四份实现 + PMD/MUCOM88 常数 + 86 板晶振 7.9872 MHz + TmEE 实机读数」交叉推出（`docs/refdocs/F07_opn_timer_clock_reference.md` §2–§4），属**间接强证据**（TmEE 是听感/计数级，不是波形级），缺一条直接时序测量。若日后在真实 PC-98 上跑 ISR 构建，判据仍是 `[ISR]` 的 `v/w ≈ 1.0`（±2%）；落在该带内即认为 258 正确，若系统性偏离再回来看 `F07` §6。
2. **运行时自校准备选**：若最终需要同时支持多个模拟器/真机而不分档，可改为「长窗口测量 + 小数累加器」的自动标定（墙钟粒度决定收敛速度），届时以本文件 §3 的模型为初值。
3. **方案 B（vclock 有界相位追赶）** 继续作为协作路径的回退方案保留；本文件不改变它。
4. **MIDI 后端 ISR 化**仍未覆盖（本环境无 MPU-401），不在本文范围。
