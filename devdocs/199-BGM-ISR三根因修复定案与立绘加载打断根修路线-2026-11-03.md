## 一、结论摘要（先看这一节）

1. **BGM 无声已修复并经用户实机确认**（"音乐基本上是播放正常了"）。三个根因全部实证，修复集中于 [hal_irq.c](../core/plat/hal_irq.c) 与 [hal_audio.c](../core/plat/hal_audio.c)，详见 §二。
2. **197 §A1 重开 ISR 的前提有一处缺口**：它论证的是 P7 修复挡住了 *hook 自己发起的 DOS 调用反射*，但没有覆盖 *Timer-B 硬件 IRQ 本身的 DPMI 反射*。ISR 重开后，解码调用链（含泵窗口）每张图仍会吃到 20–65 次反射——这正是"立绘/文字加载被打断"最可疑的机制（§三）。
3. 两个残留问题：**A. 立绘/文字加载打断**（已取证，改判为加载期音频攒批，见 §五 A/A-补 C4）；**B. 节拍速度可能不准**（用户弱证据，未量化）。
4. 根修路线（§五）最终状态：**A 取证**（完成）→ **E 消除加载期音频泵空窗**（完成，由 199E 实施，maxu 6708→1290）→ **B 解码期 PIC 屏蔽**（**关闭**：实测整段屏蔽会造成约 1 秒音频空窗，不能按现文实施）→ **C 解码状态迁出栈**（**关闭**：触发条件未出现）→ **D ISR 瘦身**（未实施，转入后续候选）。
5. 代码里仍有 198/199 诊断残留（`[ISR-DRAIN]`/`[MAG-ISR]` 日志 + 计数器 + 未使用变量），发布前必须清理（§七）；清理前需先补 `NAIZ_BGM_IRQ=0` 的 decode stub，否则该构建链接失败。
6. devdoc 198 的验收惯例要修正：**"3 次通过"不构成结论**（197 §A1 即栽在此），ISR 相关改动一律按 I04 §七 的布局矩阵口径验收。

## 二、devdoc 198 回填：BGM ISR 无声的三根因与三层修复

> 背景：194 曾因 mag_decode 间歇失败直接禁用 DOS/32A 的 ISR（`hal_bgm_irq_init()` 早退）；197 §A1 认为可安全重开；重开后用户反馈"还是没有"（无声）。198 定位并修复了三个独立根因。

### 2.1 根因清单（全部实证）

| # | 根因 | 机制 | 证据 |
|---|---|---|---|
| R1 | **init 顺序颠倒** | Timer-B 在 hook 向量安装 + PIC unmask **之前**被编程启动 → NP2kai 侧可能在 hook 前就 overflow，留下 sticky 状态、首个 ack 与计数错位 | 修复前 produced 停在 11094；调整顺序后开始累加 |
| R2 | **`g_irq_active/probing/line` 缺 `volatile`** | Watcom 把三个全局缓存进寄存器，handler 内 `if (g_irq_active)` 分支永不执行（`g_isr_ticks++` 无条件执行，所以表面"ISR 在工作"而 units 恒 0） | 加 `volatile`（[hal_irq.c L127-129](../core/plat/hal_irq.c#L127-L129)）后 produced 立即开始累加 |
| R3 | **FM 端口对 race → Timer-B 永久死亡（最致命）** | `outb($188, addr)` 与 `outb($18A, val)` 之间被 Timer-B ISR 插入，handler 内的 `$188=0x27` 覆盖地址锁存 → 主线程的 `val` 落到 `$27`；NP2kai [opna_settimer](../../../tmp/np2_opntimer.c) 对 D1=0 执行 `nevent_reset(FMTIMERB)`——**IRQ 唯一来源被永久删除**，ISR 再也不会触发来修自己 | 每次运行 produced/total_hits 在 171～2418 之间随机冻结，之后永不变 |

R3 的完整链路（2026-11-02 定案）：

```
主线程 hal_fm_write_reg: outb($188, X) ──► ISR 插入：outb($188, 0x27) ──► IRET
                                          主线程继续: outb($18A, val)
NP2kai 收到: $27 ← val；若 val 的 D1=0（多数 FM 寄存器值都满足）
  → opna_settimer() → nevent_reset(FMTIMERB) → Timer-B event 永久移除
  → IRQ 永不再来 → 无声，且任何 ISR 侧自愈都无效（自愈也在 ISR 里）
```

### 2.2 三层修复

| 层 | 位置 | 内容 | 作用 |
|---|---|---|---|
| L1 | [hal_audio.c `hal_fm_write_reg()`](../core/plat/hal_audio.c#L285-L308) | 端口对写入用 `_disable()/_enable()` 包裹（ISR 内调用时跳过） | 消除 race 的产生条件；单独使用只把冻结点从 171 推到 2418 |
| L2 | [hal_irq.c handler](../core/plat/hal_irq.c#L259-L323) | 每次 ack 重写 `$27 = RESET\|ENABLE\|LOAD`（并重写 `$29` 保 EN_TB） | ISR 侧自愈；单独使用无效（R3 一旦发生 ISR 就不再来） |
| L3 | [hal_irq.c `hal_bgm_irq_take_pending_units()`](../core/plat/hal_irq.c#L590-L649) | **主线程每次 drain 在 cli 内重写 `$27`（D1=1）** | 决定性一层：即使 NP2kai 侧 Timer-B event 已被 `nevent_reset` 杀掉，`$27` 重写会走 `opna_settimer()` 的 D1=1 分支把 event 重新挂上——自愈与被杀谁在前面都能翻盘 |

另有两处配套修复：init 顺序改为 **hook+unmask 在前、编程 Timer-B 在后**（[hal_irq.c L554-570](../core/plat/hal_irq.c#L554-L570)）；probe 成功后 full re-arm（重写 `$27` + re-unmask PIC）。

4400+ ticks 连续不停；`not_ours=0` 说明端口对 race 无残留（L1 有效）。

## 三、残留问题 A：立绘/文字加载被打断（已取证：改判为加载期音频攒批，见 §五 A/A-补）

### 3.1 现象

用户实机反馈（2026-11-03）：**"立绘文字加载打断的问题依然存在"**。未提供串口日志，现象未分级。

两种候选签名（取证前不要预设）：

| 签名 | 表现 | 判据 | 对应病史 |
|---|---|---|---|
| S-a：**解码被改写** | 立绘/背景加载失败或花屏，串口出现 `mag_decode failed`（`code=11`、`at≈255998` 族、`short cnt` 记录） | `cat log \| tr '\r' '\n' \| grep "mag_decode failed"` | 192/194/I04（P7 族） |
| S-b：**解码停顿** | 加载瞬间画面/打字机/音乐停 1-2 帧，但最终显示正确；串口无 `mag_decode failed` | `[VC]`/`[AP]` 时间线在 image_load 处出现 ~1s 的 gap（原估 30–50ms 已被实测推翻） | 177（同步解码占住主线程） |

### 3.2 为什么 197 §A1 的前提有缺口（强推断）

197 §A1 的重开依据是：

> "ISR 进来时 `IF=0`，所以反射不会落在热循环上——理论上 P7 的修复应该已经顺带解除了 ISR 路径风险。"

但 I04 §一·补 已实证的机制是：**DOS/32A 把 `cli` 虚拟化成 VIF，硬件 IRQ 并未真正停止**；被推迟的反射会在泵的深调用链结束后落到解码栈帧上。P7 的 `_enable(); hook(); _disable();` 只保证 *hook 自己发起的 `INT 21h` 反射* 落在 hook 自己的帧内；它对 *Timer-B 硬件 IRQ 的反射* 没有任何约束力——后者由 DPMI 在 IRQ 交付时刻决定落点。

数量级核算（原估 30-50ms 已被实测推翻）：ISR 62Hz（周期 16.15ms），640×400 一张图实测 **~1000ms**，中等图 18–21 个 → **每张图有 20–65 次 Timer-B IRQ 落进解码调用链**。每个 IRQ 都是一次落到 32A 应用栈的反射。198 修复后的 handler 还比较重（§3.3），窗口更大。

若 S-a 成立，则历史签名（`code=11` 族）应原样回归；若 S-b 成立，则属于 177 遗留的同步解码阻塞，与 ISR 无关，只是被用户同时感知。**第 0 步取证（§五 A）负责把两者分开。**

> 实测（§五 A-实测结果）已给出关键一半：`in_cli` 恒 0（cli 内不会交付），每张图 20–65 次 IRQ 全部落在泵窗口；3 次运行 0 失败。S-a 的"cli 内交付"前提不成立，剩余需用用户实机日志区分"泵窗口反射致改写"与"1 秒同步解码停顿"。

### 3.3 ISR 现状偏重（对照 194 §F3 的设想）

194 §F3 设想的 handler 是"读状态 → 计数 → 清 Timer-B → EOI，不调用任何 C 函数"。当前 handler（[hal_irq.c L259-323](../core/plat/hal_irq.c#L259-L323)）实际做了：

- 调用 C 函数 `hal_wallclock_fixed_advance(258)`（纯计算、全局量，但仍是 ISR 内的 C 调用）；
- 额外重写 `$29`（第二次端口对）；
- 诊断计数器三处（另有 §A 的 `g_decode_depth/g_isr_in_decode/g_isr_in_cli` 判读）。

反射窗口 = 整个 handler 执行期。窗口越大，反射与主线程关键区重叠的概率越高。瘦身后窗口可缩小一个量级。

## 四、残留问题 B：节拍速度可能不准（弱证据，未量化）

用户原话"虽然速度可能有些不准确"。两个候选机制（未验证）：

| 候选 | 机制 | 与 S-b 的关系 |
|---|---|---|
| B1 | **drain 突发**：解码停顿期间 units 攒批，解完后 `audio_tick_isr_pending()` 按 [audio.c L793-807](../core/engine/audio.c#L793-L807) 的 split-drain 补发，事件以突发节奏落到 OPNA，听感为"赶拍后回正" | 与 S-b 同源：解码阻塞的时间线抖动（**"每 drain 重写 `$27` 会造 tick"的放大器假设已被 §A C3 否掉**） |
| B2 | **单位换算舍入**：Timer-B 实际周期 16.154ms ≈ 258.5 units，`BGM_TIMER_B_UNITS=258` 每 tick 少 0.5 unit（~0.2%），split-drain 的 `units/16` 整毫秒截断进一步离散化 | 恒定小偏差，单独解释不了可感知的"不准" |

判据：若 B1，症状应与解码活动强相关（加载时赶拍、静止时准）；若 B2，症状恒定且方向单一。**在 A 取证时顺带记录 `[ISR] ticks v w` 与 `[AP]` 时间线即可区分，无需单独实验。**

## 五、根修路线（按顺序执行，每步独立验收）

### A. 取证（第 0 步，先做；原设计零行为变更，实际插桩有两个已知缺陷，见 §七）

1. `mag_decode` 入口置 `g_decode_depth=1`、出口清 0（`volatile int`，hal 层 extern）；
2. ISR 入口检查：`if (g_decode_depth) g_isr_in_decode++;`；
3. 串口日志周期性打印 `in_decode` 累计值。

> 实际实现改为 begin/end API（`hal_bgm_irq_decode_begin/cli_end/cli_begin/end`），见下方 A-实测；原因是要把泵窗口 `_enable()/hook()/_disable()` 单独区分出来。

一次构建同时回答三件事：IRQ 是否真的落在解码区内（S-a 成立的前提）、每张图撞几次、与 `mag_decode failed` 出现是否相关。**不做这一步，后面三步都是猜。**

#### A-实测结果（2026-11-03，openpack，`demo-a2`，可用三次运行 `mag199-1/2/3`）

实现：`hal_bgm_irq_decode_begin/cli_end/cli_begin/end`（[hal_irq.c](../core/plat/hal_irq.c)），mag.c 两处热循环插桩并记录解码耗时；`begin` 后置 `in_cli` 标志，泵窗口前清、后置，出口 `_enable()` 前先清。日志签名 `[MAG-ISR] decode saw N IRQ (in cli=M) in T ms`。

| 图像规模 | IRQ 数/解码 | `in cli` | 实测耗时 |
|---|---|---|---|
| 640×400 背景（stride 62.5） | 61–65 | **0** | 1000 ms |
| 中等/小图 | 18–21 | **0** | <1000 ms（计数粒度为 1s） |
| 三次运行（`mag199-1/2/3`，`in_decode` / `in_cli`） | 371 / 452 / 254，`in_cli` 均 **0**（合计 1077） | 0 | — |

> 数据口径说明：`clean199-2/3*.log` 为 **0 字节**（串口捕获失败），可用的三次运行是 `test/mag199-1.log`、`mag199-2.log`、`mag199-3.log`。原表"三次累计 452"实为单次值（`mag199-2` / `clean199-1`），已按实际日志更正。§A-补 的 001 场景数据见 `test/scene001.log`。

`mag_decode failed`：**0 次**；`produced` 持续增长（BGM 正常）；`not_ours` 各次 0–3（共享线噪声）。

三条结论：

1. **C1（推翻 §3.2 的一半）**：`in_cli` 恒 0 —— DOS/32A 的 `cli` 对 Timer-B **确实是真屏蔽**，IRQ 不会在 `IF=0` 期间被交付。I04 里"硬件 IRQ 打断 cli 热循环"的正确解读是：**被延迟到下一个 `_enable()` 才交付**，而不是在 cli 内交付。197 §A1 关于"IF=0 挡住落点"的前提成立。
2. **C2（暴露面仍在）**：640×400 一张图解码耗 **约 1 秒**（NP2kai 实测），期间按 16.15ms 周期交付 **约 62 个** Timer-B IRQ；中等图 18–21 个。全部落在 `_enable(); hook(); _disable();` 的泵窗口——即每次图上仍有 20–65 次 DPMI 反射落在 `mag_decode` 调用链上。P7 把落点搬进了泵帧，但解码帧仍在其下方存活，**32A 的反射是否越过泵帧写回解码帧，仍未被证伪**（但本轮 0 失败，说明概率远低于历史 7.5%）。
3. **C3（否掉 §四 B1 的放大器假设）**：`hits ≈ elapsed/16.15ms` 严格吻合——`$27` 自愈**不会**每次 drain 造 tick。为验证此项做过单因子构建（`NAIZ_199_SELFHEAL_ON_TICK=1`，只在 `units != 0` 时重写 `$27`）：解码窗口 IRQ 归零，但 `produced` 在 300 ticks（~5s）后冻结 —— 再次确认 L3 是 Timer-B 存活的必要条件，且"每 drain 造 tick"假设不成立。

**推论**：本轮 0 次 `mag_decode failed`，说明 S-a（解码被改写）在 3 次运行里未复现；用户实机感知的"打断"更可能是 **S-b：单张 640×400 解码占住主线程约 1 秒**（177 遗留的同步解码阻塞），ISR 只是旁观者。要定案必须拿到用户实机的串口日志：若日志同样 0 失败、但解码耗时 1s，则问题是性能而非中断。

#### A-补：001 场景实测（音频攒批，2026-11-03）

用户后续确认"打断"的实际表现是 **"音乐在加载时停顿或跳拍"**（无立绘花屏/加载失败），问题被改判为音频侧。用 `BGM_IDLE` 直接进 001 场景复跑：

```
构建: EXTRA_DEFS="-DBGM_IDLE=1 -DBGM_IDLE_SCENE=nbook001"（自动进 nbook001.nb 并停在第一页）
```

7 次解码窗口（001 进场加载 bg + 立绘）：

```
[MAG-ISR] decode saw 62 IRQ (in cli=0) in 2000 ms banked=0  maxu=0
[MAG-ISR] decode saw 19 IRQ (in cli=0) in 0 ms    banked=1  maxu=2322
[MAG-ISR] decode saw 20 IRQ (in cli=0) in 1000 ms banked=1  maxu=2322
[MAG-ISR] decode saw 19 IRQ (in cli=0) in 1000 ms banked=3  maxu=6708
[MAG-ISR] decode saw 21 IRQ (in cli=0) in 0 ms    banked=5  maxu=6708
[MAG-ISR] decode saw 19 IRQ (in cli=0) in 0 ms    banked=6  maxu=6708
[MAG-ISR] decode saw 19 IRQ (in cli=0) in 0 ms    banked=7  maxu=6708
```

`banked` = 单次 drain 拿到超过一个周期（258 units）的次数；`maxu` = 单次最大 units。关键数：

> **maxu = 6708 units = 6708 / 258 ≈ 26 个 Timer-B 周期 ≈ 420ms。**

即加载期存在一段 **约 420ms 完全没有 drain** 的空窗，随后 `audio_tick_isr_pending()` 把 26 个周期一次性喂给 `audio_tick_isr()`（split-drain 逐周期循环，FM 写入在同一调用里瞬间打完）。听感就是：**先停 420ms（没有事件推进），再一次性补 26 拍（跳拍）**。用户描述完全吻合。

结论 **C4**：加载时音乐停顿/跳拍的直接原因是 **加载期音频泵停摆 → units 攒批 → split-drain 突发补发**；不是 ISR 丢 tick（`not_ours=0` 全程），也不是 `$27` 自愈（C3 已否）。`in_cli` 仍恒 0，图像侧无失败。

修复候选（按代价排序）：

1. **消除 420ms 空窗**：把 `audio_tick_isr_pending()`（或 `frame_decode_pump()`）插进加载期所有长循环/长阻塞点（preload 任务、scene 解析、`[PRELOAD] jobs=7` 的连续读盘）。只要空窗降到 <2 个周期，听感问题即消失。先用一次带时间戳的桩定位 420ms 花在哪一段。
2. **split-drain 加上限**：单次最多补 2 个周期，剩余只推进 seq 时钟、不逐周期发事件（需要 fmseq 提供"跳到时间 T、丢弃过期事件"的入口）。这是不依赖定位的兜底，可把跳拍压到不可闻。
3. 若空窗来自某一次具体阻塞（如上例的 7 个 preload job），可在该循环里单独插泵。

> 注意：C4 与 §四 B1 的关系 —— **"攒批补发"成立**（B1 的主体）；C3 否掉的是"每次 drain 重写 `$27` 会额外造 tick"这一放大器，两者不矛盾。

### B. 止血：解码期在 PIC 上屏蔽 IRQ12（待重设计，勿按现文实施）

§A 的 C1 已证 `cli` 对 Timer-B 是真屏蔽；但解码期仍有 20–65 次 IRQ 落在泵窗口，B 的原意是把这段反射**全部清零**。**若实机日志确认 0 次 `mag_decode failed`，则 B 不是必要的**，优先级应让给 E/C/性能。

> **修正（2026-11-03 核对）**：本节原按"解码只占 30–50ms"估算，已被 §A-实测推翻（640×400 一张图实际约 1 秒）。整段屏蔽 IRQ12 会让 ISR 在约 1 秒内不产 units，`audio_tick_isr_pending()` 无料可泵——与 §五 A-补 C4 的 420ms 空窗同源，听感只会更差。原写的"unmask 后补一次 `hal_wallclock_smooth_advance()`"也不成立：它只推进虚拟钟、不补 units，`audio_tick_isr_pending()` 会看到 `now` 前跳约 1 秒而 units 仅 258，直接把 fmseq 事件跳过（跳拍），不是"追赶"。

若将来仍要做，必须满足全部三条：

- 仅在实机日志确认 `mag_decode failed` 复现时启用（否则不做）；
- 屏蔽前后记录真实耗时，unmask 时把该时长按 258 units / 16.15ms 折算补进 `g_irq_units_total`，而不是只补 smooth 时钟；
- 禁止整段屏蔽：优先只屏蔽短窗口，并与 §五 E 的插泵配合。

其余 PIC 细节仍有效：IRQ12 = slave IRQ4 → `PIC1_IMR` (0x0A) bit4；probe 期间（未定 owner）mask/unmask 退化为空操作；`mag_decode_into` 同步改。**mask 期间 ISR 不来，198 的 L3 自愈（主线程重写 `$27`）不受影响，无 Timer-B 死亡风险。**

### C. 根治：解码热状态迁出栈（194 §F1，视 B 的听感决定做不做）（**2026-11-03 关闭**）

> 关闭依据：199E 全程 0 次 `mag_decode failed`，B 路径（反射损毁解码状态）无实证；E 已把空窗压至实机投影 ≤2 拍。若日后实机出现解码损毁证据，本节可按原方案重启。

`fa_bit/fa_bits/fb_pos/col_pos/out_pos/act_idx/action` 仍是栈上局部量（[mag.c L306-314](../core/lib/mag.c#L306-L314)）。把它们连同 canary 放进一个 `malloc` 的 `MagDecodeCtx`，反射即使真落下来也改不坏解码状态。C 落地后 B 可以撤掉，BGM 完全无解码期断点。

**硬约束（194 S1 的教训）**：守卫上下文一律 `malloc`，**不得新增文件级静态数据对象**——DOS/32A 报 fatal 4005（unrecognized fixup）。

### D. ISR 瘦身（194 §F3，可与 B/C 并行或其后）

handler 收缩为：读状态 → `volatile` 计数 → 清 Timer-B（`$27` 一次端口对）→ EOI。`hal_wallclock_fixed_advance` 挪进 `take_pending_units` 的主线程路径（该函数本来就有 `$27` 自愈，可合并）；`$29` 重写保留在主线程侧。反射窗口缩一个量级，对 S-a 直接减害。

### E. 消除加载期音频泵空窗（当前最高优先，先于 B）

§A-补 C4 已把用户感知的"加载时停顿/跳拍"定位为：加载期没有 drain → units 攒批（实测 `maxu=6708` ≈ 26 个 Timer-B 周期 ≈ 420ms）→ split-drain 一次性补发。B 的整段屏蔽只会把空窗从 420ms 放大到约 1 秒（见 §五 B 修正），因此 E 先于 B。

**目标**：单次 drain 的 units ≤ 2 个 Timer-B 周期（≤516 units / ≈32ms），且加载期 `banked` 显著下降。

**步骤**：

1. **定位空窗（零行为变更）**：在 scene 解析、`[PRELOAD] jobs=7` 的连续读盘、`nb_load` 行处理、首次立绘/背景解码前后打时间戳，找出单段 >32ms 的阻塞。
2. **在长阻塞点插泵**：
   - ISR 模式：`audio_tick_isr_pending()`（主栈，安全）；
   - cooperative 模式：`audio_tick()`；**不要**用 `frame_decode_pump()`，它带 anim/reveal 语义且会重复推进；
   - 若位于 `mag_decode` 的 cli 区内，必须沿用 P7 规则 `_enable(); pump(); _disable();`，禁止在 IF=0 内直接调用。
3. **兜底（不依赖定位）**：split-drain 加上限——单次最多补 2 个周期，其余只推进 seq 时钟、丢弃过期事件；需要 fmseq 提供"跳到时间 T、丢弃过期事件"的入口。
4. 若空窗只来自某一具体循环（如上例的 7 个 preload job），优先在该循环单独插泵，避免全局改动。

**验收**：`BGM_IDLE=1` + `BGM_IDLE_SCENE=nbook001` 复跑，解码窗口日志 `maxu ≤ 516`、`banked` 不超过 1；实机确认"加载时不再停顿/跳拍"；再按 §六 布局矩阵回归。
