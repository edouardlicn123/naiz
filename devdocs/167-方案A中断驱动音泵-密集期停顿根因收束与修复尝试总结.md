> **状态**: 进行中（根因已定位，待实施）  
> **日期**: 2026-10-22（当日修订：§五/§六 依实机日志重写、撤回伪阻塞；新增 §二 第 4/5 条真根因）

> **目标**: 根治「加载立绘（char/cg）或弹出 question 菜单时 BGM 暂停/顿挫」问题

## 一、背景

方案 A（OPNA Timer-B 中断驱动音泵）已在实机验证中证明中断持续触发（`[ISR] ticks` 单调递增），但用户反馈在立绘变化/场景切换时的停顿依旧存在。需进一步收束真正的根因并尝试修复。

### 1.1 取证时序澄清（2026-10-22 修订）

「停顿依旧」这条反馈**不是在 ISR 构建下听到的**：

- ISR 构建的实机抓取是 `logs/serial_demo-a2.log`（2026-10-22 17:43），内含 `BGM IRQ: Timer-B installed` 与 `[ISR] ticks`；
- 而当前工作树里的引擎是**默认构建**——`core/engine.exe` 与 `games/demo-a2/engine.exe` 均为 2026-10-22 18:44 重编，`strings` 命中 `BGM IRQ` = 0，与 §四 的「恢复默认构建」一致。

⇒ 反馈测的是**协作式音泵**路径：立绘解码、场景重绘这类 CPU 密集期把音泵饿死，音乐原地停住，即 `devdocs/163` 的 M1 时间债。ISR 构建当时并未被听到。

即便 ISR 构建被听到，它当时**也不是对的**：`BGM_TIMER_B_UNITS` 取成了真值的一半（手册 1152 口径 vs 实现 2304 主时钟），虚拟时钟以真实时间 49.8% 的速率前进 ⇒ BGM 半速、SE/voice 欠喂断续、动画与打字机半速，主观听感同样接近「顿挫」（见 §二 第 4 条与 `devdocs/168`）。

## 二、根因定位

基于代码审计和实机串口取证，锁定以下根因（前 3 条为初稿所列，第 4/5 条为 2026-10-22 复核新增）：

| 编号 | 根因 | 分析 | 状态 |
|---|------|------|------|
| 1 | **嵌套锁破坏临界区** | `bgm_irq_lock()` 原为非重入的 `_disable()/_enable()`。`audio_bgm_start()` 外层持锁时调用 `fmseq_stop()`，后者通过 `fm_sink_write()` 再次进入 `bgm_irq_lock()/unlock()`，内层 `unlock()` 会在外层临界区中间提前开启中断，导致 ISR 在 `bgm_release()`、`g_bgm.*` 状态提交、`fmseq_events()` 之间抢占，可能破坏状态一致性或导致 OPNA 寄存器交错写入。 | 已修复（改为深度计数可重入，ISR 上下文直接返回） |
| 2 | **临界区过大（阻塞中断）** | `audio_bgm_start()` 原在持锁状态下执行 `farchive_read_alloc()`（读取整个 MIDI）和 `midi_parse()`，关中断长达数十毫秒，Timer-B 停摆导致 BGM 明显停顿。 | 已修复（移出锁，仅在状态提交段持锁） |
| 3 | **ISR 内 PCM 一次推送过多字节** | `hal_pcm_tick()` 原固定上限 2048 字节且每次推到 FIFO 满为止。SE 起始时可能在单次 ISR 内执行上千次 `outb()`，耗时数毫秒（远超 8ms Timer-B 周期），导致中断处理过长、主线程响应延迟、音频/画面停顿。 | 已修复（改为按经过毫秒数 `elapsed_ms` 折算推送量，单次上限降至 1024，`audio_tick_isr()` 计算 `pcm_dt` 并传入）；**但引入新回归，见第 5 条** |
| 4 | **Timer-B 周期常量取成了真值的一半（真根因）** | 代码按手册 1152 口径取 129 units（8.0625 ms/tick），而真机（2304 clk @7.9872 MHz）与 NP2kai（`288×(256−NB) µs`）都是 16.13–16.15 ms ⇒ 虚拟时钟以真实时间 **49.8%** 的速率前进，BGM/动画/打字机全线半速，SE/voice 欠喂断续。 | **未修复**（方案见 `devdocs/168` §五） |
| 5 | **PCM 泵的时间源取自虚拟时钟（167 引入）** | `hal_pcm_tick(elapsed_ms)` 的 `elapsed_ms` 由 `hal_wallclock_smooth_ms()` 得出，即虚拟时钟而非真实时间 ⇒ SE/voice 播放速度与音高继承虚拟钟的速率误差（钳制带 ±25%）。此前实现是「一直推到 FIFO 满」⇒ 硬件速率精确。 | **未修复**（方案见 `devdocs/168` §五） |

### 2.1 第 1 条：嵌套锁（已修复）

`core/engine/audio.c` 的 `bgm_irq_lock()/unlock()` 改为深度计数（`g_irq_lock_depth`，`audio.c:55-68`）：只有最外层才 `_disable()/_enable()`；`bgm_irq_is_in_isr()` 为真时直接返回，避免 ISR 内 `_enable()` 导致中断重入。临界区内的调用链（`audio_bgm_start()` → `fmseq_stop()` → `fm_sink_write()` → `bgm_irq_lock()`）由嵌套变平，OPNA 寄存器写入不再被 ISR 交错。

### 2.2 第 2 条：临界区过大（已修复）

`audio_bgm_start()` 移除开头的锁：所有早期校验与 `farchive_read_alloc()` + `midi_parse()` 在锁外执行，只有 `fmseq_stop()`、`bgm_release()`、`g_bgm.*` 状态赋值、`fmseq_events()`、`bgm_apply_volume()` 等状态提交在锁内。读 MIDI 期间中断保持开放，Timer-B 不再停摆。

### 2.3 第 3 条：PCM 推送量（已修复，评级订正）

修复方向正确（按经过时间折算推送量，避免一次塞满 FIFO），但初稿的机制描述被夸大：

- 2048 字节在 22.05 kHz 下 ≈ 93 ms 音频，量级确实不小；
- 但原实现每字节前先 `inb` 查 FIFO 满位，FIFO 满时循环自然停住，实际不会一口气写满 2KB；
- ⇒ 它**不是致顿主因**，真实代价更接近「单次 ISR 端口 I/O 偏多」。评级由「关键」下调为「次要」，主因见第 4 条。

### 2.4 第 4 条（真根因）：Timer-B 周期常量取成了真值的一半

**现象**：`logs/serial_demo-a2.log` 的 `[ISR]` 采样首末两点：

```
[ISR] ticks=204  v=1636  w=0
[ISR] ticks=6999 v=56421 w=110000
```

- Δticks = 6795，Δv = 54785 ms，Δw = 110000 ms；
- 虚拟步进 = 54785 / 6795 = **8.0625 ms/tick**（= `core/plat/hal_irq.c:66` 的 `BGM_TIMER_B_UNITS 129` ÷ 16，与常量一致）；
- 真实步进 = 110000 / 6795 = **16.188 ms/tick**；
- ⇒ 虚拟时钟速率 = 54785 / 110000 = **49.8%**。

**机理（NP2kai 源码）**：`sound/opntimer.c:59-68` `set_fmtimerbevent()`：

```c
l = 288 * (256 - opna->s.reg[0x26]);   /* :59  NB=200 -> 16128 */
if (pccore.cpumode & CPUMODE_8MHZ)    /* :60 */
    l = (l * 1248) / 625;              /* :62  -> 32204 */
else
    l = (l * 1536) / 625;              /* :66  -> 39636 */
l *= pccore.multiple;                  /* :68 */
```

事件以 CPU 周期计，而 `pccore.realclock = pccore.baseclock * pccore.multiple`（`pccore.c:326-328`）⇒ `multiple` 约掉：

| 宿主 | 周期公式（化简后） | NB=200 实际周期 | 折算 units(1/16 ms) |
|---|---|---|---|
| 真机 86 板 OPNA（φM=7.9872 MHz） | `tB = 2304×(256−NB)/φM` | **16.154 ms** | **258.5** |
| NP2kai 8 MHz 模式（baseclock `1996800`） | `288×(256−NB) µs` | **16.128 ms** | **258** |
| NP2kai 5 MHz 模式（baseclock `2457600`） | `288×(256−NB) µs`（同一闭式） | **16.128 ms** | **258** |

⇒ **NP2kai 与真机只差 −0.16%**（标称 8.0000 MHz vs 实测晶振 7.9872 MHz），模拟器是**忠实建模**；错的是 `hal_irq.c` 的 129（把手册 1152 当 φM 个数 ⇒ 半个周期）。实测 16.188 ms 与模型 16.128/16.154 ms 差 +0.37%/+0.21%，墙钟 `w` 只有 1 秒粒度（全窗口误差 ±0.9%）⇒ 相符。

> **⚠ 订正（2026-10-24）**：本段初稿写「NP2kai 的模型 = 真机的 2 倍」，并据 2.0/2.5 MHz 两档 baseclock 推出「周期随宿主不是常量」。实际 baseclock 是 **1996800/2457600**，两种模式的换算因子除以各自 baseclock 都恰好等于 1e-6 ⇒ 闭式恒为 `288×(256−NB) µs`，与 CPU 模式无关。真机 Timer-B 每步是 **2304** 主时钟（手册 1152 配 φM/2 时钟）。完整推导见 `docs/refdocs/F07_opn_timer_clock_reference.md`，事故记录见 `devdocs/168` 文首订正表。

**后果**：ISR 构建下整个虚拟时钟以 49.8% 速率前进，所有以虚拟钟为时基的量同时失准：

| 受影响项 | 位置 | 现象 |
|---|---|---|
| BGM 事件调度 | `core/engine/audio.c:87,385`（`g_bgm.wall0`）、`core/lib/fmseq.c` | 音乐**半速** |
| SE / voice 的 FIFO 投料 | `core/engine/audio.c:674-684` | 每 tick 只喂 22050×8.0625/1000 ≈ 178 字节，而 DAC 每 16.188 ms 需 ≈ 357 字节 ⇒ **欠喂 ~50%**，FIFO 欠载 ⇒ 断续 |
| 打字机揭示 | `core/engine/nb_dialog.c:258` | 半速 |
| 动画时基 | `core/engine/nb_anim.c:568` | 半速 |

**与 165「相位精确」说法的关系**：165 用「141 tick × 8.064 ms = 1136 ms」与**假设周期**自比，得出「相位精确」；`[ISR]` 行里的 `w=`（真实墙钟）正是为此准备的对照项，却从未被用来比。订正见 `devdocs/165` 头部 ERRATA 与 `devdocs/168`。

### 2.5 第 5 条（167 引入）：PCM 泵的时间源错了

`hal_pcm_tick(uint32_t elapsed_ms)`（`core/plat/hal_audio.c:176`）的 `elapsed_ms` 由 `audio_tick_isr()` 用 `hal_wallclock_smooth_ms()` 算出（`core/engine/audio.c:674-684`）⇒ 取的是**虚拟时钟**而非真实时间。

- 协作式路径下虚拟钟是自测量时钟，速率带 ±25% 钳制（`core/lib/vclock.h:115-116` 的 `VCLOCK_MAX_WINDOW_RATIO_NUM/DEN=5/4`），实测 `logs/probe_run.out` 尾段 Δv/Δw ≈ 4646/5000 = 93%；
- ⇒ SE/voice 的播放速度与音高随虚拟钟漂移。此前实现是「一直推到 FIFO 满」⇒ 硬件速率精确。

⇒ 修复方向：**PCM 投料必须由真实时间驱动**——协作路径用墙钟 `hal_wallclock_ms()`，ISR 路径用硬件 tick 步长（前提是先把周期常量改对）。

## 三、实施的修复

### 3.1 `core/engine/audio.c`
- **可重入锁**：将 `bgm_irq_lock/unlock` 从简单 `_disable/_enable()` 改为深度计数（`g_irq_lock_depth`），最外层开/关中断；在 `bgm_irq_is_in_isr()` 返回真时直接返回（避免 ISR 中 `_enable()` 导致重入）
- **缩小临界区**：`audio_bgm_start()` 移除开头的锁，所有早期校验和 `farchive_read_alloc()` + `midi_parse()` 在锁外执行，仅 `fmseq_stop()`、`bgm_release()`、`g_bgm.*` 状态赋值、`fmseq_events()`、`bgm_apply_volume()` 等状态提交在锁内
- **ISR 音频核心重构**：`audio_tick_isr()` 统一读取时钟，计算 `pcm_dt = now - last_pcm_ms`（首调用或跳变时钳制到 1000ms），调用 `hal_pcm_tick((uint32_t)pcm_dt)`；`audio_bgm_start/stop` 锁语义与 FM 路径配合

### 3.2 `core/plat/hal_audio.c`
- **时间驱动 PCM 泵**：新增采样率表 `g_pcm_rate_hz[8]`，`hal_pcm_tick(uint32_t elapsed_ms)` 按 `rate_hz * elapsed_ms / 1000` 计算推送量，最小 1 字节，单次上限 1024 字节，并限制不超过剩余样本长度
- **接口变更**：`hal_pcm_tick` 从无参改为 `uint32_t elapsed_ms`，需同步更新所有调用点

### 3.3 `core/engine/frame.c`
- **ISR 心跳增强**：`[ISR]` 日志从 `ticks=%lu v=%lu` 增加 `w=%lu`（真实墙钟），便于对比 `v`（虚拟时钟，由 ISR 固定步进）与 `w` 判断 ISR 是否跟上真实时间

### 3.4 `core/plat/hal.h`
- 更新 `hal_pcm_tick()` 文档说明，标注 `elapsed_ms` 用于按实时折算推送量，避免一次塞满 FIFO

### 3.5 本轮修复的边界（2026-10-22 修订）

§3.1–3.4 已落地且与代码一致；但它们**没有触及**：

- Timer-B 周期常量（`core/plat/hal_irq.c:66` 仍是 129）⇒ §二 第 4 条仍在；
- PCM 泵的时间源（仍是虚拟时钟）⇒ §二 第 5 条仍在。

两项修复方案与验证判据见 `devdocs/168` §五。

## 八、经验教训

- **锁重入性必须考虑调用链**：看似独立的模块（`fmseq_stop` 调用 `fm_sink_write`）在临界区内可能形成嵌套调用，需在设计锁时考虑整个调用树
- **临界区要极简**：I/O（文件读取）、解析等耗时操作绝不能在关中断下执行
- **ISR 耗时需量化**：固定字节数推送在高速采样率下会转化为大量端口 I/O，必须按时间折算
- **内存是第一道门槛**：在 DOS 实模式/保护模式环境下，额外的全局对象和分配可能触及内存上限，需纳入可行性验证
- **诊断信息要齐全**：同时记录 ISR 计数（`ticks`）、虚拟时钟（`v`）、真实墙钟（`w`）才能判断时序是否正常
