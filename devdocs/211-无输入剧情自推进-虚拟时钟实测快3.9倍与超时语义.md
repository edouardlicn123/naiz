## 一、现象

用户报告原文：

> 即使我不做任何操作，剧情依然会在长期停下来后推进，有时候还会切换到其他特殊场景。

两条：

1. **自推进**：停在对话/选项页，手离开键鼠，过一段时间剧情自己往下走。
2. **串场景**：偶尔直接跳进 `special.nb` 一类的特殊场景。

## 三、实证：虚拟时钟比真实时间快 3.9 倍

数据源：`logs/serial_demo-a2.log`（2026-11-13 16:26，即 0.4.032/0.4.033 期间的 `-os` 构建）。

三条探针同时存在：

- `[AP]`（`audio.c:850`）每秒一行：`v` = 虚拟时钟，`w` = `hal_wallclock_ms()`（DOS 真实时钟），`d = w − v`
- `[VC]`（`hal_clock.c:118`）每 64 次 advance 一行
- `[FPS]`（`render.c:284`）约每 10 秒一行

### 3.1 `d` 的轨迹（决定性）

| 真实经过 | v 虚拟 | w 真实 | d = w−v | 比值 |
|---:|---:|---:|---:|---:|
| 2 s | 0 | 2 000 | +2 000 | 0.00 |
| 4 s | 9 315 | 4 000 | −5 315 | **2.33** |
| 6 s | 25 504 | 6 000 | −19 504 | **4.25** |
| 10 s | 53 148 | 10 000 | −43 148 | **5.31** |
| 20 s | 102 360 | 20 000 | −82 360 | **5.12** |
| 32 s | 123 518 | 32 000 | −91 518 | **3.86** |

**启动 4 秒内虚拟时钟已领先 5 秒，全程平均约 3.9 倍速。**

### 3.2 `/16` 的错误口径（重要，别再犯）

`[FPS]` 打印的 `N fr / M ms` 里，`M` 是 `window_ms = Σ(now − last_ms)`，而 `now` 取自 **`hal_wallclock_smooth_ms()`**（`render.c:265`）。

**所以 `[FPS]` 的毫秒是虚拟时间，不是真实时间。** 拿它当真实时间会得出「帧率 28→77 pass/s 在涨」的错误结论。正确口径：

- `[FPS]` 合计 5 633 pass ／ 32 真实秒 = **176 pass/s 真实帧率**
- `[FPS]` 合计 120 185 虚拟 ms ／ 32 真实秒 = **3.76 倍虚拟推进**

## 四、后果：30 秒超时只等于真实 8 秒

`nb_interact.c:98`：

```c
deadline = hal_wallclock_smooth_ms() + UI_INTERACT_TIMEOUT_MS;   /* 30000 */
```

时钟快 3.9 倍 ⇒ 玩家感受到的超时 = `30000 / 3.9 ≈` **8 真实秒**。

超时后 `ui_interact()` 返回 `-1`（`nb_interact.c:104-107`），三个调用方都把它当「继续往下」：

| 命令 | 超时后行为 | 位置 |
|------|-----------|------|
| `question` | 不应用任何选项，继续往下 | `nb_question.c:133-134` |
| `jump` | 不跳标签，继续往下 | `nb_scene.c:254-255` |
| `jumpscene` | 留在本场景，继续往下 | `nb_scene.c:320-321` |

三处注释都写着 `/* timeout: continue after the jump line, like question */`——**这是有意设计**。它把「玩家没选」和「玩家选不了」压成同一个返回值。

于是：一个 `jump()` 选项块在真实 8 秒后被静默跳过，脚本落到 `jump` 行之下的下一条命令。玩家看到的就是「剧情自己往前走了」。

## 五、机制：**已破案（2026-11-16，`[VW]` 实机数据定案）**

> ⚠️ 本节前半部分记录的是调查过程与已排除的假说（保留作教训）。**早期断言「`vclock_advance()` 每秒只被调用一次」是错的，已作废。**
> **最终结论见 §5.4。**

### 5.1 已用 `tools/tests/test_vclock.py` 实测排除

把 `core/lib/vclock.c` 编成宿主 .so，直接驱动，穷举调用模式：

| 调用率 | delta 形态 | 30 秒后的结果 | 结论 |
|---|---|---|---|
| 1 次/秒 | 均匀 | 虚拟 1.16 s（**0.04×**） | 变慢，非变快 |
| 2 次/秒 | 均匀 | 0.19× | 变慢 |
| 10 次/秒 | 均匀 | 0.98× | 正确 |
| 25 次/秒 | 均匀 | 1.00× | 正确 |
| 60 次/秒 | 均匀 | 1.04× | 正确 |
| 500 次/秒 | 均匀 | 1.63× | 偏快但到不了 3.9× |
| 176 次/秒 | 秒级量化 | **1.19×** | 正确 |
| 176 次/秒 | 冻结 3–6 s 后跳 | 1.05–1.14× | 正确 |
| ISR + 协作泵同时 | — | 2.29× | 偏快，但 ISR 实测未运行 |

**没有任何单一调用模式能复现 3.9×。** 也就是说：现有 `vclock.c` 在正常调用下是收敛正确的（这与已有的 16 条测试一致）。

### 5.2 实机 `step` 序列与任何模型都对不上

实机 `step`（1/16 ms 单位）：`551, 524, 498, 473, 450, …, 200`，单调下降，每 4 条记录（256 pass）降约 4.5%。

- 176 pass/s 的正确 `step` 应是 `1000/176 = 5.68 ms = 91 units`
- 实机从 551（= 34.4 ms/pass，即 6.05 倍）一路下滑，**30 秒都没到达 91**
- 而 `VCLOCK_SLEW_UNITS = 8` 在 176 pass/s 下只需 **0.4 秒**就能从 640 走到 91

实测耗时差了约 75 倍。这无法用「调用了多少次」解释——它说明**窗口极少关闭**，或 **`hal_wallclock_ms()` 的返回不是在单调增长**。

### 5.3 `[VW]` 窗口诊断：已实现（含一次失败经历）

**目标**：在**每个测量窗口关闭时**打出 `passes / accum / raw_want / want / target / step`，用来区分三种互斥解释——窗口里塞了太多 pass、`hal_wallclock_ms()` 没前进、或钳制方向搞反了。

**第一次尝试是死代码（务必记住这个坑）**

最初的写法是在 `hal_clock.c` 里 `#define VCLOCK_TRACE_WINDOW(...)`，在 `vclock.c` 里引用它。编译**零警告**、链接成功、跑起来**一行 `[VW]` 都没有**。

原因：`core/Makefile:79` 是 `LIB_SRCS = $(wildcard lib/*.c)`，`vclock.c` **被单独编译成 `build/vclock.o`**。宏定义在 `hal_clock.c` 这个翻译单元里，`vclock.c` 永远看不到它，于是 `#ifndef` 分支悄悄退化成 `((void)0)`。

> 教训：**跨翻译单元的埋点不能用宏**。它不会报错，只会沉默。任何"加了诊断但没输出"的情况，第一件事就是确认这段代码到底在不在同一个 `.o` 里。

**现行方案：回调注册**

`vclock.c` 保持零 I/O（宿主可测），由平台层注入打印器：

```c
/* vclock.h */
typedef void (*vclock_window_fn)(const VClock *vc, unsigned long raw_want,
                                 unsigned long want, unsigned long passes,
                                 unsigned long accum);
void vclock_set_window_observer(vclock_window_fn fn);
```

```c
/* vclock.c —— 窗口关闭处，计数清零之前 */
#define VCLOCK_NOTIFY_WINDOW(vcp, raw_want, want)                          \
    do {                                                                   \
        if (s_window_observer)                                             \
            s_window_observer((vcp), (raw_want), (want),                   \
                              (vcp)->passes, (vcp)->accum);                \
    } while (0)
```

```c
/* hal_clock.c */
static void hal_vclock_window_trace(const VClock *vc, unsigned long raw_want,
                                    unsigned long want, unsigned long passes,
                                    unsigned long accum)
{
    hal_logf("[VW] passes=%lu accum=%lu raw=%lu want=%lu tgt=%lu step=%lu\r\n",
             passes, accum, raw_want, want, vc->target, vc->step);
}

void hal_clock_init(void)
{
    vclock_init(&g_vclock);
    vclock_set_window_observer(hal_vclock_window_trace);
}
```

关键点：

- 观察者**在计数清零之前**调用，所以 `passes/accum` 是那个窗口的真实值，不是残留。
- `raw_want` 是**钳制前**的测量值。`raw` 就已经错了 → 钳制无罪，问题在 delta 形状；`raw` 对而 `want` 不对 → 钳制方向有问题。
- 默认不装观察者，宿主测试与所有非平台构建零影响。
- 关闭开关：`make -C core EXTRA_DEFS=-DVCLOCK_WINDOW_TRACE=0`。

**已加回归测试**（`tools/tests/test_vclock.py`，2 条）：`test_window_observer_receives_every_closed_window` 断言 100 帧 × 10ms 恰好触发 1 次、`passes=100 accum=1000 raw=160`；`test_window_observer_null_probe_is_the_default` 断言未装观察者时不崩。总 20 条全绿。

**判读表**（引擎实测约 176 pass/s，健康值 `raw≈want≈tgt≈step≈91`）：

| `[VW]` 表现 | 指向 | 下一步 |
|---|---|---|
| `passes` 远大于 176（数百上千） | 同一窗口塞了过多 pass | 查 `frame.c` 是否被多路调用 |
| `accum` 远小于 1000 | `hal_wallclock_ms()` 没前进 | DOS 时钟被卡；查 `int386` 返回 |
| `raw` 本身就对、`want` 被压 | 钳制（`5/4`）方向反了 | 查 §7.3 |
| `passes≈176 accum≈1000 raw≈91`，但 `step` 仍 ≈551 | **窗口根本没关过**——看 `[VW]` 出现频率即可确认 | 查 `real_prev` 被谁改了 |
| `[VW]` 一条都没有 | 观察者没装上 / 编译被裁掉 | 查 `hal_clock_init()` 是否真的被调 |

**`[VW]` 出现频率本身就是最强信号**：健康情况下应约每秒 1 条。若 30 秒空跑只出现 3-4 条，就证明窗口极少关闭，`step` 长期停留在初始值附近——这正好解释 §5.2 的 551 序列。

> 仍然成立的原则：**拿到 `[VW]` 之前不要改 `vclock.c` 的机制**。现在的假说已经被实测推翻过一轮，盲改只会引入新的时序 bug。

### 5.4 定案：pass 率突跳 + IIR/比例钳制收敛太慢（2026-11-16 `[VW]` 实机数据）

取数方法：容器 devpts 被锁（`ptmxmode=000` 且挂载选项不可改），但 `unshare -m` 私有挂载
命名空间里手工 open `/dev/pts/ptmx` + `TIOCSPTLCK(0x40045431)` 解锁 + `TIOCGPTN` 取号，
PTY 完全可用——工具 `tools/diag/vclock_pty_probe.py`。用
`EXTRA_DEFS=-DBGM_IRQ_PROBE_MIN_TICKS=1000` 强制走协作泵路径（正常构建大多由 ISR 接管），
35 秒空跑拿到决定性数据：

```
[VW] passes=117 accum=1000 raw=136 want=136 tgt=136 step=136   ← 首窗采纳（117 pass/s）
[VW] passes=321 accum=1000 raw=49  want=49  tgt=136 step=136   ← pass 率突跳到 315/s！
[VW] passes=314 accum=1000 raw=50  want=50  tgt=50  step=50    ← 修复后第 2 窗即收敛
（之后 19 个窗口全部 tgt=50 step=50 稳定）
[AP] d 修复前：−16 076 且每秒涨 ~200；修复后：恒定 ≈ −4 850（不再增长）
```

**三段式结论**：

1. **测量无罪**。`accum=1000`（DOS 时钟在走）、`raw=50`（1000ms÷315 pass=3.17ms/pass，
   完全正确）。窗口机制本身工作正常。
2. **pass 玛率是元凶**。引擎的 pass 率不是设计的 ~25Hz，而是启动期 117/s、随后 **315/s**——
   `frame.c` 的泵根本没有被帧锁（NP2kai 的 vblank 等待在模拟器下近乎瞬时返回）。
3. **收敛慢是放大器**。pass 率一跳，真实每-pass 速率减半以上；而
   `VCLOCK_MAX_WINDOW_RATIO`（5/4）+ `VCLOCK_MEAS_SMOOTH`（1/4）每窗口最多修 ~5-20%，
   30-60 个窗口（30-60 秒）才追上。期间 `step=136`（8.5ms/pass）× 315 pass/s =
   **虚拟时钟快 2.7 倍**——这就是 §三 的 3.9 倍实测（初值更高时更糟）。

**为什么 16:26 那次狂奔而其他次不狂奔**：IRQ12 探测通过（≥6 ticks）时 ISR 接管时钟
（`vclock_advance_fixed`，不测量、不收敛、天然正确，实测 v/w=0.94）；探测失败
（`IRQ12 silent (3 ticks in 8 frames)`）时落到协作泵，才进入上面这条狂奔链路。
**用户实机的「剧情自己走」就是协作泵开机 + 该收敛缺陷的组合。**

**修复（§7.3，已实装并验证）**：连续 2 个窗口的 `raw_want < target/2` → 判定为
持续性速率塌缩，直接重新采纳 `raw_want`（与首窗同契约）。单窗不采纳（防硬 stall
误伤）。`vclock.h` 的 `VClock` 加了 `undershoot` 字段（宿主测试的结构体已同步）。
回归测试：`test_pass_rate_jump_readopts_within_two_windows`、
`test_single_low_window_does_not_crash_the_target`。

## 六、串进特殊场景：独立链路

`special.nb` 只能从 `nb_mainmenu.c:106-108` 进入。所以「偶发跳进特殊场景」= 某次 `menu_show()` 的点击命中被判成 `special` 按钮。

按可能性排序的可疑点：

1. **`menu_show()` 没有输入就绪门**。`ui_interact()` 有 `UI_INTERACT_INPUT_READY_MS = 400` 的门控（`nb_interact.c:118-130`），`menu_show()` **没有**——它 `hal_mouse_flush()` 之后立刻进循环（`nb_menu.c:278-280`）。emulator 把「推进上一行的按键」合成成一次左键边沿的已知问题（见 `nb_interact.c:62-72` 注释）在菜单里完全没有防护。
2. **命中判定用的是当前位置，不是事件坐标**。`mouse_click_fifo` 里明明存了 `x/y`（`mouse.c:404-405`），但 `nb_menu.c:285-287` 传的是 `hal_mouse_get_x()/get_y()`。若 FIFO 里是陈旧事件，位置早已变了，两者失配。
3. **`mouse_pos_explicit` 只跳一帧**（`mouse.c:245-246`）。`hal_mouse_set_pos()` 把指针放到屏幕中心，只让下一帧跳过 NP2 覆盖。若该帧 `hal_mouse_update()` 没被调用（被长 decode 吃掉），指针会瞬间跳到别处。

## 七、修复方案（按优先级，且标注依赖）

### 7.1 超时语义分离（**不依赖 §五 定论，可立即做**）

```c
#define UI_INTERACT_TIMEOUT  (-2)   /* 安全阀到期 */
#define UI_INTERACT_CANCEL   (-1)   /* 无效请求/显式取消 */
```

超时的默认动作从「继续往下」改为**原地等待 + 重绘**：重置 deadline，焦点框闪一下作为可见提示。

理由：即使时钟再次失准，玩家看到的是「选项还在，只是没反应」，而不是「剧情自己走了」。这是**把不可见故障降级为可感知故障**，比修时钟更兜底。

保留「超时即推进」作为编译期可选（`NAIZ_INTERACT_TIMEOUT_ADVANCE`），供 headless/冒烟构建用。

### 7.2 截止时间加一致性校验

```c
/* 时钟漂移超过 20% 时不要相信 smooth clock 做的 deadline */
long drift = (long)(hal_wallclock_ms() - hal_wallclock_smooth_ms());
```

漂移超阈值时，要么回退到 `hal_wallclock_ms()` 算截止，要么直接延长 deadline 并记一条 `WARN`。

### 7.3 时钟机制（**等 §5.3 的 `[VW]` 数据**）

拿到数据前不动 `vclock.c`。已知需要补的两条（无论机制如何都要有）：

- **`vclock_advance()` 的自检**：单次 delta 超过「单帧合理上限」时不计入窗口测量。现有 `delta < 500UL` 上界只在 `calibrated` 之后生效（`vclock.c:131-139`），首窗口是裸奔的。
- **`vclock_advance()` / `vclock_advance_fixed()` 不得混用于同一 `VClock`**；切换必须复位基线（新增 `vclock_reset_baseline()`）。

### 7.4 菜单输入门控（修「串场景」）

`menu_show()` 加与 `ui_interact()` 相同的 400 ms 门控；同时把命中判定改成**用事件自带坐标**：

```c
/* 让 hal_mouse_was_clicked 顺带返回事件坐标，而不是查询当前位置 */
if (hal_mouse_pop_click(&cx, &cy, HAL_MOUSE_LBUTTON)) { ... }
```

## 九、踩坑清单

1. **`[FPS]` 的 `ms` 是虚拟时间，不是真实时间**。它的 `now` 来自 `smooth_ms()`。拿它当真实秒用，会把「虚拟时钟跑快」误读成「帧率在涨」——我在这上面浪费了一轮推断。
2. **`[AP]` 的 `d` 才是唯一可信的漂移指标**。`d = 真实 − 虚拟`，一个数就说完了。任何「无操作却有时序行为」的 bug，第一步看这一列。
3. **不要把「虚拟时钟」当秒表**。它是给 BGM/打字机/动画用的**节拍器**，只保证速率平滑和长期平均（`vclock.h:36-40` 明说「只有速率重要，相位不重要」）。**任何截止时间都不该盲信它。**
4. **`-1` 不能同时表示「取消」和「超时」**。一旦共用，任何时钟误差都会变成剧情跳过。
5. **改 `vclock.c` 之前先拿 `[VW]` 数据**。本文档第一版就是因为「算术上太自洽」而写下了错误结论（「每秒调用一次」），实际一测反而变慢 25 倍。vclock 的窗口/钳制/IIR 三层叠在一起，直觉推演不可靠——**用宿主测试直接跑**。
6. **宿主测试能证的只有「给了什么输入就出什么输出」**。它证不了「实机到底给了什么输入」，所以 `[VW]` 这类实机埋点是不可替代的。
7. **跨翻译单元的埋点不能用宏**。`LIB_SRCS = $(wildcard lib/*.c)`（`core/Makefile:79`）意味着 `vclock.c` 单独编译；`hal_clock.c` 里的 `#define` 传不过去。第一版 `[VW]` 就这样**编译零警告、运行时一行不出**。现在改成 `vclock_set_window_observer()` 回调，并加了回归测试锁住。详见 §5.3。
8. **`#ifndef` 兜底宏最危险**。它让「忘记定义」变成合法的空实现，于是失败完全没有声音。诊断代码宁可缺省报错，也不要缺省静默。
