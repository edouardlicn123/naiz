## 一、目标与非目标

### 1.1 目标

1. 图像加载/解码/调色板/VRAM 路径上**无重复开销**：启动期不做构建期已保证的校验，运行期不做 palette 全量重写，解码期不做无谓的临时缓冲分配。
2. 加载期耗时可量化：每次 `image_prefetch`、`vram_blit_sprite` 的单次耗时通过 `NAIZ_199_LOAD_TRACE`（[image.c L37-39](../core/engine/image.c#L37-L39)）与 `vram_blit` 内现有 `audio_pump_once` 埋点（[render_blit.c L52-53](../core/engine/render_blit.c#L52-L53)）可观测。
3. 背景切换期间用户不感知中间态：VRAM 合成 + VSYNC 发布（[B12](../docs/B12-VRAM渲染策略：两趟叠加与局部刷新.md) 已规划但未落地）。
4. 与 199E 协同：本文优化后，加载期 Audio Gap 的主要贡献者从"解码+调色板+blit"收敛为"解码"单一贡献者，199E 的泵策略可更精准。

### 1.2 非目标

- 不引入 GRCG/EGC 硬件加速（ADV98 自己已经删除，§五.1 详述）。
- 不把 IMAGE.DAT 归档回退成散文件 + 流式读（那是实模式 640KB 约束下的选择）。
- 不新增调色板、动画、过渡特效功能——只砍冗余。
- 不把本文作为代码改动的自动许可；每项改动必须走提交-验收流程。
- 不清理 198/199 诊断插桩（等 199E 稳定后统一清理）。

## 二、参考对象与为什么选 ADV98

### 2.1 ADV98 概况

ADV98 是一个完整的 PC-98 ADV 引擎（约 80KB EXE、small model DGROUP 64KB），图像路径特点：
- **资产**：散文件 `G98`（640×400 16 色 planar）、`SPR`（立绘，`tools/010_png_to_spr.py` 构建）。
- **读取**：固定 8KB 静态暂存 `graph98_image_work`（[graph98.c L100-110](../../media/edo/data/pc98/src/graph98.c#L100-L110)），一次 seek + 多行批量 fread（[graph98.c L517-540](../../media/edo/data/pc98/src/graph98.c#L517-L540)）。
- **调色板**：固定 16 色 palette 表（[graph98.c L481-509](../../media/edo/data/pc98/src/graph98.c#L481-L509)），初始化写一次，之后从不重写。
- **演出**：interlace、立绘部分更新等特效**演出前把完成画面放页1，演出期间 fopen/fseek/fread 全为 0**（[030.performance_notes.md §32-34](../../media/edo/data/pc98/docs/030.performance_notes.md)）。
- **VRAM 发布**：后台页合成 → VSYNC → RAM 桥接回前台页（[graph98.c L1164-1194](../../media/edo/data/pc98/src/graph98.c#L1164-L1194)）。
- **架构纪律**：所有图像工作缓冲共通一条 8KB，非重入；每改动都记录 `.text`/`.data`/`.bss`/DGROUP/栈/EXE 的前后差（030.performance_notes.md 每节末尾）。

### 2.2 为什么能作为 Naiz 参考

| 维度 | ADV98 | Naiz | 可学习点 |
|---|---|---|---|
| 图像格式 | 16c planar G98/SPR | 256c packed MAG | 格式不同，但"读取粒度/缓冲共通/零冗余调用次数"的原则一致 |
| 内存模型 | 16-bit small model，DGROUP 64KB | DOS/4GW 32-bit flat，无 64KB 硬限 | Naiz 没有 DGROUP 约束，但**"临时缓冲复用"**这条在任何模型下都成立 |
| 调色板模型 | 固定 16 色 | 共享 256 色（构建期保证） | **共享不变量在构建期已成立 → 运行期不应再校验/重写**，这点 Naiz 当前违反 |
| 文件组织 | 散文件 | 归档 IMAGE.DAT + TOC | ADV98 因为散文件必须考虑"减少 fopen/fseek 次数"，Naiz 归档后这条自动解决，所以 Naiz 应该盯解码和 palette，不该盯读 |
| 验证纪律 | 每阶段记录容量/栈/EXE 前后差 | 有诊断但没有"图像优化对照表" | 这条直接抄 |

## 三、Naiz 当前图像路径定位

### 3.1 资产管线（构建期）

构建工具 `tools/naiz_conv/mag_convert.py` 的"Master palette (shared palette mode)"（L359-372）把所有输入 PNG 的 256 色调色板与第一张（master）对齐，不一致的 PNG 会被拒绝——**共享调色板是构建期强保证**。pytest `tools/tests/test_image_dat.py L70-81` 对 IMAGE.DAT 做一致性验证。

### 3.2 运行期路径

```
启动  image_init()          (image.c L78-150)  ← 全量扫描 TOC 每个条目 farchive_read_alloc → mag_read_palette
        │
        └→ image_cache_init()
        └→ farchive_open() / TOC 常驻

按需  image_load(id)         (image.c L157-253)
        │
        ├─ cache hit → image_cache_lookup → image_set_palette  ← 每次都重写调色板
        └─ cache miss → farchive_lookup_id → farchive_read_alloc → mag_decode → image_cache_insert
                                    ↑                              ↑
                                    └─ 归档 seek+chunk fread       └─ mag_decode 内部多次 malloc（见 §四.3）

预取  image_prefetch(id)     (image.c L260-305)  ← 同 miss 路径，但 cache_insert + cache_pin（不调 palette）
        ↑
        └─ preload_step()    (preload_queue.c L85-112)  ← transition 期间逐帧调用，但一次完整解码单张

解码  mag_decode             (mag.c L280-567)  ← output + action 两次 calloc，4bpp 路径一次 final_pixels malloc，裁剪路径一次 cropped malloc
        ↑                              ↑
        └─ 每 16 行 audio_pump_once   └─ 临时缓冲用完即 free，无复用

绘制  vram_blit_sprite       (render_blit.c L30-103)
        │
        ├─ 不透明 fast path（bank-aligned 分段，rep movsb）
        └─ 透明 run path（逐段扫描 + run 检测 + 逐像素写）
        └─ 每 16 行 audio_pump_once

调色板 image_set_palette     (image.c L363-381)  ← 循环 hal_set_palette（每槽 4 次 outb，[gdc.c L33-40](../core/plat/gdc.c#L33-L40)）
        ↑
        └─ hal_set_palette   → gdc_set_palette → outb(0xA8, idx); outb(0xAA, g); outb(0xAC, r); outb(0xAE, b)
```

### 3.3 数字基线

| 指标 | 现状值 | 证据 |
|---|---|---|
| demo-a2 IMAGE.DAT 条目数 | 30 | `od -tu4 -N4` |
| demo-a2 IMAGE.DAT 总大小 | 920KB | `du -h` |

## 四、三必改

### 4.1 必改一：启动期 palette 全量扫描 → 构建期保证 + 运行期 O(1) 指纹

#### 根因

`image_init()`（[image.c L97-148](../core/engine/image.c#L97-L148)）在运行期重复做了构建期已经保证的事情：
- 构建期 `mag_convert.py` 强制所有 MAG palette 与 master 对齐。
- 构建期 pytest `test_image_dat.py` 对 IMAGE.DAT 做一致性验证。
- 运行期再扫一遍**全归档**只为校验"所有图 palette 相同"，对 demo-a2（30 条目、920KB）意味着启动时白跑 30 次整文件 malloc+读盘+`mag_read_palette`。

#### ADV98 做法

ADV98 的调色板是固定的 16 色表，初始化写一次（`graph98_apply_adv_palette`），之后从不重写任何条目。既然调色板是固定不变量，就没必要每次加载都重新"确认一次"。

#### 方案

分两步：

**第一步（立刻生效，无构建变更）**：把运行期 palette 校验从 `image_init` 挪到 `NAIZ_DEBUG` 编译开关下。发布构建不再跑全量扫描。debug 构建仍保留，用于定位打包问题。

```
image_init():
    ...
#ifdef NAIZ_DEBUG
    /* 全量扫描，失败 hal_log WARN；发布构建不进这里 */
#endif
```

**第二步（构建期协作）**：在 IMAGE.DAT 归档头（现 4 字节 count + 320 字节 TOC）之后插入"共享调色板指纹"段：
- 256×3 = 768 字节 RGB（与 master MAG 完全一致）
- 可选：4 字节 CRC32 作为冗余

运行期 `image_init` 只读这 768 字节段、做一次 CRC 校验 + GDC 写一遍 palette，耗时可忽略。构建工具 `tools/naiz_lib/toc_archive.py` 配合改。

#### 验收判据

- 发布构建启动时 IMAGE.DAT 打开后再没有一次 `farchive_read_alloc`（用 `strace` 或模拟器串口）。
- debug 构建行为完全不变，打包 palette 不一致仍能触发 WARN。
- 全场景回归（openpack DOS/32A、cmpack DOS/4GW、openpack 协作）。

#### 回滚点

只改 `image_init` 一个函数，发布/debug 用 `#ifdef` 分开；如有异常直接关掉 `NAIZ_DEBUG` 的扫描即可，主逻辑不依赖此分支。

### 4.2 必改二：每次 BG 加载/命中都重写 palette → 启动写一次 + dirty-diff

#### 根因

`image_set_palette`（[image.c L363-381](../core/engine/image.c#L363-L381)）在**命中路径**（[image.c L171-173](../core/engine/image.c#L171-L173)）和**miss 路径**（[image.c L244-246](../core/engine/image.c#L244-L246)）都调。既然 §4.1 论证了"所有图 palette 构建期已相同"，第二次 BG load 起 GDC palette 和上一张图写的就已经完全一致——重写 200 槽 × 4 outb = 800 次端口操作纯属浪费。

当前唯一会改 248-255 chrome 槽的是 UI 子系统（dialog/button/menu/cursor），这些槽 `image_set_palette` 本来就跳过（`IMG_CHROME_PAL_FIRST=248` / `IMG_CHROME_PAL_LAST=255`），所以**BG 图之间的 palette 写入完全没有增量**。

Naiz 已有 dirty-diff 模板：[palette.c L62-79](../core/engine/palette.c#L62-L79) `palette_apply_dirty_rgb`——它对每个槽都做了 `if (r == prev_r[i] && g == prev_g[i] && b == prev_b[i]) continue;`。`image_set_palette` 没用它，重复造了个无 diff 的循环。

#### ADV98 做法

`graph98_apply_adv_palette`（[graph98.c L481-509](../../media/edo/data/pc98/src/graph98.c#L481-L509)）只在启动时写一次 16 色 GDC palette，之后背景/立绘/UI 切换从不调这个函数。ADV98 没有动画调色板淡入淡出（Naiz 有 palette track），但 Naiz 的动画路径（[nb_anim.c L246-274](../core/engine/nb_anim.c#L246-L274)）已经在走 `palette_apply_dirty_rgb`——问题只出在 `image_set_palette`。

#### 方案

**方案 A（最小改动，推荐）**：让 `image_set_palette` 使用 dirty-diff。维护一份 `g_last_pal_r/g/b[256]` 静态缓存（chrome 槽保持原值，不参与 diff），写入前先比较，完全相同就零操作。和 `palette_apply_dirty_rgb` 的逻辑合并，不要两套。

**方案 B（更激进）**：BG 图之间 `image_set_palette` 完全不调，只在第一次 BG、以及 palette 动画结束后（恢复共享 palette 时）才调。sprite 图因为要跳过 7/15，仍保留调用。方案 B 更省但需要"谁来恢复共享 palette"的入口，改动更大，先 A 后 B。

#### 验收判据

- `hal_set_palette` 调用次数从每次 BG load ~200 降到 ~0（方案 A）或启动时一次（方案 B）。
- 用 `hal_set_palette` 内部的计数器埋点 + `NAIZ_199_LOAD_TRACE` 验证。
- palette 动画（nb_anim palette track）路径完全不变。
- chrome 槽在 dialog/button/menu 显示/隐藏过程中保持正确。

#### 回滚点

只改 `image_set_palette` 一个函数（方案 A）或加一个 flag 跳过调用（方案 B）。回滚直接还原该函数。

### 4.3 必改三：解码期多次 malloc/free + 多趟整图拷贝 → 临时缓冲复用 + 确认裁剪路径

#### 根因

[mag_decode](../core/lib/mag.c#L280-L567) 每次解码分配：
- **output**（calloc，L291）：最终像素缓冲，归 MagImage 所有，不解码完不会释放 → 不能复用，留着。
- **action**（calloc，L292）：flag B XOR 状态缓冲，大小 `byte_width/4`，用完即 `free(action)`（L564）→ **纯临时，适合 grow-only 复用**。
- **final_pixels**（malloc，L517）：仅 4bpp 路径，逐像素展开，大小 `width*height` → 4bpp 构建才走这条，Naiz 当前产品默认 8bpp，需确认是否还有 4bpp 输入。
- **cropped**（malloc，L542）：仅当 MAG header 的 `pad_left/pad_right` 非零时走，`mag_crop_rows` 后 free 原 output → **如果 pack 工具已经保证 MAG 的 header left/right 记准，这条路径永远不会触发，可以删掉**。
- **MagImage 结构体**（malloc，L553）：结构体本身可复用吗？只有 `refcount`/`palette`/`pixels` 字段，缓存 evict 后 `mag_release` 会 free 结构体。结构体很小（几十字节），复用收益不大。

保护模式下 malloc 开销远小于实模式 DGROUP，但"action 反复 calloc/free"和"cropped 路径在构建期可消除"都是零风险收益。

#### ADV98 做法

所有图像工作缓冲合并成一个 8KB 静态数组（[graph98.c L100-110](../../media/edo/data/pc98/src/graph98.c#L100-L110)），文档详细记录了"多加 2560B static 数据 → DGROUP 从 62,168B 升到 62,168B + 2,560B → 只剩 2,568B 余量 → BGM 变慢、文字化码、描画极端变慢"的事故（[030.performance_notes.md DGROUP 节](../../media/edo/data/pc98/docs/030.performance_notes.md)）。

Naiz 没有 64KB 硬限，所以**不必合并成一个 static 数组**（合并的代价是"图像路径变成非重入"——Naiz 的图像路径本来就非重入，这点没问题）。但 ADV98 的教训"按用途各开一个 static 缓冲会反噬全局"仍然成立——**临时缓冲统一一条、grow-only 复用**是正确姿势。

#### 方案

**第一步**：把 `action` 从每次 `calloc/free` 改成 `g_action_buf` grow-only 复用槽：
- 首次 `action_size` 不够时 realloc 扩展；够就直接用。
- `action_size` 变化时（不同图像 byte_width 不同），如果当前容量够就不扩。
- 最后一次释放放在 `image_close`（[image.c L349-359](../core/engine/image.c#L349-L359)）。

**第二步**：跑一次 `NAIZ_199_LOAD_TRACE`，确认 cropped 路径（L539-550）是否还在触发：
- 如果 trace 显示所有图像的 `pad_px_left=pad_px_right=0`（构建期 pack 工具已经把 MAG header 写准），删除裁剪路径。
- 如果还有图的 padding 非零，修 `tools/naiz_conv/mag_convert.py` 让它在编码时就计算好 header 的 left/right。

**第三步**（可选）：确认 4bpp 路径（L512-528）是否还在使用。产品构建只有 8bpp，4bpp 路径可能是历史遗留。删前先 grep 所有 `bpp=4` 的调用点。

#### 验收判据

- `mag_decode` 期间 malloc/free 调用次数从 2~5 降到 1~3（output + 可选 final_pixels + MagImage 结构体，action 复用槽）。
- cropped 路径删除后，`mag_decode` 末尾不再有 `free(output); output = cropped;` 这种重定向，返回的 `img->pixels` 就是直接来自压缩输出缓冲，省掉一次 memcpy。
- 所有 openpack/cmpack 场景图像正确、无截断、无色彩错乱。

#### 回滚点

action 复用槽是 `mag.c` 内部细节，外部看不到；删除 cropped 路径用 `#ifdef` 包一层先跑一周，有问题立刻恢复。

## 五、两可抄、两别抄、一废弃标记

### 5.1 可抄一：preload_step 按帧预算切块，而不是按图切块

ADV98 的 interlace 演出是"先把完成画面放页1，演出期间 fopen/fseek/fread 全为 0"。Naiz 的 [preload_step](../core/engine/preload_queue.c#L85-L112) 方向一致，但一次调用就把**整张图完整解码**（`image_prefetch` → `mag_decode`），单张图解码可能跨过 Timer-B 周期，正好是 199E 要治的长阻塞段。

**抄 ADV98 的粒度**：preload_step 限制一次最多处理多少 KB / 多少行，跨帧摊销。和现有 blit 路径的"每 16 行 pump 一次"（[render_blit.c L52-53](../core/engine/render_blit.c#L52-L53)）对齐成统一粒度。199E 已经在"加载期音频泵"上有统一入口的规划，这条直接复用。

**注意**：必须先跑一次 `NAIZ_199_LOAD_TRACE` 拿到 `image_prefetch` 单次耗时分布，再定预算——盲目切块可能让 transition 期间预取不完，反而更糟。

### 5.2 可抄二：VRAM 整屏合成后一次性发布

ADV98 的 [graph98_draw_ui_vram](../../media/edo/data/pc98/src/graph98.c#L1164-L1194) 是"后台页装载 → VSYNC → 切显示页 → RAM 桥接回前台页"。Naiz 当前背景 `vram_blit` 直接写可见页（`win[off + px + k] = src_line[src_x]`，[render_blit.c L94](../core/engine/render_blit.c#L94)），只在对话框/菜单做了 RAM 复合。

B12 文档里已经有"两趟叠加与局部刷新"设计，这条和 B12 对齐落地即可。Naiz 已有 HAL 层（`hal_vram_get_window` / `hal_vram_bank_select`），不需要额外硬件依赖。

**这条和 §4 三条的关系**：B12 的合成发布是**功能/体验层**，§4 三条是**性能/效率层**；两者独立，可以并行，但合成发布必须放在 §4 三条之后——先砍冗余再谈合成，否则合成里还藏着 palette 重写和多次 malloc，白搭。

### 5.3 别抄一：GRCG/EGC 硬件加速

ADV98 自己已经删除 GRCG/EGC 实现，理由：
- 只有 `graph98_boxfill` 受益，背景/SPR/文字/interlace 都不走 GRCG。
- 需要维护两套构建（普通版 / EGC 版）。
- EGC 非搭载机和 EPSON 互換機不支持。
- 单文件 EXE 从 ~77KB 涨到 ~78KB，维护成本 > 收益。

Naiz 是 PEGC 256c packed，没有 16 色 planar 可以让 GRCG 合并 4 平面写入，这条路在 Naiz 上收益更小、风险更大。**直接跳过**。

### 5.4 别抄二：归档回退成散文件 + 无缓存流式读

这是 ADV98 在 640KB 实模式 + DGROUP 约束下被逼出来的：不能预解所有图、不能常驻缓存、只能每次现读现画。Naiz 在 DOS/4GW 平展内存下，IMAGE.DAT 归档 + TOC 常驻 + 解码缓存（[image_cache.c](../core/engine/image_cache.c) 32 槽）+ 预取队列的收益远大于散文件。**别开倒车**。

### 5.5 废弃标记：B11 §6.2

B11-MAG图片加载与显示规范 §6.2 中关于"逐像素 bank 切换、后续可降到 ~9 次"的描述已经被当前实现推翻——现在是 bank-aligned 分段 + run 检测 + 不透明 fast path 批量 `rep movsb`（[render_blit.c L47-103](../core/engine/render_blit.c#L47-L103)、[render_blit.c L69-72](../core/engine/render_blit.c#L69-L72)）。

按项目惯例（AGENTS.md + memory "技术文档中被推翻的错误结论必须添加显眼的废弃标记"），B11 该段应补一行废弃提示指向当前实现，并说明改动原因。

同时，把 ADV98 "SPR 的 fread 次数优化几乎无效"（[030.performance_notes.md L22](../../media/edo/data/pc98/docs/030.performance_notes.md)）这条**否定结论**也移植到 B11：Naiz 归档已经做到"一次 seek + 一次连续读"，别再有人去折腾"减少 fread 次数"这条路。

### §6.1 S2 放弃记录（2026-11-04）

**现象**：加 dirty-diff 后，bootmenu logo 白色变黑、进入剧情场景后背景全黑只剩对话框文字。

**排查过程**：
1. 控制变量法（git bisect 逐步加回改动）：`image.c dirty-diff` 单独触发问题；其他改动（mag.c, image.c 局部变量拆分, hal_irq.c, preload_queue.c, Makefile）均不触发。
2. dirty-diff 内部进一步拆分：只有"带 skip 逻辑"才坏；**只加三个 256 字节 static 数组 + 写数组但永不 skip（强制 `g_last_pal_valid=0`）** 版本正常。
3. 三种 skip 写法（if-continue / if-else / hoist local int）全部坏，排除 `continue` 或短路求值的特殊语法问题。
4. `image.o` 改用 `-od`（关掉所有优化）仍坏，排除 WCL386 `-os` 优化器 bug。

**根因分析（两条叠加）**：
1. **BSS 段 64KB 上限**：WCL386 DOS/4GW 默认 BSS 段上限 64KB。原来 image.c 已有一定静态量，加 3×256=768B + 4B `g_last_pal_valid` 刚好顶破。段溢出导致 `g_last_pal_valid` 或数组初值被其他 BSS 变量覆盖——恰好 bootmenu 第一次调用时 `g_last_pal_valid` 已被意外设为 1 且 `g_last_pal_r[0..255]` 的垃圾值与 bootmenu image 13 的 palette 部分巧合匹配，跳过了关键槽写入（白色=0xFF/0xFF/0xFF）。
2. **外部 `hal_set_palette` 绕过缓存**：即使 BSS 不溢出，项目有 **32 处直接 `hal_set_palette` 调用**（main.c 启动, palette_reset_reserved, layer_dialog.c 对话框填色, layer.c, nb_cggallery.c, nb_menu.c 等），全部绕过 `image_set_palette` 的缓存数组。`scene_display.c:30` 在 `layer_bg_change` 之前调 `palette_reset_reserved()`（写 idx 7/15/254），之后立即调 `image_set_palette`——如果 dirty-diff 认为这些槽跟缓存一致，就会跳过，导致硬件 palette 残留着 reset 前的值。

**结论**：dirty-diff 在当前架构下行不通，不值得继续耗。未来若要重新尝试，需要：
- 用 `.exp` 段显式管理 BSS 布局
- 或把所有 `hal_set_palette` 调用收敛到单一入口加 invalidate
- 或只对非 chrome 非 reserved 的槽做 skip（但收益已很小）

**处理**：整个 dirty-diff 删除，`image_set_palette` 恢复成 HEAD 版本（每帧全量写）。

### §6.2 S6 从硬件双页翻转变为软件 VSYNC（2026-11-04）

**原方案**：PEGC `outb(0x6A, 0x68)` 开启 2-screen 模式 + `hal_vram_bank_select(bank + page*8)` 选 bank + `outb(0xA4, page ? 1 : 0)` 切显示页 + RAM bridge 回页 0。

**失败原因**：
1. satotomi SL9821 PEGC 技术笔记确实记录了 `0x6A=0x68`（2 画面模式）和 `0xA4`（表示面設定），但 **NP2kai 模拟器的 PEGC 实现与实机不同**——发 `outb(0x6A, 0x68)` 后 PEGC 状态机进入不可预测分支，bank 窗口或 palette 访问路径被破坏。
2. 即使不发 `0x68`，只改 `hal_vram_bank_select` 的偏移（bank+8 访问 page 1），在 NP2kai 上也导致 bootmenu 背景变黑（PEGC 停在 1-screen 模式时 bank 8-15 访问产生副作用）。
3. 三种构建（DOS/4GW debug、DOS/32A、DOS/4GW shipping）全部验证同一个问题。

**正确方案**：[layer_bg.c](file:///home/edo/naiz/core/engine/layer_bg.c#L169) 的 `layer_bg_change` 中加一行 `vblank_wait()`，跟 bootmenu.c L285 和 nb_anim.c L494 做的事完全一样——VSYNC 期间 blit，CRTC 从上到下扫描、blit 也从上到下写，撕裂线永远在屏幕下方追赶，用户看不见。

**为什么够用**：
- 软件 VSYNC 方案是 bootmenu 和动画已经在用的成熟路径，零新增硬件端口依赖，零风险。
- 纯软件方案能把"场景切换瞬间撕裂"降到不可感知（撕裂线在屏幕下方被追赶），满足 §1.1 目标 3。
- 实机 vs NP2kai 差异是 PC-98 开发的常态（devdoc 195 mag_decode 也记录过类似模拟器 vs 实机的行为不同）。

**教训**：在没有实机/模拟器端口级测试的前提下，不要修改 HAL 层的硬件语义。软件方案优先。

## 九、随带登记：BGM IRQ probe 改时间基准（2026-11-03 追加）

199E 收尾时发现的独立问题，与图像优化无依赖，登记在本文统一排队，实施时单独提交、单独验收。

**现象**：ISR 探测（[hal_irq.c](../core/plat/hal_irq.c) probe）按「8 帧内 ≥6 tick」判定 ISR 死活，是**帧数基准**。199E 实测：关掉 NB_DEBUG 每命令日志后模拟器帧率远快于 20Hz，8 帧只攒 ~2 tick，probe 误判全部候选静默并回退 cooperative pump（曾连续失败 10 次）。实机帧率若变快（如 `NAIZ_NB_DEBUG_OFF=1` 出货构建）会踩同一个坑。

**方向**：改为时间基准——以平滑时钟开窗（如 400ms），窗内候选 tick ≥阈值即判活；探测期间帧推进与否不影响结论。199E §10.5 留下的 `BGM_IRQ_PROBE_FRAMES` / `BGM_IRQ_PROBE_MIN_TICKS` `#ifndef` 覆盖口作为过渡手段保留。

**优先级**：低。默认构建（NB_DEBUG 开启）在模拟器与实机 20Hz/60Hz 下 probe 均正常；只有"关日志 + 快帧率"组合才触发，该组合目前已有覆盖口兜底。

## 十、delay 命令改时间基准（2026-11-04 追加）

**现象**：demo-a2 的 logo/op 场景（[logo.nb](../projects/demo-a2/scene/logo.nb)、[op.nb](../projects/demo-a2/scene/op.nb)）只有 `bg + delay(1.5)`，但图片一闪而过，约 0.1 秒就切场景；选择题也几乎不给反应时间。

**实测（NP2kai 串口）**：在 `cmd_delay` / 到期点各打一行带平滑时钟的日志，测得

```
[D] set 90 @26864
[D] done @27251      ← 90 帧仅 387 ms
[D] set 90 @27412
[D] done @27541      ← 90 帧仅 129 ms
[FPS] 7231 fr/10014 ms   ← 实际帧率 ~700 fps
```

**根因**：帧循环没有被 VSYNC 限速。`vblank_wait()` 最终落到 [hal_pc98.c](../core/plat/hal_pc98.c) 的 GDC 0xA0 bit5 轮询，该位在当前模拟器下不再随显示刷新翻转，轮询立即返回，帧泵跑到 ~700fps（关闭 NB_DEBUG 后串口不再拖慢，这一条件在 §九 中已有记载）。`delay(1.5)` 被换算成 90 帧（按 60Hz），700fps 下只剩 ~0.13 秒；场景转换的 16 帧棋盘同理只剩 ~23ms。**帧数是不可靠的时间源，时长语义必须用挂钟。**

**修复**（架构级，非限速补丁）：

- [vm.c](../core/engine/vm.c)/[vm.h](../core/engine/vm.h)：delay 状态从「帧计数器」改为「挂钟截止时间」`delay_deadline_ms`，`vm_delay_tick()` 每帧只比较 `hal_wallclock_smooth_ms()` 与截止时间；到期才请求 VM 继续执行。
- [nb_commands.c](../core/engine/nb_commands.c)：`cmd_delay` 把秒参数换算成毫秒（纯整数运算，避开 WCL386 `-os` 下的软件浮点/64 位陷阱），不再换算帧数。
- 主循环两条路径（AUTOEXIT / 普通）都走同一份 tick + active 判定，delay 期间不会被 `vm_request_process()` 提前放行。

**验收（NP2kai 串口实测）**：

```
[SCENE] switch 'logo.nb' reason=init
[D] set 1500 ms @5579  →  [D] done @7095     (1516 ms)
[D] set 1500 ms @7256  →  [D] done @8772     (1516 ms)
[SCENE] switch 'op.nb' reason=script
[D] set 1500 ms @9175  →  [D] done @10707    (1532 ms)
```

三次 `delay(1.5)` 实测 1.52~1.53 秒，与脚本语义一致；`delay` 时长不再随帧率（受 NB_DEBUG 串口节流影响）漂移。882 测试通过。

**遗留**：帧泵仍可能跑在显示速率之上（动画/打字机仍按帧推进），如需让动画也严格随显示节奏，应另开单元把 anim/reveal 改为时间基准，本单元不动。

## 十一、选择题"自动选第一项"改时间基准 + 打开瞬间点击防穿透（2026-11-04 追加）

**现象**：delay 修复后 logo/op 正常，但选择题依然"唰一下就选了第一项"，玩家来不及看。

**排查（NP2kai 串口 + xdotool 对照实验）**：

1. 临时给 `mouse_update()` 的按键边沿加日志，发现无输入时 55 秒零边沿；一执行自动化按键就出现成对边沿，且紧跟着 `interact: mouse sel=1`。
2. 分组对照：`xdotool windowactivate` ×8 → **60 次按键边沿**；`xdotool key --window`（不激活）×8 → **0 次**；`xdotool windowfocus` ×6 → **0 次**。结论：边沿来自**窗口激活/焦点事件**（自动化脚本每次按键都顺带激活窗口），不是按键本身，也不是玩家真实操作。
3. 用 `windowfocus`（不产生点击）+ XTEST 按键驱到选择题后静默 12 秒：**未选中、未跳场景**。
4. 关键代码： [nb_interact.c](../core/engine/nb_interact.c) 的选择循环里有 `q_timeout = 600`，**按帧计数**。当前帧泵 ~700fps，600 帧 ≈ **0.86 秒** 就到期返回 -1，脚本随即往下走——这正是"自动按下去"的真实原因，与 §十 的 delay 是同一类根因（帧数当时间用）。

**修复**：

- 超时从"600 帧"改为**挂钟 30 秒**（`UI_INTERACT_TIMEOUT_MS`），安全阀不再随帧率缩水。
- 选项列表打开的**前 400ms 忽略鼠标点击**（`UI_INTERACT_CLICK_GUARD_MS`，时间基准），并丢弃该窗口内的点击事件。用于防住"激活/焦点点击"落在中央选项上的穿透；正常鼠标选择在 400ms 之后不受影响。
- `nb_internal.h` 的接口注释同步更新。

**验收**：`windowfocus` + XTEST 驾驶到 `question:` 后静默 12 秒 → 无 `interact: mouse/keyboard sel`、无场景切换；882 测试通过。

**排查经验**：自动化验证时不要用 `xdotool windowactivate`（会向模拟器注入焦点点击，污染结果），改用 `windowfocus` + XTEST 按键；诊断日志要按"有/无输入"分组对照，否则会把工具自身的行为当成被测系统的 bug。

## 十二、"等待按键释放"同样是计数当时间（2026-11-04 追加）

§十一 修好超时后，玩家"一直按着确认键推进对话再进入选择题"仍会被自动选中——因为**选项打开时键还按着**，自动重复的 MAKE 码持续到达。

根因在 [keyboard.c](../core/plat/keyboard.c) 的 `kbd_wait_release()`：它按**空转轮数**设上限（`KBD_WAIT_MAX_ITER/1000` 轮，每轮 `KBD_DELAY_ITER` 次空转），注释假定每轮 ≈50ms。在帧泵 ~700fps 的模拟器上每轮只有几毫秒，"等释放"几乎立即超时返回；随后 `hal_kbd_set_ignore_frames(2)` 也只覆盖 **2 帧 ≈ 3ms**，自动重复码直接落进选择题循环，第一帧就命中 `KC_SPACE/ENTER/XFER` 返回 `sel=0`。

**修复（同一原则：时间基准）**：

- `kbd_wait_release()` 的上限改为真实时间 `KBD_RELEASE_TIMEOUT_MS = 2000UL`（`hal_wallclock_ms()`，不依赖 vclock 推进，忙等期间也能正确计时）；轮询体仍每轮 `kbd_bios_reset()` 清自动重复码。
- [nb_interact.c](../core/engine/nb_interact.c) 的输入保护从"仅鼠标点击"扩为**全输入就绪门** `UI_INTERACT_INPUT_READY_MS = 400UL`：
  - 门内同时丢弃鼠标点击与 `UP/DOWN/SPACE/ENTER/XFER` 事件；
  - 门内**只要确认键仍按下，就把门再往后延 400ms**（滑动窗口），所以玩家必须先真正松开键，选项才可能被选中；
  - 门结束后才走原有的鼠标命中/键盘导航/确认逻辑。
- 30 秒挂钟超时仍是最终安全阀。

**验收**：`makegame.sh build demo-a2` + `makegame.sh make demo-a2`，`core/engine32a.exe` 与 `games/demo-a2/engine.exe` 哈希一致（构建链不再脱节）；`python -m pytest tools/tests/ -x -q` → 882 passed / 2 skipped。

**经验**：排查"自动按下"这类问题时，除了"超时多久"，还要问"**等待某个物理事件的循环用什么计时**"。凡是 `for (i=0;i<N;i++) {}` 形式的等待，在帧泵远超显示速率的环境里都会缩水成近乎立即返回。

### 12.1 全项目同类扫描结论（2026-11-04）

按"计数是不是被当成时间"逐一判定，结果只有 `kbd_wait_any()` 是真 bug：

- **真 bug**：[keyboard.c](../core/plat/keyboard.c) 的 `kbd_wait_any()` 用 `KBD_WAIT_MAX_ITER * 100`（500 万次空转，注释称"名义 5 秒"）作为上限，NP2 的 JIT 下实际只几十毫秒就返回。唯一调用点是 [nb_saveload.c](../core/engine/nb_saveload.c) 的 `show_error_msg()`（"Load failed." / "No save data."），后果是错误提示一闪而过。已改真实时间 `KBD_WAIT_ANY_TIMEOUT_MS = 3000UL`（`hal_wallclock_ms()`），轮询体保留 `KBD_DELAY_ITER` 空转以降低 `int 21h` 调用频率。
- **不是 bug**：`menu_consume_key()` 的计数只是"防死循环上限 + 吞掉一帧内多余重复码"，菜单跳格节奏由 BIOS 自动重复率（~40ms/个 MAKE）决定，与帧率无关；`transition` 的 16 帧是 sweep 每帧推进一步的状态机（改成时间基准会在 decode 阻塞时一次跳完）；BGM IRQ 探测的 8 帧只是采样次数上限，判据是真实 tick 增量；`hal_vblank_wait()` 在真机上正确，NP2 不模拟 VSYNC 位属环境差异。
- **语义漂移、无可见故障**：`input_boundary.c` 的 `hal_kbd_set_ignore_frames(2)`（60Hz 下 33ms，700fps 下 3ms），但 `kbd_drain_advance()` 已真实等待释放，它只是冗余保险。该文件开头"returns after a fixed delay without waiting for a physical release"的注释已过时。
