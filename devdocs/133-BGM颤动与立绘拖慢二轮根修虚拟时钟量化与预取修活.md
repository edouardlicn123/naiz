# 133 — BGM 颤动与立绘拖慢二轮根修：虚拟时钟量化锯齿 + 预取修活 + 撤销方案 A

> 状态：`实现完成待实机验证`
> 版本：`0.3.031`
> 相关：devdoc 131（分析/建议，规格来源）、132（一轮 A/B/D 落地）、129（帧泵）、130（vclock 平滑步进）、B19 §1/§2（时钟源决策与 pass 率）、B91 §3（32-bit 保护模式）
> 前序：devdoc 132 落地 A/B/D 后**用户实测无改善**，并新增「BGM 一开始播放较快」症状。本轮据此重新定位根因：132 的 A/B/D 未触及真正的颤动源（虚拟时钟自身的量化锯齿），且方案 D 因**调用点只覆盖多页对白**而基本未运行。

## 1. 症状（用户 0.3.030 实机反馈）

1. **声音依然有颤动感**——且**静置在对白页、不做任何立绘切换时仍然颤**（用户确认）；
2. **一开始播放较快，然后速度正常**——出现在进入场景 1 的 BGM 起播；
3. **加载立绘时拖慢**——与 132 之前无异。

三条互相独立，132 一轮未命中其根因。

## 2. 根因（代码级，逐条）

### 2.1 症状 2「起播较快」— 虚拟时钟起步无标定（`vclock.c:44`）

`vclock_init()` 置 `step = VCLOCK_INIT_STEP_UNITS = 640` = **40ms/pass**，而这只是 NP2kai ~25Hz 的旧经验值。真实每 pass 时长（NP2kai ~48.8ms @20.5Hz，真机 16.7ms @60Hz）与之不符；且因 DOS 时钟 `DL` 恒 0、秒值成块交付（B19 §2.6/§3.1：冻结 3–6s 后一次 +1000..+6000ms），**首个校准窗口可长达数秒**，期间无从纠正。旧代码更在窗口闭合后以 `VCLOCK_SLEW_UNITS=8`（0.5ms/pass）从 640 **缓慢爬向**目标，令偏差再延续约 1s。合成结果即「先快后正常」。

### 2.2 症状 1「静置也颤」— 窗口测量的整数量化锯齿（`vclock.c:81`）

`want = (delta * 16) / passes`。因 `delta` 被量化为 1000ms 的整数倍、`passes` 是整数（NP2kai ~20.5 → 每窗口 20 或 21），`want` 的量化误差约 ±1000/passes² ms/pass：passes=20 时 **±2.5ms ≈ ±5%**。而 `step` 只以 0.5ms/pass 追 `target`（`vclock.c:92-100`），每窗口 target 跳变一次、需数个 pass 才跟上 → **step 在 ±5% 范围内做秒级周期的三角摆动**，听感即颤。此机制**与立绘加载无关**，故静置也颤——这正是用户反馈的关键判别。

加载时 `passes` 骤降、`want` 被 `VCLOCK_RATE_MAX_MS=100` 夹住，恢复还要约 100 pass，是第二段更大的漂移。

### 2.3 症状 3「立绘仍拖」— 方案 D 有三个缺陷，导致预取基本未生效

1. **调用点只覆盖多页对白**：`nb_prefetch_lookahead()` 的唯一调用点 `nb.c:439` 位于 `if (nb_dialog_get_offset() >= 0 && nb_dialog_get_text())` 分支内。**单页对白行的 `text_offset` 被置 -1**（`nb_dialog.c:163`），走 else 分支（`nb_dialog_dismiss(); continue;`），因此最常见的一行对白**从不预取**。
2. **`char` 忽略表情 expr**：`nb_prefetch_key()` 对 `char` 固定取 `resolve_expr(cid, "normal")`（`nb_commands.c:120`），而实际命令用 `expr = (argc >= 3 && argv[1][0]) ? argv[1] : "normal"`（`nb_commands.c:310`）。脚本写非 `normal` 表情时预取的是错图。
3. **预取图最易被淘汰**：`image_cache_insert()` 以最低 `hits` 为淘汰依据（`image_cache.c:98`），刚预取进来的图 `hits=0`，**恰是第一个被淘汰的对象**，预取白做。

### 2.4 方案 A 是负资产（`audio.c:512`）

`audio_tick()` 每 16 次调一次 `hal_vblank_wait()` 阻塞。主循环每 pass 调一次 `audio_tick()`，NP2kai 下即每约 0.8s 多一次最长约 48ms 的阻塞 → 周期性 hitch；解码期每 64KB 一次。B 已覆盖「解码期时钟不停」的诉求，A 的让出价值消失，只剩扰动。

## 3. 本轮修复（Phase 1–4）

> 用户决策：C 单独立项（见 devdoc 134），本轮只执行 Phase 1–4。方案 E 仍不做。

### 3.1 Phase 1 — 虚拟时钟：首窗直采 + 测量平滑（`core/lib/vclock.{c,h}`，症状 1+2）

纯整型、无 I/O，主机可穷举（`test_vclock.py`）。

1. **按时间累积窗口**：新增 `accum`，累加每 pass 的真实增量；达到 `VCLOCK_WINDOW_MS=1000`（一个 DOS 秒）才闭合测量。取代原「只要 delta>0 就闭合」，令真机 10ms 量化也可平均，NP2kai 1s 块亦自然对齐。
2. **首窗直采**：新增 `calibrated` 标志；**首个闭合窗口**直接 `target = step = want`，不再从 640 缓升——消除症状 2 的爬升段。
3. **测量平滑**：非首窗用 `target += (want - target) / VCLOCK_MEAS_SMOOTH`（IIR，因子 4）吃掉 ±5% 整数量化抖动——消除症状 1 的锯齿摆动。
4. **短窗丢弃**：`passes < VCLOCK_MIN_WINDOW_PASSES=2` 的窗口（一次 pass 吞掉整秒的硬停）不参与测量，保留上一速率。
5. `VCLOCK_SLEW_UNITS` **保持 8**：平滑后 target 稳定，不再需要大步追赶；维持「相邻 advance 差 ≤ slew」的连续性契约。

### 3.2 Phase 2 — 让方案 D 真正生效（症状 3）

1. **调用点每 pass 覆盖所有对白分支**：`nb_prefetch_lookahead()` 由 `static` 改为导出（声明入 `nb.h`），在 `main.c` 三处主循环的 `engine_frame_pump()` 之后各调一次（AUTOEXIT / 主循环 / 输入等待内循环）。`done_pc == nb.pc` 保证每脚本位置只扫描一次；单页对白行的整个阅读窗口由此被覆盖。`nb.c:439` 原调用保留（翻页即预热，幂等）。
2. **`char` 传出 expr**：`nb_prefetch_key(cmd, key, expr)` 增第三参；`nb.c` 传入 `(argc >= 3) ? args[1] : "normal"`，与 `cmd_char` 的取值逐字一致。
3. **预取图 pin**：`image_internal.h` 新增 `image_cache_pin(int id)`，`image_cache.c` 实现（把该槽 `hits` 提到保底 `IMAGE_CACHE_PREFETCH_HITS`）；`image_prefetch()` 末尾调用，使预取图不再最先被淘汰。

### 3.3 Phase 3 — 撤销方案 A（`core/engine/audio.c`）

删除 `AUDIO_YIELD_EVERY` / `g_audio_yield_ctr` 及 `audio_tick()` 内的阻塞 vblank 等待，恢复 `audio_tick()` 为纯泵；同步订正 `frame.c`/`frame.h` 注释中指向 A 的说明。防复发守卫**反向改写**为「`audio_tick()` 不得含阻塞 vblank 等待」。

### 3.4 Phase 4 — 串口确定性标记与收口

- **`[VC]` 标记**：`hal_wallclock_smooth_advance()` 内每 64 pass 打一行 `[VC] v= step= tgt= cal=`（串口、节流、编译期 `VCLOCK_TRACE_ENABLED` 可关），供 §八 五禁要求的确定性判别（禁靠点击计数/听感）。
- 新建本 doc；CHANGELOG `c62`/`0.3.031`；AGENTS 头部同步；`bump_version`；`test_devdoc_refs`/`test_frame_pump`/`test_vclock` 复核。

## 4. 实机验收判据（用户执行 `build`+`make` 后）

1. 串口启动行含 `AUD MPU OK` 或 `AUD OPNA OK` → 确定 BGM 后端（时基修复对两后端均有效，阈值不同）。
2. `[VC]` 相邻行 `step`/`tgt` 波动 <1%，`v` 与真实时间长期差 <0.5%。
3. 场景 1 BGM 起播 1s 内节奏即正确（不再先快）。
4. 立绘切换无卡顿（预取命中）。

## 5. 遗留

- **加载期 tempo 塌陷**：Phase 1 治「稳态颤」与「起播快」，但**主循环 pass 率被长操作绑架**导致窗口内音乐时间不足，属结构性，只有中断驱动音泵（方案 C，devdoc 134）能根治。若本轮后 `[VC]` 显示 steady 但加载瞬时仍慢，即转 C。
- 症状 3 的「拖」由 Phase 2 预取 + Phase 3 去 hitch 共同缓解；根治仍是 C 之外的独立课题。
