## 二、症状 1 判定过程：证据链

### 2.1 串口日志（唯一直接证据）

```
logs/serial_demo-a2.log:13: AUD WARN: no MPU-401 (BGM disabled, PCM unchanged)
```

该行由 `core/engine/audio.c:338` 打印，紧随 `g_mpu_ok = hal_audio_detect()`（`audio.c:334`）之后。

> 注：这份日志只到开机菜单（无 `[SCENE]` 行），证明的是**开机探测失败**，不证明 `bgm()` 执行时的行为——后者由代码路径给出（§2.3）。

### 2.2 探测实现与它预告的失败模式

`core/plat/hal_audio.c` 文件头注释 **第 5-8 行**已经把失败模式写死了：

```
 *   - hal_audio_detect(): reset (0xFF) then UART (0x3F), each acknowledged
 *     by 0xFE on the data port.  On a real machine without a card, or an
 *     NP2kai build with MIDI disabled, the status port reads back 0xFF and
 *     the probe times out -> 0.
```

- 端口：`MPU_DATA_PORT 0xC0D0` / `MPU_STATUS_PORT 0xC0D2`（`hal_audio.c:29-30`）
- `mpu_read_byte()`（`hal_audio.c:41-49`）轮询 status bit7（`0x80`，RX_PENDING）为 0 才读数据，最多 `MPU_PROBE_ITER 20000` 次（`hal_audio.c:38`），超时返回 -1
- `hal_audio_detect()`（`hal_audio.c:51-60`）：reset(`0xFF`) 期待 ACK `0xFE`，再 UART(`0x3F`) 期待 ACK；任一步失败即返回 0

status 恒为 `0xFF` ⇒ bit7 永远置位 ⇒ `mpu_read_byte()` 每次都超时 ⇒ 探测返回 0。

### 2.3 探测结果如何变成「每个 bgm 都丢弃」

```
audio_init()  audio.c:334   g_mpu_ok = hal_audio_detect();   → 0
             audio.c:338   else → hal_log("AUD WARN: no MPU-401 ...")

audio_bgm_start(key)         audio.c:109  if (!g_mpu_ok) {
                             audio.c:110      hal_logf("BGM WARN: '%s' ignored (no MPU detected)", key);
                             audio.c:111      return;   ← 每个 bgm(){key} 在此静默丢弃
                             audio.c:112  }
```

`audio_bgm_start` 里 `g_mpu_ok` 之前还有两道闸（`audio.c:105-108` 的用户开关 `g_bgm_on`、`audio.c:113-116` 的归档可用），本例两道都通过，**唯独 MPU 这道把请求挡掉**。

这是**设计内的降级**：不崩溃、不静默无日志，只打一行 WARN。`docs/B92-NB脚本命令参考.md:36` 记载的也是「BGM 播放（key 在花括号负载）」，未承诺任何环境下都可闻。

### 2.4 环境证据：宿主没有 MIDI 栈

| 检查项 | 结果 |
|---|---|
| `~/.config/wxnp21kai/wxnp21kai.toml` | `mpu98en = true` 但 **`mpu98dev = ''`**（没有宿主 MIDI 设备可路由） |
| `/dev/snd/midi*` | 不存在（只有 `hwC0D0`/`hwC1D0`/`pcmC*` 等 PCM 设备） |
| `/dev/seq` | 不存在（ALSA sequencer 未启用） |
| `snd-seq` / `snd_midi` 内核模块 | 未加载 |
| `fluidsynth` / `timidity` / `acconnect` | 均未安装 |

即：**NP2kai 侧配了 MPU-98 但没有后端设备**，引擎探测自然失败。这与 `docs/B91-构建环境与参考速查.md:289` 的既有声明一致——「无实体 PC-98……涉及硬件时序/I/O 端口差异/MIDI 等无法验证」。

### 2.5 结论

`nbook001.nb:3` 的 `bgm(){test1}` **写法正确、执行正常**，只是在本环境被 MPU 闸门丢弃。**不是脚本缺陷，不需要修脚本。**

## 三、症状 2 判定过程：`hi` 被 `ding` 瞬顶

### 3.1 数据本身完好

```
assets/demo-a2/voice/hi.pcm     len=5528  min=0 max=255 distinct=160
assets/demo-a2/se/chime.pcm     len=6631  min=0 max=255 distinct=160
assets/demo-a2/se/ding.pcm      len=8836  min=0 max=255 distinct=160
```

三者统计特征一致 ⇒ 排除「`hi.pcm` 是静音/空文件」。

### 3.2 时长（`NAIZPCM` 头 rate code → `tools/naiz_audio/wav_convert.py:44` 的 `_PCM_RATES`）

| 文件 | rate code | 采样率 | payload | 时长 |
|---|---|---|---|---|
| `chime.pcm` | 2 | 22050 Hz | 6615 B | 0.30 s |
| `ding.pcm` | 2 | 22050 Hz | 8820 B | 0.40 s |
| `hi.pcm` | 4 | 11025 Hz | 5512 B | **0.50 s** |

### 3.3 争用机制

86 板只有**一条** PCM FIFO。引擎侧对应单一缓冲区：

```
core/engine/audio.c:185  static void pcm_play(const AudioAssetMap *map, const char *key, int chan)
core/engine/audio.c:204      raw = farchive_read_alloc(&g_arc, off, size, NULL);
core/engine/audio.c:221-223  /* Replace current stream. ... */
core/engine/audio.c:224      hal_pcm_play(raw + PCM_HDR_SIZE, ..., rate, 0);
```

`pcm_play` 由 `audio_snd_play`（`audio.c:231`）与 `audio_vc_play`（`audio.c:240`）**共用**，后一次调用直接顶掉前一次的流。`docs/B92-NB脚本命令参考.md:38` 已白纸黑字写着「与 SE 共享单 PCM 通道，**后到覆盖**」。

### 3.4 触发条件：脚本相邻

```
11 voice(){hi}          ← 0.50 s
12 sound(){ding}        ← 0.40 s，相邻两行
```

`cmd_voice`（`core/engine/nb_audio.c:43`）与 `cmd_sound`（`nb_audio.c:32`）都是**非阻塞**、无自暂停的（同 `AGENTS.md` §十四.6/§十四.7），故两行在**同一个 `nb_process` pass 内背靠背执行**：`ding` 在 `hi` 启动后毫秒级内顶掉它 ⇒ **`hi` 实际发声 < 1 ms，听不见**。

### 3.5 对照验证：`chime` 为什么能听见

```
5  sound(){chime}       ← 0.30 s
6  char(l,normal,body){fei}
7  char(r,normal,body){ira}
8  ira(){Good Morning,Fei.}   ← 对白页，engine 侧暂停等待
```

`chime` 之后跟的是 `char`（sprite 操作，不碰 PCM 通道）与台词行，直到第 8 行才进入等待点 ⇒ `chime` 有完整播放窗口。**这与「chime/ding 可听见、hi 听不见」的实机报告完全吻合**，因果闭合。

### 3.6 修法（纯脚本，不动引擎）

把 `sound(){ding}` 移到 `hi` 之后**一个对白页**之后，使 `hi` 在等待期间播完：

```
11 voice(){hi}
12 ira(){Really?...}     ← 对白页：hi 在此期间播完
13 sound(){ding}         ← 由原第 12 行挪来
```

## 四、三条音频通路：各自能播什么

### 4.1 通路对照

| 通路 | 引擎实现 | 硬件 | 本环境状态 |
|---|---|---|---|
| **MIDI over MPU-401** | `core/lib/midi.*`（SMF 解析）+ `hal_midi_out()`（`hal_audio.c:62`） | PC-98 **扩展卡**（音源箱） | ❌ 探测失败，BGM 全哑 |
| **PCM（采样）** | `pcm_play()`（`audio.c:185`）+ 86 板 FIFO 泵 | YM3433B（86 板标配） | ✅ 可闻 |
| **FM 合成** | **无**（HAL 里没有任何 YM2203/YM2608 端口访问） | YM2203 / YM2608 | — 无法验证 |

### 4.2 内容 → 格式适配

| 内容 | 应当用 | 理由 |
|---|---|---|
| **语音（角色说话）** | **PCM，无替代** | 人声波形极复杂；FM 合成只能得到「机械音/机器人音」，不是真人说话 |
| 短音效 SE（提示音、门铃） | **PCM** | 现成方案，本项目 `chime`/`ding` 即在此路，已通 |
| 长旁白 / 剧情朗读 | PCM | 同语音 |
| **BGM 背景音乐** | **FM**（次选 PCM 循环） | ① FM 数据量极小（一首曲子 = 音符序列 + 包络参数）② 天然循环 ③ 音色可变 ④ **PC-98 真机就是这么做 BGM 的** |

PC-98 原生做法佐证：`docs/refdocs/F01_sound_boards.md:108-110` 列出 DOS 音源驱动 **FMP**（FM 音源驱动/播放器）、**PPZ8**（与 FMP 配合的 PCM 驱动）、**PMD/PMD98**（FM 音源驱动/播放器 + **MML 编译器**）——即「**FM 出 BGM + PCM 出语音/音效**」，与上表完全一致。

**由此可判**：本项目当前「BGM 走 MIDI」是**移植思路**（PC-98 原生并无 MIDI），而非平台原生思路。

### 4.3 为什么 PCM 不能直接当 BGM

1. **单通道硬伤**：`sound`/`voice` 共用一条 FIFO（§三）。BGM 若循环占用该通道，**第一个 SE 就会掐断背景乐，且播完不会自动恢复**——§三的 `hi`/`ding` 就是这条规律的最小复现。
2. **体积/内存**：8bit 单声道，60 秒循环（按 `wav_convert.py:44` 的 `_PCM_RATES`）：

   | 采样率（code） | 60 s 体积 |
   |---|---|
   | 44100 Hz（0） | ≈ 2.5 MB |
   | 22050 Hz（2） | ≈ 1.26 MB |
   | 11025 Hz（4） | ≈ 646 KB |
   | 4134.4 Hz（7） | ≈ 242 KB |

   且 `audio.c:204` 的 `farchive_read_alloc` 把**整条** malloc 进堆，峰值堆 = 曲目大小 + 其余全部（代码中无显式上限声明，实际边界取决于 VEM486 DPMI，**须实测**）。
3. **代码侧缺口**：`hal_pcm_play(..., loop)` 本身**已支持 loop**（`hal_audio.c:131`），但 `pcm_play` 硬编码 `loop=0`（`audio.c:224`，注释 `audio.c:221-223` 引用 devdoc 101 §4.3），且脚本语法 `sound(){<key>}` **没有 flags 参数**（`docs/B92-NB脚本命令参考.md:37`）。两者都要改。

## 五、WAV → FM：结论是不可行，且不应指望

### 5.1 原理上不可行

- **FM 合成是参数化模型**：一首歌 = N 通道 ×（音色包络参数 + 音符序列），全部信息可能只有几千个数字。
- **WAV 是任意波形采样**，信息量 = 采样率 × 时长。
- 由 WAV 反推 FM 参数是**严重欠定的逆问题**：不同音乐可产生相同波形；同一段波形对应无穷多种 FM 解释，**不存在唯一解**。硬做只能得到「劣化到几乎不像原曲」的结果。
- 学术上有可微 DSP / 神经合成器（DDSP 类）做「音色迁移」，但那是玩具，不是音乐制作工具。

**业界实际做法是反过来的**：用 tracker 挑 FM 音色**现场作曲**（选 patch + 排音符），而非从录音反推。FM 的价值恰恰在于「用受限参数表达音乐」——绕开这个限制，FM 也就没有意义了。

### 5.2 由此得到的方向（**具体作曲方法留作下一步研究**）

推荐工具链方向：**FamiTracker**（内置 YM2612/OPN2 模拟；与 PC-98 的 **YM2608/OPNA** 同源——2608 = 2612 的 6FM + 6SSG + ADPCM，FM 核心一致，故 FM 音色基本通用），可**导出 WAV**（立刻可听可交付，不依赖引擎实现 FM）与**导出 MIDI**（将来 MPU 路线直接可用）。

其价值在于**切断一个循环依赖**：

> 引擎没有 FM 通路 → 做不出 FM 音乐 → 无法验证音乐 → 一直卡住

用 tracker 作曲并导出 WAV 后，**音乐资产与引擎播放通路解耦**：资产先以 WAV 进管线，引擎将来播 PCM / MIDI / FM 是独立决定，不被实现进度阻塞。

**许可提示**（`AGENTS.md` §十 关心传染性）：FamiTracker 本身 GPLv2，但**其生成的音频数据不被传染**（GPL 只覆盖代码，不覆盖输出数据）；内置 YM2608 patch 来自硬件厂商音色表；MIDI/WAV 输出物无 GPL 约束。**若日后自研** FM 播放器或 MML 解析器，须另找许可干净的参考（MML 格式本身公开）。

> **下一步研究（不在本文范围）**：FM 乐谱格式选型（MML/PMD `.MML` 采样 vs 直接驱动 YM2608 端口序列 vs MIDI+音源映射）、tracker 导出的资产如何进管线、Hibiki 类浏览器 MML 编辑器是否可用。

**堵的缺口**：`tools/naiz_build/nb_validator.py:80-85` 只加载 `IMG`/`ANI`/`CG` 三类 name 集，**不校验音频 key**。故未登记的音频 key 能一路通过 `build`，只在实机表现为一行 `BGM WARN: '<key>' is not a registered BGM asset`（`audio.c:117-120`）——即 `AGENTS.md` §九.6 所称「假通过比失败更危险」。

**负例已验证**：临时投放含 `bgm(){nosuchtrack}` / `sound(){alsomissing}` / `voice(){ghost}` 的场景文件，守卫如期变红并逐条指出 `file:line` 与期望 type；删除后复跑通过。（守卫不生效等于没有守卫。）

## 八、踩坑清单

1. **同通道相邻播放 = 前者静音**。`sound`/`voice` 共享 86 板单 FIFO、后到覆盖；相邻两行非阻塞命令会在同一 pass 内背靠背执行。写场景时把 `voice` 与 `sound` 隔开至少一个对白页。**判据**：某 `.pcm` 单独可闻、放在脚本里听不到 → 先查相邻行有没有另一条 PCM 命令，不要怀疑文件或采样率。
2. **`voice`/`sound` 能听到 ≠ `bgm` 能听到**。三条通路硬件不同：PCM 走 86 板 YM3433B（标配，可闻），BGM 走 MPU-401（扩展卡，需外接音源）。「有声音」不能推出「BGM 通路正常」。
3. **BGM 静音先看串口有没有 `AUD MPU OK`**。`audio.c:336` 成功时打这行；见到 `AUD WARN: no MPU-401`（`audio.c:338`）即已定性，不必再怀疑脚本、key 登记或 `AUDIO.DAT`。
4. **`.pcm` 自带 16 字节 `NAIZPCM` 头**（magic 8 + rate code 1 + flags 1 + reserved 6，`wav_convert.py` 生成）。裸采样数据直接喂引擎会在 `audio.c:209-213` 报 `PCM WARN: '<key>' bad .pcm header`。
5. **`scene()` 会停所有音频**。`scene_switch()` → `audio_stop_all()`（`nb.c:300`）。不要指望 BGM/语音跨场景延续，也不要为了「保险」在每个场景末尾堆 `bgm(stop)`（001:23 即冗余实例）。
