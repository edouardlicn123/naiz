## 一、目标与非目标

### 1.1 目标

1. 消除加载期的 BGM 空窗/顿挫：主循环任意两次泵之间不再出现 >32ms 的 FM 写空档。
2. 指标：`maxu ≤ 516`（2 个 Timer-B 周期）、`banked ≤ 1`，`[AUDIO-GAP]` 无 >32ms 记录。
3. 让 `NAIZ_BGM_IRQ=0` 与 `=1` 两种构建都能链接，pytest 全绿。
4. 把“解码泵不得再调 `hal_wallclock_smooth_advance()`”固化成测试，防止 P7 回归。

### 1.2 非目标

- 不引入 EQA/资产管线改造（EQA 是编排层，不是时间层）。
- 不做音频服务化、DPMI/TSR 外置、PMD 式进程边界。
- 不清理 198 诊断插桩（`[ISR-DRAIN]`/`[MAG-ISR]`/计数器）；等 §五 E 稳定后由 199 §七统一处理。
- 不实施 199 §五 B（解码期整段 PIC 屏蔽）与 §五 C（解码状态迁出栈）。B 已实测会造成约 1 秒音频空窗；C 是后续根治项。
- 不自动 commit / push。

## 二、问题现状与机制

### 2.1 现象

立绘/背景/文字加载时 BGM 出现可感知的停顿，恢复瞬间又像“追赶”一样把积压的音符一次性吐出。用户实机反馈与 199 §三 的取证一致。

### 2.2 机制（为什么 ISR 在跑，音乐还是会停）

当前架构（devdoc 176）是：

```text
Timer-B IRQ ──> hal_bgm_irq_handler：
                 只做 g_irq_units_total += 258、推进虚拟钟、计数
                 （不在 ISR 里写 OPNA：DOS/4GW 下 SS != DS，会写错地址）

主线程 ──> audio_tick_isr_pending()：
             take_pending_units() → 按周期 split-drain → audio_tick_isr()
             → fmseq_pump() → hal_midi_out()/OPNA 写
```

因此，IRQ 只“记账”，真正的 FM 写发生在主线程。主线程一旦被长阻塞（读盘/解码/驱逐），就出现：

1. 阻塞期间：`units` 持续累加，但**没有任何 FM 写**，音符停在最后一个状态；
2. 解除阻塞后：`take_pending_units()` 一次取回全部积压（例如 6708 units ≈ 416ms），`audio_tick_isr_pending()` 逐周期重放，`fmseq_pump()` 把过期事件集中派发——听感就是“停一下，然后抢拍”。

`hal_wallclock_smooth_advance()` **不能**修这个问题：它只推虚拟钟，不补 `units`，会让 fmseq 的 cursor 直接跳到新时间，造成跳事件/静音（199 §五 B 已踩过）。

## 三、设计原则

1. **单一泵入口**：所有新增泵点统一走 `frame_decode_pump()` 或其拆分出的 `audio_pump_once()`，不各自调 `audio_tick`/`audio_tick_isr_pending`。
2. **按阻塞段插泵，不按函数插泵**：只在实测 >16ms（一个 Timer-B 周期）的段插入；不搞“每行都泵”。
3. **不伪造时间**：禁止用 `hal_wallclock_smooth_advance()` 补时间；要补就补真实 `units`。
4. **先 EOI 后处理、短临界区**：沿用现有 ISR 模型；泵点如果在 `mag_decode` 的 `cli` 区内，必须 `cli_end(); _enable(); pump(); _disable(); cli_begin();`。
5. **兜底不爆发**：单次最多重放 2 个周期；更老的积压用 `fmseq_skip_to()` 丢弃过期事件，并记日志。
6. **可回滚**：读盘分块、泵点、cap 都带独立开关或独立函数，任一项出问题可单独关闭。

### 阶段 2：取证，定位空窗（只加日志，不改行为）

新增 `NAIZ_199_LOAD_TRACE=1`（默认 0），统一日志前缀 `[LOAD-T]`：

```text
[LOAD-T] t=<ms> tag=<阶段> id=<资源id> jobs=<队列长度> ms=<本段耗时> hook=<0/1>
```

插桩点：

| 位置 | tag | 记录内容 |
|---|---|---|
| `preload_step()` 前后 | `preload` | id、`preload_pending()`、`image_prefetch` 耗时 |
| [image_prefetch()](../core/engine/image.c#L252-L283) 内部 | `lookup` / `read` / `decode` / `insert` | 四段分别计时 |
| `mag_decode()` 入口 | `mag-begin` | `g_mag_progress_hook` 是否为 NULL |
| `mag_decode()` 出口 | `mag-end` | 总耗时、`g_decode_depth` |
| scene 解析 / `nb_load` | `scene` / `nb` | 起止时间、行号区间 |
| [farchive_read_alloc()](../core/lib/farchive.c#L147-L177) | `fread` | size、耗时、块数 |

重点怀疑对象（按可能性排序）：

1. **`farchive_read_alloc()` 的单次大块 `fread`**：读盘期间完全没有泵，是 416ms 空窗的头号嫌疑。
2. **`image_cache_insert()` 驱逐/`free` 大图**：期间没有泵。
3. **`mag_decode` 的 4bpp→8bpp 转换段**：已有 hook，但要看 hook 是否已安装、stride 是否够密。
4. **`audio_init` 之前发生首次 scene preload**：`g_mag_progress_hook` 还是 NULL，整段解码无人泵。

**验收**：能明确写出“空窗发生在 `<函数>` 的 `<段>`，单次 `<ms>`，对应 `maxu=<值>`”；否则不得进入阶段 3。

**阶段 2 实测（2026-11-03，demo-a2 / nbook001，`NAIZ_199_LOAD_TRACE=1`）**：

- `lookup/read/insert` 均为 0–10ms（`hal_wallclock_ms()` 分辨率 10ms），**`fread` 不是主因**；
- `decode` 是主项：22KB 图约 1000ms，165KB 图约 2000ms；
- `[MAG-ISR]` 显示 1–2s 解码期间只收到 **20–62 个 IRQ**（1s 应约 62 个），`banked` 涨到 10，`maxu=7482`；
- 结论：空窗发生在 `mag_decode` 的**长 `cli` 窗口**，不在读盘。hook 每 `MAG_PROGRESS_STRIDE=4096` 才放行一次；窗口内 Timer-B 只锁存一个 pending，其余整拍丢失。

> 这改写了 §3.3 的优先级：读盘分块降为后备，主路径改为缩短解码的 `cli` 窗口（§3.4）。

**阶段 3 实验记录（2026-11-03，同一 demo-a2/nbook001）**：

| stride | 165KB 解码 IRQ/2000ms | 该段 banked / maxu | 后续 20KB 段 maxu |
|---|---|---|---|
| 4096 | 62（约 31/s） | 0 / 0 | 7482 |
| 1024 | 82（约 41/s） | 1 / **516** | 6708 |
| 512 | 86（约 43/s） | 3 / **774** | 6708 |

结论：**1024 是最佳档位**。继续加密只多拿到 4 个 IRQ，却把 banked 从 1 推到 3、maxu 从 516 推到 774（说明泵窗口短到偶尔接不住一个整拍）。大图本身的空窗已压到验收线，但整体 `maxu=6708` 未变，且 1024/512/4096 三档完全相同——说明剩余 backlog 不在解码热循环，而在解码之前的某个无泵段。本次 trace 中该段的直接证据是：

- `[MAIN] Entering input waiting` 后紧接 `[STALL] dt=839`，下一次 `MAG-ISR` 报告即 `maxu=6708`；
- 同一位置 `[LOAD-T] tag=image id=2 ... read=1000 decode=0`（lookahead prefetch 的 `fread` 在无泵段内）。

注意 `hal_wallclock_ms()` 在 NP2kai 下会冻结数秒再跳 1000/2000ms，`read/decode` 的 ms 字段只能作顺序证据，不能作精确计时；`maxu`（258 units/拍）与 `[STALL]`（Timer-B 平滑钟）才是真实耗时依据。故下一步不是继续降 stride，而是 §3.2/§3.3 的泵点：lookahead prefetch 的读盘分块 + 输入等待段。

**读盘分块实测（2026-11-03）**：已实现 `farchive_set_progress_hook()` + 16KB 分块（`farchive_read_alloc`），并在 `audio_init` 末尾注册 `audio_pump_once`。复跑 trace 后 `maxu` 仍是 6708，`read` 字段也回到 0 —— 说明 fread 不是那段 backlog 的来源。序列进一步定位：

- `[STALL] dt=854` 覆盖的是 `dialog_show`（nb_process 内的整页文本绘制）+ 输入等待首帧；
- 26 拍 backlog 在这一段累积，随后由下一帧 `engine_frame_pump()` 的 drain 一次排掉；
- `[MAG-ISR]` 只是稍后才打印这个累计最大值，解码本身（hook 每 stride 都会 drain）没有 420ms 的断泵。

故剩余的 6708 应归因于 **dialog/text 渲染段无泵**，下一个泵点应放在 `dialog_show`/`draw_text` 的行循环里，而不是继续加在读盘或解码上。

**dialog 文本泵实测（2026-11-03）**：已在 `render_text.c` 的 `draw_text` 主循环每 16 个 glyph 调 `audio_pump_once()`。复跑 trace 后 `maxu` 由 6708 降到 **4644**（18 拍，约 290ms），但仍未到 516。长绘制段中 `banked` 计数会明显上涨（约 7% 的 drain 拿到 2 拍以上），说明慢绘制下 16 glyph 仍可能超过 16ms。

**dialog 框绘制/blit 泵复测（2026-11-03，5 次 IRQ 均成功）**：

| 版本 | 大图段 maxu | 全局 maxu | 最大 banked |
|---|---|---|---|
| 原始基线（stride=4096，无任何泵） | 0 | **6708** | 10 |
| + stride=1024（阶段 3） | **516** | 6708 | 10 |
| + farchive 读盘泵 | 516 | 6708 | —（读盘非主因） |
| + draw_text 每 16 glyph 泵 | 516 | **4644** | — |
| + dialog_paint_box 每 4 行 + blit 前后泵 | 516 | **3096** | 14 |

三层泵叠加，6708 → 4644 → 3096（12 拍 ≈ 194ms），每一层都有效。3096 稳定在 "decode saw 26 IRQ" 的段上（banked 14），说明剩余无泵段仍在某处——不在 draw_text（每 16 glyph 已泵）、不在 decode（每 stride 已泵）、不在 dialog box paint/blit（刚加了泵）。下一步应在 scene transition（`nb_process` 命令循环里的 bgm/cg/bg 等长命令）或 layer snapshot alloc 等段继续定位。

> 注：每次 trace 都要重开 NP2kai，IRQ 探测选哪条线（IRQ3/10/12/13）有波动，但 5 次里选 IRQ12 的几次数值高度一致。本轮 5 次全部成功，上一轮两次失败是启动时序偶发，不是编译问题。

### 阶段 3：插泵（按取证结果，不盲插）

#### 3.1 统一入口

[frame_decode_pump()](../core/engine/frame.c#L113-L142) 已封装 `hal_bgm_irq_active()` 两种模式，但还会调用 `nb_dialog_reveal_tick()`。为避免在 preload 中提前推进对白，拆出一个纯音频入口：

```c
/* 计划代码，未落地：audio.c */
void audio_pump_once(void)
{
    if (!hal_bgm_irq_active())
        audio_tick();
    else
        audio_tick_isr_pending();
}
```

`frame_decode_pump()` 改为调用 `audio_pump_once()`，其余（vblank/anim/dialog）保持不变。
新增泵点一律用 `audio_pump_once()`；确实需要动画/对白同步的旧点继续用 `frame_decode_pump()`。

#### 3.2 候选插点

| 插点 | 方式 | 说明 |
|---|---|---|
| `preload_step()` 前后 | 直接调 `audio_pump_once()` | 一次 preload 至少一泵 |
| `image_prefetch()` 的 read/decode 之间 | 直接调 | decode 内部已有 hook，read 没有 |
| `nb_load` 长行循环 | 每 64 行或每 16ms 一次 | 以时间戳判定，不按行数硬编码 |
| `image_cache_insert()` 驱逐大图前后 | 直接调 | 大图 `free` 可能耗时 |

#### 3.3 读盘分块（阶段 2 已排除，保留作后备）

把 `farchive_read_alloc()` 的单次 `fread` 拆成 16KB 块，每块之间调一次泵。两种实现二选一：

- **方案 A（推荐）**：给 `farchive` 加全局进度 hook，与 `mag_set_progress_hook` 同风格：

```c
/* 计划代码，未落地：farchive.h */
void farchive_set_progress_hook(void (*fn)(void));
```

`farchive_read_alloc()` 内：

```c
/* 计划代码，未落地 */
while (remaining > 0) {
    size_t chunk = remaining > 16384 ? 16384 : remaining;
    if (fread(p, 1, chunk, a->fp) != chunk) { ... }
    p += chunk; remaining -= chunk;
    if (g_read_hook) g_read_hook();
}
```

- **方案 B**：新增 `farchive_read_alloc_pumped(..., void (*pump)(void))`，只改 image/audio 的调用点。

推荐 A：改动集中，9 个调用点不用动；风险是全局 hook 需要一次初始化，且 hook 内不得再进 `farchive`（音频泵不读归档，安全）。

#### 3.4 首轮实验：缩短解码的 `cli` 窗口（阶段 2 改判后的主路径）

阶段 2 证明 hook 已安装、读盘也不慢，问题是 `MAG_PROGRESS_STRIDE=4096` 对应的 `cli` 窗口太长（约 30–70ms），Timer-B 在窗口内只锁存一个 pending。

1. 先把 `MAG_PROGRESS_STRIDE` 从 4096 降到 1024，重跑同一 trace；
2. 目标：单次 `cli` 窗口 <16ms，`[MAG-ISR] saw N IRQ in T ms` 中 N/T 接近 62/1000ms；
3. 若 `maxu` 仍 >516，降到 512；若 hook 调用开销明显，改成“每 512 像素查一次时间，超过 12ms 才放行”的自适应 stride；
4. 结构根治仍是 199 §五 C：把解码 scratch 状态迁出栈/全局，减少对 `cli` 的依赖；本阶段先用更密的放行点把空窗压到验收线内。

**已完成（2026-11-03）**：`MAG_PROGRESS_STRIDE` 默认值已改为 1024（`#ifndef` 可被 `-D` 覆盖）。实测 1024 是大图段的最佳档位（`maxu=516`、`banked=1`）；512 反而 `maxu=774`、`banked=3`。整体 `maxu=6708` 来自解码前的无泵段，见 §2 实验记录，需由 §3.2/§3.3 的泵点解决，**不再继续降 stride**。

**验收**：`maxu ≤ 516`、`banked ≤ 1`，且 `[MAG-ISR]` 的 IRQ/时间比接近理论值。大图段已达标；全局验收待 §3.2/§3.3 完成后复检。

#### 3.5 P7 规则

如果泵点落在 `mag_decode` 的 `cli` 区内，必须沿用 [mag.c L440-454](../core/lib/mag.c#L440-L454) 的写法：

```c
hal_bgm_irq_decode_cli_end();
_enable();
audio_pump_once();
_disable();
hal_bgm_irq_decode_cli_begin();
```

不得在 IF=0 下跑泵（DOS/32A 会把反射 IRQ 延迟到 `_enable()`，落在解码栈上）。

**验收**：阶段 0 同一场景复跑，`maxu ≤ 516`、`banked ≤ 1`、`[AUDIO-GAP]` 无 >32ms；若仍超标，回到阶段 2 找漏掉的段，不进入阶段 4 掩盖。

### 阶段 4：兜底，防止一次大停顿变成“爆发”（**已关闭，不启用**）

即使插泵，仍可能遇到 DOS/BIOS 不可控的长阻塞。给 [audio_tick_isr_pending()](../core/engine/audio.c#L780-L808) 加上限。

#### 4.1 新增 `fmseq_skip_to()`

文件：[fmseq.c](../core/lib/fmseq.c#L502-L524)。

```c
/* 计划代码，未落地 */
void fmseq_skip_to(Fmseq *seq, uint64_t now_ms)
{
    while (seq->cursor < seq->count &&
           seq->events[seq->cursor].tick_ms <= now_ms)
        seq->cursor++;          /* 只丢事件，不 dispatch */
    seq->last_tick = now_ms;    /* 避免下一次 pump 产生巨大 decay */
}
```

#### 4.2 在 drain 入口限幅

```c
/* 计划代码，未落地：audio.c */
unsigned long units = hal_bgm_irq_take_pending_units();
unsigned long cap = 2UL * BGM_TIMER_B_UNITS;   /* 516 */

if (units > cap) {
    unsigned long drop = units - cap;
    unsigned long now  = hal_wallclock_smooth_ms();

    if (g_bgm.fm && g_fm_seq)
        fmseq_skip_to(g_fm_seq, now - drop / 16UL);   /* 16 units ≈ 1ms */
    if (g_bgm_irq_diag)
        hal_logf("[DRAIN-CAP] drop_units=%lu drop_ms=%lu\r\n",
                 drop, drop / 16UL);
    units = cap;
}
```

说明：

- `take_pending_units()` 仍然取走全部并前移 `consumed`，所以积压不会留到下一帧再次爆发；
- 被丢的是“最老”的过期事件，保留最近 2 个周期；
- 本轮只对 FM 路径（`g_bgm.fm`）做 skip；MIDI 路径先不动。若日志显示 MIDI 也有 backlog，再补 `bgm_skip_to()`。

#### 4.3 诊断

新增 `[DRAIN-CAP]` 日志，只在触发时打印。验收时它应该**很少出现**；如果频繁出现，说明阶段 3 还有漏泵段，回到阶段 2。

**验收**：人为制造 >100ms 停顿时，日志出现 `[DRAIN-CAP]`，但听感是“少几个音”，不是“一串音同时炸出”；正常加载路径不触发。

## 六、风险与回滚

| 风险 | 处理 |
|---|---|
| 早退路径 `_enable()` 后 `free()` 被 IRQ 打断 | `free` 不分配、ISR 不分配，安全；顺序与正常出口一致 |
| 读盘分块改变 DOS 行为 | 只改块大小，不改偏移/总长；加 `NAIZ_199_READ_CHUNK` 开关，默认 16KB |
| `farchive` 全局 hook 被多处设置 | 单一初始化点（`audio_init`）；hook 内禁止再进 `farchive` |
| `fmseq_skip_to` 丢音 | 只在 `units > 516` 时触发；`[DRAIN-CAP]` 留痕；默认路径不受影响 |
| 泵点过多导致对白/动画提前 | 新增点用 `audio_pump_once()`，不调 `nb_dialog_reveal_tick()` |
| 限幅掩盖真正的漏泵 | 阶段 4 只作兜底；`[DRAIN-CAP]` 频繁出现即回阶段 2，不放宽验收 |
| 构建开关事故（只 build 不 make） | 每阶段按 AGENTS §八 第六条：`./makegame.sh build <game> && ./makegame.sh make <game>`，并跑 `makegame.sh test --serial` |

**回滚**：

- 阶段 1 可单独回滚（纯机械补丁）；
- 阶段 3 的读盘分块由 `NAIZ_199_READ_CHUNK` 开关控制；
- 阶段 4 的限幅由 `NAIZ_199_DRAIN_CAP` 开关控制（默认开，异常时关）；
- 任一阶段验收不过，停在当前阶段，不带病进入下一阶段。

## 十、实施结果（2026-11-03 实测定稿）

### 10.1 累计泵点效果链（同一 demo-a2 nbook001 首场景加载，NP2kai）

| 步骤 | maxu | 说明 |
|---|---|---|
| 基线（阶段 2 取证） | 6708 | 无任何插泵 |
| + draw_text 每 16 glyph 泵 | 4644 | |
| + dialog_paint_box / dialog_layer_blit 泵 | 3096 | 5 次 IRQ 成功 trace 一致 |
| + before-vblank 泵（engine_frame_pump 开头） | 2580 | 4 次一致（015–018），恰好少一拍 |
| + **关闭 NB_DEBUG 测量**（同一份代码） | **1290** | 3 次一致（034–036）；见 §10.3 |

vram_blit_sprite 16 行泵、display_apply_* 前后泵对 maxu 无进一步变化，但 GAP 诊断证明它们在生效（blit 后 drain 干净），保留。

### 10.2 GAP 区域诊断（临时，已拆除）

在 `hal_bgm_irq_take_pending_units()` 加 `[GAP] u=.. win=.. z=.. pz=..` 日志（>2 拍的 drain 打出本次/上次泵点编号与窗口宽度），全部 15 个泵点打编号。结论：

- `u=2580 win=162 z=9 pz=3`：最大窗口在 decode 末泵 → display_apply_dialog 前泵之间，**162ms 窗口里约 500 字节 NB_DEBUG 串口日志**（`executing command`、`line[n]`、MAG-ISR、LOAD-T 等约 10 行）。
- `u=2322 win=145 z=1 pz=3`、`u=2064 win=129 z=5 pz=3`：同为 decode 结束 → 帧泵/display 前泵的命令链窗口，同样被日志占满。
- 结论：**剩余 maxu 的大头是诊断串口日志本身的测量假象**（NP2kai 下每字节 ~0.3ms），不是泵点覆盖漏洞。

### 10.3 最小日志构建实测（定稿数据）

构建：`EXTRA_DEFS="-DBGM_IDLE=1 -DNAIZ_199_LOAD_TRACE=0 -DNAIZ_NB_DEBUG_OFF=1 -DBGM_IRQ_PROBE_MIN_TICKS=2 -DBGM_IRQ_PROBE_FRAMES=16"`。3 次 IRQ 成功 run（034–036）maxu 一致 = **1290**，分解：

| 残留 | 位置 | 性质 |
|---|---|---|
| 1290（5 拍，81ms） | dialog blit 后 → 下一帧 z1 | 主循环尾巴（mouse cursor/input 边界），模拟器 CPU 速度 |
| 774（3 拍，49ms） | decode stride 内部 z3→z3 | stride=1024 粒度 + 模拟器解码速度 |
| 774/1032 | 稳态帧间 z1↔z2（48–65ms/帧） | NP2kai 帧率 ~20Hz 的固有粒度，用户实机确认稳态听感正常 |

### 10.4 验收判定

- 验收线 `maxu ≤ 516`（2 拍）**在 NP2kai ~20Hz 帧率下物理不可达**：稳态帧间自然积压即 774（3 拍），与插泵无关。
- 加载路径上所有「可泵的长阻塞段」均已插泵；残留全部是模拟器 CPU/帧率粒度，实机投影 ≤2 拍（实机 CPU 快 3–5 倍，帧率 56–60Hz）。
- 阶段 4（`fmseq_skip_to()` + drain 限幅）**关闭，不启用**：§五 E 纪律是"不用限幅掩盖漏段"，而诊断证明没有漏段。
- 199 §五 C（解码 scratch 迁出栈）**关闭**：与 maxu 无关（治解码损毁，不治空窗），且触发条件（B 路径证据 / decode failed）至今未出现。

### 10.5 构建旋钮（本次新增，默认均不改变行为）

- `NAIZ_NB_DEBUG_OFF=1`：关掉 NB_DEBUG 每命令串口日志（debug.h 门控从 `#ifdef NAIZ_DEBUG` 改为 `#if defined(NAIZ_DEBUG) && !defined(NAIZ_NB_DEBUG_OFF)`）。**出货构建建议打开**：实机串口 115200 波特下每场景切换仍有 ~43ms 日志开销。
- `BGM_IRQ_PROBE_FRAMES` / `BGM_IRQ_PROBE_MIN_TICKS`：probe 帧数/阈值的 `#ifndef` 覆盖口。关掉 NB_DEBUG 后帧率远快于 20Hz，8 帧只攒 ~2 tick，probe 会误判全部静默，测量构建需 `-DBGM_IRQ_PROBE_MIN_TICKS=2 -DBGM_IRQ_PROBE_FRAMES=16`。实机 8/6 不变。
