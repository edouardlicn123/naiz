# 146 — BGM 现状代码分析与改造建议

> **状态**：`分析（只读；不含任何代码改动）`
> **版本**：`0.3.037`
> **创建于**：2026-10-18
> **类型**：非实现轮 —— 逐读当前 BGM 通路代码，给出「BGM 应该怎么改」的优先级化方案
> **前序**：`144`（开源 PC-98 游戏与 BGM 实现调研）、`145`（ADV98 / 98fmplayer / ReC98 逐读记录）、`134`（方案 C：OPNA Timer-B 中断驱动音泵，计划中）、`131`（剩余颤动分析）、`139`（虚拟时钟单窗速率尖峰钳制）

---

## 一、一句话结论

当前 BGM 的节拍是**「软件重建的软时钟 × 帧泵」**，`lib/vclock` 的全部机制（窗测速 + slew + IIR + ±25% 钳制）都只是在**掩盖**一个粗粒度、成簇交付的 DOS 时钟——这是结构天花板，不换时基就会反复出现新形态的抖动（`133` 修一版、`139` 又修一版）。

在此之上还叠着**四个确定的 BGM 正确性缺陷**（循环接缝早断、回卷丢相位、事件突发齐发、pump 覆盖依赖约定），它们不依赖中断即可修复、可在主机单测。

改造建议：**P0（修正确性缺陷）+ P2（ADV98 纪律审计）立即可做；P1（Timer-B 中断，`134` 方案 C）单独立项，因本环境无法验证中断、写错静默死机。**

## 三、根本性质（为什么还在颤）

1. **节拍 = 软时钟重建 × 帧泵**。`hal_wallclock_ms()` 本身是 1/100s 量化、成簇交付的粗源；`vclock` 用滑动步长去「猜」真实速率，`139` 又加了 ±25% 窗钳制防尖峰。这些都是补偿手段，不是时基本身。`134` 已判定这是结构性的：只要 tick 由帧泵驱动的软时钟产生，加载期/低 pass 率期就会 tempo 塌陷。
2. **帧泵粒度 = 一帧**。真机 ~60Hz → 16.7ms 量化；NP2kai pass 率 ~20Hz（`hal_pc98.c:154-155`、`frame.c:28-29` 注明）→ ~50ms 量化。音符起音时间被量化到帧，原版靠 Timer-B 中断把它降到芯片分辨率。
3. **原版对照**（`145`）：ADV98 把音泵交给常驻 PMD 驱动（Timer-B 中断），游戏侧只 `int $0x60` 下命令、**不 `cli`**；98fmplayer 亦以 Timer-B 为音乐 tick。naiz 是「自研 fmopn 直写、无外部常驻、无中断」——是相反取舍，代价即节拍由主循环协作轮询决定。

## 四、具体代码缺陷（决定性的 BGM bug，与颤独立）

### 4.1 循环接缝早断（曲长丢失）

`fmseq_finished()` 在**最后一个事件派发完**即为真（`fmseq.c:547-550`），而 `midi_parse` **不记录 EOT 的绝对时间**（`midi.c:198-201` 直接 `break`）。若原曲末尾有静默（EOT 晚于末事件），naiz 会在末音刚发出就回卷 → **每次循环比原曲短、尾音被裁**。MPU 路径同病（`audio.c:567`）。

### 4.2 回卷丢相位

FM 路径回卷用 `g_bgm.wall0 = now`（`audio.c:536`），MPU 路径同（`audio.c:568`）。`now` 是「探测到回卷的那一帧」，而非 `wall0 + song_len` → 每次循环丢掉 `cur - song_len` 的余量，**每循环累积最多一帧漂移**，且循环边界处节拍不连续。正确做法是 `wall0 += song_len_ms`（保留相位），仅当余量 ≥ 一曲（长时间未 pump）时才用 `now` 兜底。

### 4.3 事件突发齐发

`fmseq_pump`（`fmseq.c:505-509`）与 MPU 路径（`audio.c:552-563`）的 `while (tick_ms <= cur)` 会把**整个窗的积压事件在同一 pass 全部派发**。当 `cur` 因窗口/加载跳变时，一串音符会在几毫秒内齐发；FM 路径还会在单帧内写爆 OPNA 寄存器（每写 = 两次 `outb`）。`vclock` 缓解但不根除。

### 4.4 pump 覆盖靠约定、无强制

BGM 只在 `engine_frame_pump()` 被调用处推进（见 §二 列表）。任何**未覆盖的长阻塞循环**（快照/缩略图合成、map 加载、未来新增的忙等）都会让 BGM 停帧或积压。当前覆盖看似完整，但**没有任何机制保证新增阻塞循环会记得 pump**——属易复发面。`frame_decode_pump` 只挂了 MAG 解码的 progress hook（`audio.c:462`）。

## 五、改造建议（按优先级）

### P0 — 低风险、可主机单测（不引入中断）

1. **记录曲长**：`midi_parse` 增加 `out_len_ms`（EOT 的绝对 tick→ms；无 EOT 时用末事件 tick）。同步更新 `midi.h` 原型与 `test_midi`。
2. **循环按曲长**：`fmseq_finished` 语义改为「播放时刻到达曲长」；MPU 路径回卷判据同步。回卷 `wall0 += song_len_ms`（余量 ≥ 一曲时用 `now` 兜底）。
3. **事件派发分片**：每 pass 给 `fmseq_pump`/MPU 派发加**事件数与字节预算**，把整窗积压摊到多帧，消除齐发与单帧寄存器写爆。
4. **补齐/护住 pump 覆盖**：审计所有长阻塞循环是否 `engine_frame_pump()`；对无法 pump 的路径（若存在）加注释与守卫，避免新增循环漏 pump。

> 以上 1–3 可纯主机验证（`fmseq` 设计为「无端口、可测」，见 `fmseq.h:1-7`；`test_fm_seq` 已存在）。4 可加静态守卫（仿 `test_frame_pump.py` 的 `PUMP_CALLERS` 断言）。

### P1 — 根治：Timer-B 中断驱动（`134` 方案 C，单独立项）

- 需从零建：OPNA Timer-B 编程（`$24-$27` 写入、`$29` 使能 IRQ）、DOS/4GW DPMI 中断挂钩（`_go32_dpmi_set_protected_mode_interrupt_vector` + `_go32_dpmi_lock_code/data`）、PIC 级联 EOI、链到原 ISR；ISR 内推进 `fmseq`。
- **现状**：`core/plat/` **无任何 DPMI ISR / `cli` / `sti` / EOI 基础设施**（`pc98.h:191-207` 只定义了 `PIC_EOI` / `IRQ_*` 常量，零使用）。
- **风险**：本环境（NP2kai）无法验证中断投递与级联 ACK，写错 = 静默死机（AGENTS §八）。故须 **build flag 门控 + 失败回落现有帧泵**，并按 `134` §3 先做「中断投递探针」判定可行性。
- **前置未确认项**：NP2kai 是否/以何频率投递 OPNA Timer IRQ（`134` / `F04`）、DOS/4GW 下默认 IRQ 号与向量映射（`G08`）、`$29` 默认位行为（`F04:173`）。

### P2 — 纪律（`145` 的 ADV98 教训）

- **BGM 活跃期不写 `cli`**（当前无，保持）。
- **`fopen`/`fread` 与逐像素合成移出帧窗口 / 预载**：naiz 已有 `image_prefetch` / `nb_prefetch_lookahead`（`frame_decode_pump` 机制），继续扩展覆盖 map / 存档缩略图等长耗时构造路径。
- 审计点：任何在 BGM 播放期间做重 I/O 的代码，优先改为预载 + 帧内增量。

## 六、建议与下一步

1. **先做 P0（1–3 是确定的 BGM 正确性 bug，降抖动且可单测）+ P2 审计**。
2. **P1 单独立项**：先写实施 devdoc、按 `134` §3 落「中断投递探针」，确认可行后再挂音泵；本环境不能验证中断，不得与 P0 混提。
3. 若用户实机 `[VC]` 实测 `tgt` 为**平滑漂移**而非尖峰（`139` §遗留），则 P0 足以收敛感知抖动；若仍为**周期性 tempo 塌陷**，则唯 P1 根治。
