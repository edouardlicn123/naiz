## 一、结论速览

1. **代码级确证了 `F05` 的节拍模型**：原版 BGM 的**音乐 tick 由 YM2608 Timer-B 硬件中断驱动**，主循环完全不管节拍。`98fmplayer` 的驱动重实现里，Timer-B 溢出 → `driver_opna_interrupt()` → 处理一拍音符（`pmd_timerb`），Timer-A 只作子 tick（fadeout/SSG 效果）。
2. **拿到了完整的 PMD 游戏侧调用 API**（`ADV98` + ReC98 合并）：`AH=00/01/02/03/06/0B/0C/22h`，其中 `06h`/`0Bh` 取缓冲区段:偏移、`22h` 取缓冲区大小（KB）——**游戏把曲子文件直接读进驱动的常驻缓冲**，而非让驱动自己开文件。
3. **集成纪律**（`ADV98` 设计笔记）：①**禁止 cli/sti**，让 PMD 中断照常触发；②**把文件 I/O 与逐像素合成移出 VSYNC 窗口**（改预载），否则低速机「段间隔与 BGM 都受影响」——**这正是 naiz「演奏时快时慢」的同构病症，且原版已给出规避写法**。
4. **`98fmplayer` 给出节拍换算与计时模型的精确形式**：Timer-B 周期 = `16 × (256 − timerb)` 样本；`tempo = 0x112c / (256 − timerb)`；`0x29=0x83`（IRQ 使能 + 双定时器）+ `0x27=0x3f`（load+enable 双定时器）——**与本仓 `fmseq` 无定时器、靠帧泵推 tick 形成正面对照**。
5. **净增量相对 144 §七 有三条**：完整 API 表、缓冲移交/溢出的具体后果（ReC98 2021-05-12 逐字）、以及可搬迁到 naiz 的「低抖动主循环」纪律。

## 三、ADV98（`yarufu/pc98`）：游戏侧集成 PMD 的最小完整样本

### 3.1 常驻检测：读 INT 60h 向量 + 签名

`src/pmd.c` **【核实】**：

- 驱动挂钩在 **中断 `0x60`**（`PMD_VECTOR_NUMBER 0x60`）；
- 检测方式：读 IVT 的 `0x60*2` 处得 offset/segment，再从 `offset + 2`（`PMD_SIGNATURE_OFFSET 2`）起比对三字节 ASCII **`"PMD"`**；三字节全中即认为常驻（`pmd_is_resident`）。
- 结论：**PMD 是挂在 INT 60h 的常驻 TSR，签名位于入口偏移 +2**。游戏用一次 IVT 读取就能判定，不需要探测硬件。

### 3.2 控制 API（游戏 → 驱动，全部经 `int $0x60`）**【核实】**

| AH | 功能 | 入参 | 出参 | ADV98 调用点 |
|---|---|---|---|---|
| `00h` | 开始/播放当前缓冲曲 | — | — | `pmd_start_music` |
| `01h` | 停止 | — | — | `pmd_stop_music` |
| `02h` | 淡出（AL=08h 为该实现取值） | AL | — | `pmd_fadeout_music` |
| `03h` | SSG 音效 | AL=编号 | — | （未用，仅封装） |
| `06h` | 取**音乐缓冲**段:偏移 | — | DS:DX | `pmd_get_music_buffer` |
| `0Bh` | 取 **FM 音效缓冲**段:偏移 | — | DS:DX | `pmd_get_fm_se_buffer`（static） |
| `0Ch` | 播放 FM 音效 | AL=编号(0–127) | — | `pmd_play_fm_se` |
| `22h` | 取**缓冲大小**（KB） | — | AL=音乐、DL=FM 音效 | `pmd_get_music_buffer_size` / `pmd_get_fm_se_buffer_size` |

- `22h` 的 AL/DL 单位是 **KB**：ADV98 取 `AL & 0xFF`（或 `DL & 0xFF`）再 `× 1024`（`src/pmd.c` `pmd_get_music_buffer_size`/`pmd_get_fm_se_buffer_size`）。
- 与 ReC98 的 `AH=09h`（查驱动类型，§五.1）合并即得**完整 API 面**：`09h` 分类、`22h` 容量、`00/01/02/03/0Ch` 控制、`06h/0Bh` 取缓冲。
- **关键定性**：游戏与驱动之间**只有命令，没有寄存器直写**（`F05` §5 的结论在代码级坐实）。

### 3.3 缓冲移交与「写寄存器式装载」

`src/pmd.c` **【核实】**：`pmd_load_music_file()` 的流程 = 查 `06h` 拿 `seg:ofs` → 查 `22h` 拿 `max_size` → `fopen/fread`（C stdio，非 `INT 21h AH=3Fh`）→ **逐字节经 far 指针写入驱动缓冲**（`pmd_write_far_byte`，把线性地址拆回 `seg+ (linear>>4) : linear&0xF`），**超 `max_size` 立即 `fclose` 并返回失败**。

- 与 ReC98 的差异：ADV98 用 C 库读文件后再拷进缓冲；ReC98 的 `snd_load()` 直接用 `INT 21h AH=3Fh` 读进缓冲（§五.2）。**共同点**：都是「游戏拥有文件 I/O，驱动只提供缓冲」。
- ADV98 的容量检查（`loaded + read_size > max_size` → 拒绝）正是 ReC98 §五.4 所述**原版 ZUN 缺失**而致溢出的那道防线。

### 3.4 脚本层语义与去重

`src/script.c`（`handle_external_command`）**【核实】**：

| 脚本命令 | 行为 |
|---|---|
| `#bgm <file>` | 与当前 `state->bgm` **同名则整条 no-op**；否则记入 state → `stop` → `load` → `start` |
| `#bgmstart` | `start`（续播当前缓冲） |
| `#bgmstop` | `stop` |
| `#bgmfade` | `fadeout` |
| `#se <n>` | 若 FM 音效库已载，`pmd_play_fm_se(n)` |

- **切曲先停再载**（`pmd_stop_music()` 先于 `pmd_load_music_file()`）= ReC98 记录的原版教训（`144` §三.1.4），ADV98 直接照此实现。
- **同名去重**：避免同曲重复 load（与 naiz `bgm` 记忆 key 的意图一致）。
- 调用点：`main.c`（初始化/存档恢复/退出 cleanup）、`title.c`（`TITLE.M`）、`menu.c`。

### 3.5 部署与常驻方式

- `RUN.BAT` **【核实】**：`if exist pmd86.com pmd86.com` → 否则 `if not exist pmd86.com pmd.com` → `adv98.exe`。即**驱动作为独立 `.COM` 先于游戏常驻**，且按机型优先 `pmd86.com`（PC-9801-86/OPNA），回落 `pmd.com`。
- 与 ReC98 的「OPN- / PC-9801-26K 兼容」vs「OPNA / PC-9801-86 兼容」二分（§五.1）一致：**驱动分型由驱动本体承担，游戏只选一个常驻**。
- FM 音效用 PMD 标准 **`SE.EFC`** 单文件（编号 0–127；`1` 保留为系统决定音）——`docs/011.design_notes.md` §第28话 **【核实】**；`SE.EFC` 缺失时游戏照常运行（FM SE 静默），BGM 不受影响。
- 标题 BGM 固定文件 `TITLE.M`（`src/title.c`）。

### 3.6 集成纪律（对 naiz 直接相关）**【核实】**

- **禁止 cli/sti**：`docs/000.development_notes.md`「割り込み禁止は行わないため、PMD 割り込みは通常どおり動作できる」——不做中断禁止，PMD 的 Timer-B 中断才能照常运行。
- **把 I/O 与逐像素工作移出 VSYNC 窗口**：`docs/011.design_notes.md`「VSYNC待ち」节——正式方式在演出**前**一次性预载整张 SPR，演出各阶段（共 34 段）只做「等一次 VSYNC + 从 RAM 拷到 VRAM」，`fopen/fclose/fseek/fread` 每段 **0 次**；被废止的旧方式「把文件 I/O 与透明色判定混入 VSYNC 之间，低速环境下会影响段间隔与 **BGM**」。
- 判定：**naiz 的「演奏时快时慢」与原版规避的正是同一类病灶**——把不定长工作放进帧/中断窗口。原版解法是**预载 + 每帧少做事**，而非去调时钟常数。

### 3.7 `src/fm86.c`：直写 OPNA 的 BEEP 音效（已停用）

**【核实】** 一个**独立于 PMD**的兜底音效实现：

- 端口 `0x188`（地址）/`0x18A`（数据）= 86 板普通组；`0x28` 作 KEYON（`0xF0` 开、`0x00` 关）；`0xB0=0x07`、`0xB4=0xC0`、`0xA4=0x22`、`0xA0=0x69`。
- 计时用 **GDC 状态端口 `0xA0` bit5（VSYNC）轮询**（`wait_vsync`/`wait_frames`），非定时器中断。
- `main.c` 中 `se86_init()` 已被注释，注记「BGM は PMD に任せるため」——**作者最终选择把发声整体交给 PMD，而非引擎直写**。这与 naiz「自研 fmopn 直写、无外部常驻」是相反取舍。

### 3.8 与 naiz 对照小结

| 维度 | ADV98 | naiz 现状 |
|---|---|---|
| 音序器归属 | 外部常驻 PMD（引擎不含） | 内置 `core/lib/fmseq.c` |
| 节拍源 | PMD 的 Timer-B 硬件中断 | `vclock` 帧泵（`hal_wallclock_smooth_advance`） |
| 无音源时 | BGM 静默降级，游戏照跑 | fail-loud（AGENTS §九.6） |
| 主循环纪律 | 预载 + 每帧少做事 + 不 cli | 帧内做解码/加载（`143` 未收敛项之一） |
| 音效 | PMD FM SE（`SE.EFC`） | PCM 单通道（与 BGM 后端分离） |

## 四、`98fmplayer`：格式与节拍模型的代码级实证

### 4.1 中断驱动回调链

`fmdriver/fmdriver.h` **【核实】**：`struct fmdriver_work` 含 `void (*driver_opna_interrupt)(struct fmdriver_work*)`（由驱动注册、由 opna 调用）与 `uint8_t timerb; uint32_t timerb_cnt;`。→ **驱动被 Timer-B 中断推动**，不是被主循环轮询。

### 4.2 Timer-B = 音乐 tick，Timer-A = 子 tick

`fmdriver/fmdriver_pmd.c` **【核实】**：

- `pmd_timer()`：读 OPNA 状态（`opna_status`）→ bit0 = Timer A 命中 → `pmd_timera()`；bit1 = Timer B 命中 → `pmd_timerb()` 并 `timerb_cnt++`。
- `pmd_timerb()`：`pmd_proc_parts()`（推进所有声部的音符）+ 重写 Timer-B（`pmd_timerb_write` → `opna_writereg(0x26)`）+ `pmd_update_note_meas()`（`tick_cnt`/`meas_cnt`）。
- `pmd_timera()`：每第 8 个 Timer-A tick 做 `pmd_fadeout_tick()`；另跑 SSG 效果（`pmd_ssgeff_tick`）。
- **即：音乐节拍 = Timer-B；fadeout/效果 = Timer-A（更细分频）。**

### 4.3 寄存器序列（复位）

`pmd_reset_opna` / `pmd_reset_timer` **【核实】**：

- `0x29 = 0x83`：`0x83 = 1000_0011b` → bit7 = IRQ 使能、bit1/bit0 = Timer B/A IRQ 使能。
- `0x27 = 0x3F`：双定时器 **load + enable**（写 1 到标志位兼清标志）。
- `0x26 = timerb`（Timer B 值）；`0x25 = 0x00`、`0x24 = 0x00`（Timer A 高位/低位 = 0）。
- 复位还写 `0x22 = 0x00`（关 LFO）、`0xB4+c = 0xC0`（pan）、`0x10 = 0xFF`（rhythm）。
- 默认 `timerb = 200`（即 `0x100 − timerb = 56` 计数）。

### 4.4 tempo ↔ timerb 换算

`pmd_calc_tempo` / `pmd_calc_tempo_rev` **【核实】**：

- `tempo = 0x112C / (256 − timerb)`（`0x112C = 4396`），带四舍五入（`% timerb & 0x80`）与上限 0xFF；
- 逆向同式。默认 `timerb=200` → `tempo = 4396/56 ≈ 78`（PMD 默认速度）。

### 4.5 `libopna/opnatimer.c` 计数模型（样本域）

**【核实】**：

- `TIMERA_BITS=10`（1024）、`TIMERB_BITS=8+4=12`（4096，`TIMERB_SHIFT=4`）。
- 写 `0x26=v` 时 `timerb_cnt = v << 4`；计数在**输出样本域**自增，`0x24/0x25` 组 Timer A 值。
- 溢出条件：`timerb_cnt` 归零且 enabled → 置状态 bit1 并 `interrupt_cb()`，**同一混音回调里即触发**（`opna_timer_mix_oscillo`）。
- ⇒ Timer-B 溢出周期 = `(1<<12) − (v<<4)` 样本 = `16 × (256 − v)`；`v=200` → 896 样本。
- 与 `F04` Timer A/B 硬件规格、`F05` PMD 节拍模型一致；`98fmplayer` 是「以主时钟样本数计」的一种忠实实现。

### 4.6 与 naiz `vclock` 的对照

| | `98fmplayer`/PMD | naiz |
|---|---|---|
| 时基 | OPNA Timer-B 硬件溢出（与 CPU 主循环解耦） | 帧泵累加墙钟（`vclock.c`），受帧率与帧内工作量影响 |
| 抖动来源 | 仅硬件计数精度 | 帧率波动 + 帧内 I/O（`139` 钳制、`133` 平滑皆在补这个） |
| 结论 | 根治 = 方案 C（`131`/`134`：Timer-B 中断驱动） | 现为软件近似，需靠平滑/钳制抑制 |

## 五、ReC98 博客逐读（`F05` 的一手出处）

### 5.1 2021-05-12（P0139：TH04/TH05 声音初始化）

**【核实】**：

1. **BGM/SE 模式判定** = 「PMD 常驻类型」+「Option 菜单设置」；PC-98 东方只需区分 **「OPN- / PC-9801-26K 兼容」** 与 **「其余（OPNA / PC-9801-86 兼容）」** 两类。
2. **`AH=09h`**：返回驱动类型；作者只记录了上述两种结果（完整枚举留给爱好者）。
3. **`snd_load()`** 用 **`INT 21h, AH=3Fh`** 把曲文件**直接读进 PMD（或 MMD）的缓冲**；硬编码上限 20 KiB（TH02–TH04）/ 64 KiB（TH05）——**错**。
4. **`AH=22h`**：取**实际缓冲大小**，正是为此提供；不给参数时返回 PMD 默认值。**MMD 没有等价函数**。
5. **内存布局**：PMD 把驱动代码与数据缓冲（曲/乐器/效果音）**放在同一段**；TH04/TH05 随附的 **PMD86 v4.8o** 驱动留给缓冲的余量恰 **45,555 字节**；KAJA 对 `/M`、`/V`、`/E` 命令行参数做校验，超 **40 KiB** 即报错拒驻留。
6. **`GAME.BAT`**（TH02）：FM 曲 **8 KiB** / 音效 **2 KiB** / MMD **12 KiB**（故 `snd_load()` 的硬编码尺寸怎么看都错）。
7. **溢出后果**：`INT 21h AH=3Fh` 目标地址被 DOS 按线性处理——DOS 3.3 读越段；DOS 5.0/DOSBox-X 截断到段内剩余；结果**覆盖驱动之后的游戏 `.EXE` 与 master.lib**。
8. **最大曲目** = `幽夢 ～ Inanimate Dream` 的 -86 版 **8,099 字节**（刚好卡在 8,192 之下）。

### 5.2 2023-11-30（P0262/0263：菜单 + 首启声音设置菜单）

**【核实】**：

1. TH04/TH05 **首启声音设置菜单**含 BGM 模式 / S.E. 模式子菜单（两者代码近乎复制）。
2. 配置存于 **`MIKO.CFG`**；**把该文件第 1 字节置 `FF` 可重新触发**首启菜单（可复现排查用）。
3. TH04 一个 S.E. 模式 bug：改 S.E. 模式在菜单内**不即时生效**，需再改 Music 模式或进游戏；TH05 已修。
4. 与 naiz 关联：`MIKO.CFG` 对应本仓项目侧 `config.toml`（编译期）与玩家侧 `USER.CFG` 分家（AGENTS §十一）；原版把「BGM/SE 模式」也落盘为玩家配置。

## 六、对 naiz / 方案 C 的净增量（相对 `devdocs/144` §七）

1. **完整 API 表**（§三.2）已可直接当作审 `core/engine/audio.c` 后端检测/`audio_bgm_start` 的**对照清单**：naiz 的「后端自动检测 + 止/载/播」语义可从「PMD 的 `09h/22h/00/01/06h`」找到一对一参照。
2. **抖动规避纪律**（§三.6）是**可立即搬用**的：预载到帧窗口之外、禁止 cli/sti、每帧少做事。**这与方案 C 不冲突**——即使不上定时器中断，先按此纪律消掉「帧内不定长工作」也能改善（`143` 未收敛项的候选缓解）。
3. **节拍模型精确化**（§四）：Timera/B 分工、`0x29=0x83`/`0x27=0x3f`、`tempo=0x112c/(256−timerb)`——若推进方案 C，这些即寄存器级实现蓝本（与 `F04` 互证）。
4. **缓冲安全**（§五.3–5.4）：容量查询（`22h`）与溢出防线——若未来 naiz 引入外部曲/音色资产管线，登记为检查项。
5. **零代码改动**：本轮不产生任何 `core/`/`tools/` 修改，不触发 `bump_version`（AGENTS §十六）。

2. `AH=03h`（SSG 音效）ADV98 仅封装未调用，编号域与 PMD 手册对应关系**【未确认】**。
3. `pmd_get_music_buffer`（`06h`）返回值的 `DS:DX` 与 `22h` 的 KB 换算是否对所有 PMD 版本一致**【未确认】**（仅 PMD86 v4.8o 与 ADV98 约定）。
4. `98fmplayer` 的 `driver_pmd`/`driver_fmp` 是**为播放器重实现**，未必逐位等同原驱动（其本身 README 有精度边界声明）；用作**模型**而非规范。
5. `ADV98` 的 `pmd_write_far_byte` 线性地址拆段假设 `base_ofs` 已含在 `linear` 中、且缓冲不跨 64K 边界——若跨段其拆法是否仍正确**【未确认】**。
6. `144` §九 的遗留未确认项（FSP 源码、pc98sndpmdtools/hoot 许可、PC98src 内容、Porolith 等）**本轮未推进**。
